# RAN2 #132 增量简报

> 共 364 条事件 · [会议目录](https://www.3gpp.org/ftp/tsg_ran/WG2_RL2/TSGR2_132/)

## 本会议特性进展（6G）

### 6GR 能效（基于 15 条已摘要 6G 事件）

本会议将 UE DRX 采纳为 6G 支持 UE 和 network nodes 节能的关键特性，并以类似 C-DRX 的机制作为 UE sleeping opportunities 的研究起点。会议推进了 Cell DTX/DRX 与 UE DRX 的联合设计研究，重点关注睡眠机会对齐、灵活配置以及避免重复机制。WUS 方面，允许其触发特定的 OnDuration window configurations，同时继续研究与 C-DRX 的协同或解耦，以及跨 RRC states 的 LP-WUS/WUR；相关协议细节仍待后续明确。

**关键结论**

- UE DRX 被采纳为 6G 的关键特性，用于支持 UE 和 network nodes 的 energy and power saving。
- UE sleeping opportunities 以假设支持类似 C-DRX 的机制为研究起点，具体细节继续研究。
- 对于 6GR，允许 WUS 触发特定的 OnDuration window configurations，通过适当的 PHY setting 实现节能的 receiver reactivation。

**待决问题**

- 研究所有 RRC states 下的 Cell DTX/DRX 及其对 common signal/channel transmission 和 UE-specific transmission/reception 的影响；non-connected state 的设计仍需等待 common signal、SI、paging、RA 等相关工作进展。
- 研究 Cell DTX/DRX 与 UE DRX 或 UE preferences 的联合优化，涵盖配置和未配置 UE DRX 的 UE，并探索 flexible cell DTX 与 flexible UE C-DRX 的联合、简化设计。
- 研究 C-DRX 增强，包括多个 active DRX configurations、adaptive DRX operation，以及不同 DRX window types 与预配置 PHY-layer configurations 的关联。
- 研究 DL WUS 与类似 C-DRX 机制的协同、6G day-1 connected mode 中 LP-WUS 与 C-DRX 的解耦及不依赖 DRX 的 wake-up signal operation，并结合 RAN1 进展避免重复功能。
- 研究 IDLE mode 的 DL WUS（包括 paging 用途），以及作为所有 RRC states 候选节能技术的 LP-WUS/WUR；用于 paging reception 的 LP-WUS/WUR 仍为 day1 候选特性，以 5G NR design 为基线。
- 研究在 LR 上进一步放宽或卸载 RRM measurement，以及在 RRC_CONNECTED mode 使用 LR 进行 RRM/RLM/BFD measurements。

### 6GR 非地面网络（基于 8 条已摘要 6G 事件）

本会议明确了6G NTN可沿用的5G NTN部署场景与payload type假设，并推进了TN/NTN共同设计及NTN特定功能的研究范围。协议研究涉及接入、重传、移动性、同步与覆盖适配，并给出了mobility mechanisms的考虑优先级；具体机制及Day-1支持范围尚未定案。

**关键结论**

- 6G NTN可采用5G NTN的LEO、MEO、GSO部署场景和payload type假设。
- RAN2将研究与TN设计共同处理的功能和NTN特定功能，包括HARQ、mobility、initial access、uplink time and frequency pre-compensation、TA reporting、satellite switch with re-sync、beam hopping和discontinuous coverage。
- 6GR study中mobility mechanisms的考虑优先级依次为Time-based和Location-based CHO、RACH-less handover、MAC触发的cell switch mechanism（例如LTM），以及group handover。

**待决问题**

- 是否研究GNSS取决于RANP及其他工作组讨论；MBS、dual connection、Carrier Aggregation和VLEO可在RANP讨论。
- TN/NTN统一的grant-free initial access mechanism及支持network energy savings的control plane signaling仍待研究，讨论涉及高负载下是否采用RACH-less及network contention的需要。
- 根据service类型和operating point在user plane动态激活或停用retransmission mechanisms（例如HARQ）的方案仍待研究。
- Idle和Connected modes下的TN-to-NTN、NTN-to-TN及NTN-to-NTN mobility procedures仍待研究，后者涵盖inter-beam、inter-cell和inter-satellite mobility。
- NTN特性对initial access timers、HARQ、mobility management和paging等的影响仍待评估。
- common essential、NTN specific essential和NTN specific optional features的具体范围仍有不同意见，Day-1支持范围及后续release安排尚待明确。

### 6GR 共用协议其他议题（基于 16 条已摘要 6G 事件）

RAN2#132 围绕“flexible” protocols 和 system information（SI）安全保护推进了研究方向。前者研究在网络监督和有限控制范围内允许 UE 利用内部算法调整配置参数，并评估性能监测需求，不依赖 AI/ML model management framework；后者聚焦 mobility-related SI 的保护，同时要求考虑 PWS requirements 且不降低 PWS reachability。具体 SI 安全保护方式由 SA3 讨论决定，讨论支持等待 SA3 threat analysis 后再考虑技术方案。

**关键结论**

- 研究在 Control Plane 和 User Plane 层级启用“flexible” protocols，使 UE 能使用内部算法提升性能。
- 研究 UE 在网络监督下调整 RRC configured parameters，并在网络控制的有限范围内调整参数或配置，例如 RLC timer 和 LCH priority。
- 启动针对承载 mobility-related data 的 SI 的安全保护研究，以防御 false base stations 发起的攻击。
- SI 安全保护研究需考虑 TS 22.268 中的 PWS messages 要求，并保持 PWS 可达性；安全保护方式由 SA3 讨论决定。

**待决问题**

- UE 智能调整参数的具体机制、适用场景、收益及对 system performance 的影响仍需研究，后续可按具体 feature 提交提案。
- 支持 NW 监测 UE 性能的 KPIs、其他 metrics，以及是否需要 reporting 和 reporting 级别尚待研究。
- SI 面临的安全威胁及新增潜在风险仍需确认，具体技术方案有待 SA3 threat analysis 的后续进展。
- PWS 安全保护仍需解决跨运营商 base stations 的可达性问题，以及 UE 缺少对应 security key 时无法解码造成的可达性下降风险。
- SI 安全机制引入的 SIB Overhead，以及哪些 SI 需要或不需要保护，仍需评估。

### 6GR 数据与模型传输（基于 27 条已摘要 6G 事件）

RAN2#132 推进了 6GR 数据与模型传输的研究基线整理，以非实时数据类型为起点，拟在 TR 中记录数据特性、端点及 QoS 需求，支撑后续 unified data transfer study。会议指出现有 5G CP/UP 框架的局限，但尚未选定增强 CP、增强 UP 或新方案，具体协议仍待研究。模型方面明确了 training data collection 与 model transfer/delivery 的边界及相关职责，并同意以 5G UE-sided model 的 LCM procedure 作为 6G 研究起点。

**关键结论**

- 5G CP 数据传输框架不适合大数据量，并可能影响 essential CP signaling；现有 UP 框架存在不必要地经过 UPF、gNB 难以参与管理及终止于非 3GPP 控制的 application layers 等局限。
- RAN2 将在 TR 中记录各用例的 data type、endpoint pairs、data size、transmission interval 和 QoS requirement，作为 unified data transfer study 的 baseline。
- 对于 two-sided model，NW 到 UE-side OTT server 的 dataset/model parameter transfer 属于 AI/ML training data collection；经训练的 UE-part model 从该 server 下载到 UE 用于 inference 才属于 model transfer/delivery。
- UE-side/UE-part two-sided model transfer/delivery 对 3GPP 透明，可采用 non-3GPP 方案或经 UP 透明传输，无需定义相关要求；NW-side model 的标准化传输支持属于 RAN3/SA2/SA5 职责，并应对 UE 透明。
- 6GR AI/ML use cases 将逐案研究，优先评估无传统替代方案或能显著提升系统性能的用例；评估应以一致指标对照 non-AI/ML baselines 量化复杂度和能耗。
- 同意以 5G UE-sided model 的 LCM procedure 为起点，涵盖能力查询与指示、inference configuration、functionality applicability 判断与报告，以及功能激活或去激活。

**待决问题**

- 数据收集和传输的具体范围、消费者、termination points、是否需要 RAN 解码及 QoS 特性仍需细化，部分 QoS 细节依赖其他 WGs。
- Sensing data 的 metrics、size 和 reporting frequency 等待 RAN1 对 measurement metrics 的进一步输入。
- 尚需选择增强 CP、增强 UP 或新方案，并比较面向 CN/AF 与 RAN 消费数据的协议选项，包括前向兼容性、QoS/priority 区分能力、空口协议复用及规范工作量。
- AI/ML 用例的性能增益、benchmark、输入/输出和复杂度评估需进一步补充；normalized FLOPs、space complexity 和 derived energy consumption profiles 等指标集合仅被注意到，尚未形成确定选择。
- 适用于不同 6G AI/ML use cases 的统一 LCM procedure 仍待研究；two-sided model 的 Day1 LCM 影响尚未讨论，详细讨论需等待 R20 AI-PHY WI 取得充分进展。

### 6GR 通用设计与新业务（基于 32 条已摘要 6G 事件）

本会议明确了 6GR 对 mobile broadband 的高优先级，以及在 6G standalone architecture 中支持 Voice 的要求，并确定 eMBB（包括 immersive communication）、Voice、ISAC 和 IoT 的需求需从 Day 1 得到满足和支持。通用协议设计讨论围绕 common minimum functionality、设备能力表达和 scalable design 展开，相关参数及协议影响仍需依据 RAN plenary 的决定推进。移动 AI 流量特征已纳入研究，但 tokenized traffic 是否纳入 RAN2 研究及其具体规范影响尚未确定。

**关键结论**

- 6G radio protocol 应高优先级满足 mobile broadband services 的需求；Voice 必须在 6G standalone architecture 中得到支持。
- eMBB（包括 immersive communication）、Voice、ISAC 和 IoT 的需求需从 Day 1 满足；IoT、sensing 和 AI applications 等其他服务的 Day 1 支持需有明确的 market needs 和 use cases 作为依据。
- 以从 Day 1 满足 emergency calls、与 emergency call 相关的 positioning（如 ECID）及 PWS 的 regulatory requirements 为假设。
- 移动 AI 流量特征纳入研究；tokenized AI 的 token arrival rate/interval 依赖 source file 的 traffic pattern，且不同 tokens 可具有不同的 transmission reliability requirement，并非所有 tokens 都必须正确传输。

**待决问题**

- Voice fallback 先交由 plenary 讨论。
- 是否研究 tokenized AI traffic 尚未确定；对等待 SA4 结论还是与非 tokenized AI traffic 一并研究存在分歧，下次会议将了解 RAN2 specific requirement 及需向 SA4 提出的具体问题。
- 6G RAN computing resources deployment 的三种选项需进一步研究，相关讨论包括计算资源部署于 RAN 和 CN 的情形。
- common minimum functional capability、相关参数及影响 device design envelope 的因素待 RAN plenary 决定；设备能力表达和 scalable design 的后续讨论需以全会指导及共识为依据。
- Digital twin 的 traffic model 和潜在 specification impacts 被提出供进一步研究；6G vertical services 的 protocol flexibility、suitability 和 simplification 条目标记为 Not treated。
- device types 与具体 requirements、features 及后续 signalling 设计之间的研究顺序仍有不同意见；UE based sensing modes 的 signalling 设计被提出待 RAN1 initial design 稳定后推进。

### 6GR MAC 与调度（基于 30 条已摘要 6G 事件）

RAN2#132 明确了 6GR MAC 与调度的研究方向，重点是降低 scheduling 时延并提升 UL resource efficiency，基线支持 DL SPS，UL 继续研究 CG like mechanisms。会议明确研究至少包含 buffer status reporting 和 delay status reporting 的 scheduling information 机制，并在详细功能取得进展后争取统一 framework。L2 recovery 支持 sequence number-based ARQ，并研究利用 HARQ process status 加快重传；CB UL、CG、报告机制及 LCP 的具体增强设计仍需后续讨论。

**关键结论**

- Scheduling 增强研究包括 contention-based schemes；CB UL 至少以现有 normal SR/BSR functionality 为比较基线。
- 为支持 voice 等周期性业务，基线支持 DL SPS；UL 继续研究 CG like mechanisms，以适配 voice、bursty traffic 和其他周期性业务。
- Scheduling information 机制的研究至少覆盖 buffer status reporting 和 delay status reporting，目标是在可能时统一 framework。
- ARQ 支持 sequence number-based L2 recovery，并支持基于 STATUS reporting 的 ARQ retransmission；ARQ 保留独立于 HARQ、实现最高 100% reliability 的要求。
- 研究基于 HARQ process status、由 transmitter side 更快触发 ARQ retransmissions 的机制，先从 UL 开始，也可考虑 DL；gNB 提供显式 UL HARQ process status 被认为有益。
- Contention-based UL transmissions 不应成为发送 SR/BSR 的唯一选项，其时延可能受 transmission occasions 周期性和 contention levels 等因素影响。

**待决问题**

- CB UL 的进一步研究假设及具体方案仍待讨论，需评估相对现有机制的收益和碰撞概率，并明确 UE ID、DMRS 专用或共享以及是否仅用于 BSR 等问题。
- UL CG like mechanisms 的资源配置与调整方式、对 bursty traffic 的适配，以及是否统一 Type 1/2 CG、采用何种基线仍待研究。
- 是否需要其他 scheduling information，以及 BSR/DSR 统一的范围、报告内容、触发条件和格式仍待确定。
- 显式 UL HARQ process status 的具体细节，以及利用 HARQ status、feedback 或 network indications 加快 ARQ/RLC 重传的机制仍待研究。
- LCP 增强设计仍需研究，包括动态调整参数，以及如何考虑 delay、importance 和 inter-QoS flow/packet correlation 等 traffic characteristics。

### 6GR 移动性（基于 25 条已摘要 6G 事件）

RAN2#132 明确以 NR cell (re)selection framework 作为 6G 小区重选框架基线，并确定 5G/6G inter-RAT mobility 的起步支持范围。会议明确了 mobility schemes 的研究范围，推进统一测量与 measurement gap signaling framework 的研究，旨在减少移动性流程及测量配置、上报的复杂性。统一 handover 的具体信令与流程及 inter-RAT 增强尚未定案，仍需后续研究和跨工作组协调。

**关键结论**

- 6G cell reselection framework 以 NR cell (re)selection framework 为基线，包括 best cell principle、cell ranking 和 inter-freq/RAT prioritization。
- 5G/6G inter-RAT mobility 起步支持 RRC_CONNECTED 下的 handover 和 re-direction，并可向 UE 提供 inter-RAT cell reselection information。
- 已同意研究无预配置的网络触发流程、预配置方案及 UE 触发流程，以及 CFRA、RACH-less、early UL/DL sync 和 early CSI；该 study item 不考虑 NR DAPS。
- Mobility 方案研究需先分析 5G 的不足及其对 6G 需求的适应性，并考虑中断、鲁棒性、吞吐量下降、UE/NW 复杂度和资源效率。
- RAN2 将研究统一测量，包括 L1/L3 measurement 的 common RS configuration，并与 RAN4 协调 beam/cell level 及 L1/L3 measurement 的统一。
- Measurement gap signaling framework 的设计目标是支持 UE 根据当前 configuration 和 status 动态请求 measurement gap。

**待决问题**

- 统一 L3 HO 与 LTM 的具体方案仍待讨论，包括共同流程的整合范围、统一信令类型及是否保留 L3 与较低层信令。
- 统一 measurement configuration 和 reporting 的具体机制仍需研究，并需与 RAN1、RAN4 协调。
- Measurement gap 的 procedure 和 signaling 设计，以及 periodicity、length、pattern 和相应 requirements，仍需推进并与 RAN4 协调。
- 6G 特性对 cell selection/reselection 的影响仍待研究，后续讨论依赖其他 WGs 在 cells、reference signals 和 measurement framework/requirements 上的进展。
- Inter-RAT mobility 的进一步增强需待 intra-RAT 方案讨论后评估，并考虑 MRSS；IRAT RACH-less、early DL/UL synchronization 和 early CSI acquisition 的可行性及复杂度仍存在不同意见。

### 6GR QoS/QoE 与服务感知（基于 41 条已摘要 6G 事件）

本会议明确了 6GR application/service awareness 的初期研究方向：识别目标 6G use cases 共有的 traffic characteristics/requirements，并探索通过尽可能通用的框架向 RAN 和 UE 提供这些信息。协议层面将进一步讨论 service characteristics 和 information 对 UL/DL L2 protocols 的影响；围绕 QoS flow 内差异化处理、multi-modal 传输协调及 dynamic QoS adaptation 的具体机制仍处于提议和研究阶段。

**关键结论**

- 初期 application/service awareness 研究聚焦目标 6G use cases 共有的 traffic characteristics/requirements，探索通用信息提供框架，必要时与 SA2 协调。
- 会议观察指出，调度和资源管理更关注流量属性及 QoS requirements，而非产生流量的应用类型；动态流量特征感知有助于提高资源分配和调度效率。
- XR、mobile AI 等目标应用存在分组依赖关系和重要性差异；GenAI service flow 的特征与需求可能在不同 bursts 之间及随时间显著变化。
- 会议指出，单一 radio bearer 承载 UE 所有服务会造成接收端跨服务的 head-of-line blocking。
- 会议指出，UE 在许多场景下可获取大量 QoE 信息以跟踪应用状态，并可调整部分 L2 protocol parameters，对 NW operation 影响很小或没有影响。

**待决问题**

- 通用 awareness 框架应提供哪些信息、如何从 UE 收集和向 RAN/UE 提供，以及这些信息如何影响 UL/DL L2 protocols，仍待研究。
- QoS framework 是否及如何扩展尚待明确：材料同时指出尚无开发新框架的具体紧迫需求，以及现有模型缺少 per-packet/per-packet-group granularity 和 RAN 内动态 packet treatment 映射能力。
- QoS flow 内 packet priority、sub-flow 差异化处理及其 DRB/logical channel 映射，以及 per-packet retransmission、lossless/lossy transmission 的具体机制仍待研究。
- Multi-modal communication 的 intra-UE/inter-UE 多流协调、packet-level inter-QoS flow dependency 和 haptic traffic 高效传输仍待处理。
- RAN-level dynamic QoS adaptation、QoS burst profile、预配置 QoS profiles 切换及 UE/RAN transmission configurations 快速适配仍待研究，包括对 LCP 和 retransmission 的影响。
- Mobile AI 的 token-based/non-token-based 流量特征、immersive communications 的 E2E latency requirement、per QoS flow 性能测量，以及 AI tokenizer approach 的传输效率、失真和实现复杂性仍需评估。

### 6GR 初始接入与系统信息（基于 25 条已摘要 6G 事件）

RAN2#132 推进了 6GR 初始接入与系统信息的研究框架，以假设支持 on-demand SI 和 area specific SI 为方向，继续研究 SIB1 的内容、按需获取、结构及调度，具体机制尚未定案。会议明确了 CA、BWP 及 cell access control 的设计基线，并同意研究 IDLE/INACTIVE（如支持）状态下的 multicarrier operation，为后续确定跨载波接入、SI 获取及接入控制的协议机制提供依据。

**关键结论**

- 记录的 SI 协议方向是假设支持 on-demand SI 和 area specific SI；on-demand SIB1、可共用的信息及 area specific SIB1 仍需研究。
- SIB1 splitting 应先明确 SIB1 的设计、内容和大小，再基于 on-demand provisioning，结合合理的 PBCH load 限制、收益、UE 与网络影响及 access latency 重新评估。
- 同意研究 IDLE/INACTIVE（如支持）状态下用于 paging、system information 和/或 random access 的 multicarrier operation 需求，并与 RAN1/RAN4 协调。
- CA 被作为跨频段连续频率资源聚合的基线，各频段的连续资源分别作为一个 cell；BWP 被作为至少适用于一个 cell 内连续频率资源的基线，二者均继续研究改进。
- 5G 的 UAC、Cell status、cell reservations 和基于 MSG3 cause 的 RRC Reject 被作为 6G cell access control 的设计基线。

**待决问题**

- on-demand SIB1 的 UE request mechanism 及新到达小区 UE 获取 uplink configuration 的方式尚待确定，候选包括固定配置、PHY/MIB 中的 indexed configuration，以及 MIB/其他 SI 显式配置。
- 哪些 SI 内容可跨小区共用、是否采用 area specific SIB1，以及如何简化 identical SI identification 和 update synchronization，仍待研究。
- SIB1 的具体内容、sub-RMSI 拆分或模块化构造尚未确定，需评估节能、复杂度及 latency cost。
- 更灵活的 SI scheduling、与其他 common signalling 的传输聚类或捆绑，以及提高 SI change notification granularity，仍待研究。
- multi-cell/carrier coordinated initial and system access 的具体流程、assisting 频谱资源及碎片化频谱的 cell/carrier 建模、多个频谱片段的聚合用法仍待讨论。
- 更细粒度的 access control 增强需与 SA1/CT1 协调；考虑 service type、device type 和 NW/UE capability 的统一机制仍属提案。

### 6GR UE 能力框架（基于 47 条已摘要 6G 事件）

本会议梳理了6GR UE能力框架的信令开销、动态能力变化及UE与网络功能支持一致性问题，明确初期优先识别NR UE capabilities的痛点，待6G feature studies充分进展后再讨论增强。报告框架保留基于网络请求的基本流程，并支持显式UE Capability report及基于UE Capability ID的报告；细粒度筛选、信息复用和增量报告仍属研究方向。动态更新讨论推进到用例、处理时限及过渡期配置同步要求，同时保留“mandatory with capability signalling”类型，相关增强方案尚未收敛。

**关键结论**

- Band和BCs是能力信令增长的关键因素，CA/DC的Band combination capability information占能力信息大小的主要部分；现有RAT/band/cell-group filtering粒度过粗。
- FS、FSPC和FSC可高效表示band/BC dependent capabilities，但无法覆盖5G全部baseband dependent capabilities；BC内的optional capabilities也是开销来源。
- 保留基于网络请求的基本UE capability reporting procedure，并支持显式报告和基于UE Capability ID的报告。
- 当前阶段优先识别NR UE capabilities中观察到的问题，待6G feature studies取得足够进展后再讨论capability enhancements。
- 动态UE capability update从NR UAI及RRCReconfigurationComplete (NeedForGap)已支持的用例开始；预期网络在定义时限内处理请求，以保持transition period期间的配置同步，框架聚焦RAN capability且不影响NAS capability。
- 6G保留“mandatory with capability signalling”这一feature类型，以应对跨地区和PLMN的潜在IODT问题。

**待决问题**

- 需进一步识别overhead/complexity的主要来源，划清RAN2与其他工作组职责；向RAN1/RAN4发送LS、协调CA/band/BC structures时间安排及总体结构仍待后续讨论。
- 更细粒度及Per-BC filtering、RACS优化与模板、index-based linkage、delta reporting和网络预设条件下的UE发起BC报告仍待研究，包括跨报告复用feature set IDs的机制。
- 需统一“dynamic UE Capabilities changes”的含义，识别重要用例及理由、分析UAI痛点，并判断RRC configuration handling或lower layers能否满足需求。
- 动态更新的生效时间、是否永久、configuration handling及网络未在规定时限内更新配置时的UE行为仍待明确。
- 减少optional capabilities、定义basic feature groups，以及建立具约束力的功能部署跟踪程序仍待讨论，包括组的判定标准、binding含义和工作组职责。
- UE与网络mandatory feature支持一致性及IODT处理方案尚未收敛；厂商ID与mobility处理、能力与网络需求不一致仍待解决，基于UE model/software version控制功能的条目仅记录为Noted且Not treated。

### 6GR 用户面架构（基于 36 条已摘要 6G 事件）

RAN2#132围绕6GR用户面架构梳理了基本功能需求，并讨论减少重复功能、降低L2开销及改善硬件处理效率的方向。会议识别了sequence numbering、packet concatenation、header和MAC PDU格式等设计的收益与约束，但尚未形成完整的协议栈及层间功能划分方案。packet concatenation留待UP协议和安全理解进一步完善后再讨论，QoS remapping及随机接入资源效率等问题也需继续研究。

**关键结论**

- 大多数NR UP functions被认为是连接L2以上upper layers与physical layer所必需的，同时现有协议栈存在多组重复功能。
- 共用SN服务于ARQ与(re-)segmentation，以及security与re-ordering，有利于降低L2 overhead并提升效率；具体joint sequence numbering设计尚待研究。
- 逐PDCP SDU生成MAC-I会增加开销并占用UE processing capability；data concatenation则可能引入不固定的header bit positions及额外分段、重组时延。
- NR中MAC和RLC的可变header length不利于硬件处理；通过一律使用更长header统一长度会增大Message 3等coverage bottleneck消息，应避免这一做法。
- 单个CB失败可能延迟其他CB中PDU的交付；在TB中提供MAC CE或MAC subPDU metadata可帮助接收端加快处理。
- NR的RACH partitioning存在资源利用低效问题，且RACH resources难以适应接入负载的短期变化。

**待决问题**

- 6GR UP基本功能的具体支持方式、层间划分及可禁用性仍需明确；Header compression按plenary要求暂缓，data compression的适用范围仍有讨论。
- packet concatenation的目标场景、QoS与优先级隔离、硬件适配及安全处理仍待评估，待UP协议和安全理解进一步完善后再讨论。
- joint sequence numbering及跨PDCP/RLC统一SN的可行设计仍需研究，并需结合层间关系及PDCP与RLC是否合并考虑。
- 新的MAC PDU格式、独立CB、metadata、结构化MAC CEs及减少header length动态变化的具体方案仍待研究。
- 统一Random Access procedure、减少RACH partitions及动态或按需分配RACH resources的方案仍待研究，RA PUSCH payload size问题需与RAN1共同评估。
- Reflective QoS是否保留、采用UP control signalling实现QoS flow到DRB remapping，以及L4S区分、反馈优先传输和L2 buffer AQM等提案仍待后续处理。

### 6GR RRC（基于 62 条已摘要 6G 事件）

RAN2#132 推进了 6GR RRC 连接管理、状态建模及配置机制研究，明确当前设计采用 single RRC sublayer，并研究 inactive mode 或 sub-state 对快速进入 data exchange 和 network controlled transitions 的支持。配置方面，会议认可 delta configuration 降低信令开销的价值，同时推进实现复杂度、兼容性及部分配置无法应用问题的处理。协议设计方向包括配置存储与复用、减少不必要的 re-establishment，并保持 UE 与 NW 配置同步；具体状态模型和相关机制仍需后续研究。

**关键结论**

- 6G RRC 采用 single sublayer（no upper/lower split）；RRC layer split 讨论推迟至 RAN3 或 RAN 就 CU-DU split 作出决定。
- 连接管理研究覆盖 establishment、reconfiguration、re-establishment 和 release，并包括 UE 发起的 RRC connection release。
- Delta configuration 仍被认为有助于降低 signalling overhead，需解决其实现复杂度、兼容性及参数约束处理问题。
- 跨状态转换存储并复用 RRC configurations 可降低信令开销和功耗，并加快状态转换。
- 6G 设计将允许 UE 保留或应用可用的配置部分，以尽量减少 re-establishment procedures；UE 与 NW 的配置同步是重要要求。

**待决问题**

- 确定采用三态模型，还是两个顶层状态加 sub-states，以及 inactive 应作为独立 RRC state 还是 connected sub-state。
- 明确 inactive 或 Energy Efficient Sub-state 的功能、转换时延目标，以及 UE based mobility、WUS、SDT 和 RACH-less 等候选机制。
- 研究 single paging mechanism、统一 location tracking 和 RNA 管理，以及 UE AS context 的存储与获取方案；context 存储位置需与 RAN3/SA2 协同研究。
- 明确 RRC configuration 与 ASN.1 modularization 要解决的问题、模块划分规则及层级，并细化已存储配置和 reference configurations 的复用与激活机制。
- 研究 delta configuration 的改进方式，包括 Need codes 处理与 configuration guidelines 分离，以及初始配置和后续重配置使用不同 ASN.1 IE 的方案。
- 评估 UE 无法遵从配置导致的失败概率，确定是否需要 partial success/failure mechanism，并解决部分配置保留或应用时的 UE/NW 同步问题。

- **proposal** 10.3.3.2 — UE DRX 被采纳为 6G 的关键特性，以支持 UE 和 network nodes 的 energy and power saving。记录的意见包括保留 C-DRX、研究 WUS，以及避免 L1 和 L2 中出现多个或重复的方案。

- **proposal** 10.3.3.2 — 对于 6GR，允许由 WUS 触发特定的 “OnDuration” window configurations，以通过适当的 PHY setting 实现节能的 receiver reactivation。
- **proposal** 10.3.3.2 — RAN2 将研究 IDLE mode 的 DL WUS，包括用于 paging 的 DL WUS。
- **proposal** 10.3.3.2 — RAN2 将研究 LP-WUS/WUR，作为 6GR 所有 RRC states 的候选 UE power saving techniques，其中包括将用于 paging reception 的 LP-WUS/WUR 作为 day1 候选特性，并以 5G NR design 为基线。还将研究在 LR 上进一步放宽或卸载 RRM measurement，以及在 RRC_CONNECTED mode 使用 LR 进行 RRM/RLM/BFD measurements。

- **proposal** 10.2.2 — 讨论了 6G NTN 的基本假设和功能分类，包括 common essential features、NTN specific essential features 与 NTN specific optional features。建议 common essential features 从 Day 1 起采用 TN 和 NTN 的 harmonized design，NTN specific essential features 可讨论是否从 Day 1 支持，NTN specific optional features 可留待后续 release；具体功能范围仍有不同意见。

- **proposal** 10.3.3.1 — 提出适用于 AI/ML、sensing、SON/MDT 和 QoE 应用及 UE-side、NW-side 数据收集的 baseline requirements，包括保障数据安全、完整性和机密性，尊重用户隐私、匿名性及同意，并由 MNO 完全控制和查看 standardized data 的传输过程。设计还应可扩展，并尽量减少 UE 数据收集对电池、处理、内存、用户流量传输和省电功能的影响。
- **proposal** 10.3.3.1 — 目标是形成适用于多种 6G 数据类型（例如 AI/ML、sensing）的通用框架。
- **proposal** 10.3.3.1 — RAN2 应研究数据传输采用哪种方案：增强 control plane、增强 user plane，或新方案（例如 new data plane、new entity/protocol layer、new RB）。传输协议的研究视时间允许而定。
- **proposal** 10.3.3.1 — RAN2 将研究 UE 生成、由 CN/AF 消费的数据传输协议选项（Over NAS 或 Over IP/non-IP and UP-L2），以及 UE 生成、由 RAN 消费的数据传输协议选项（Reuse RRC、Over RRC、Over CP-L2、Over UP-L2、Over IP and UP-L2、Over non-IP and UP-L2）。对于 RAN 生成、由 CN/OAM/AF 消费的数据，传输层协议没有 RAN2 影响；协议选项将依据前向兼容性、QoS/priority 区分能力、空口协议复用和规范工作量等方面分析优缺点。
- **proposal** 10.3.3.1 — AI model transfer 需考虑模型参数传输的多种大小（具体模型大小待定）、UE mobility 期间的服务连续性，以及由 NW 决定是否及何时通过空口传输。其 latency 要求宽松，更新不频繁。
- **proposal** 10.3.3.1 — AI model transfer/delivery 研究应考虑将其流量设为不同于用户流量的优先级，并与其他用户流量区分。还应考虑安全、NW-aware 的传输保障，以及模型可寻址性，以便 UE 请求特定模型和/或版本。
- **proposal** 10.3.3.1 — 对于 two-sided model，从 NW 到 UE-side OTT server 的 dataset/model parameter transfer 被视为 AI/ML training data collection，而非 model transfer/delivery。该模型的 transfer/delivery 指从 UE-side OTT server 下载经训练的 UE-part two-sided model 到 UE，用于 model inference。
- **proposal** 10.3.3.1 — NW-side model 是否以及如何支持标准化的 model transfer/delivery（例如 CN -> RAN、OAM -> RAN），属于 RAN3/SA2/SA5 的职责范围。NW-side model transfer/delivery 应对 UE 透明。
- **proposal** 10.3.3.1 — 6G 中 UE-side/UE-part two-sided model transfer/delivery（例如模型传输、内容、版本）对 3GPP 透明，可通过 non-3GPP 方案或经 UP 透明传输，因此无需定义相关要求。原文讨论记录对模型大小、WiFi、可控性和安全等问题存在不同看法。
- **proposal** 10.3.3.1 — RAN2 将逐案研究 6GR AI/ML use cases；提案方需提供用例描述及动机/依据、性能增益及其评估方法，以及包括各 LCM 组件评估在内的规范影响。讨论中还提出明确评估基准、单侧或双侧模型，以及各用例的输入和输出。
- **proposal** 10.3.3.1 — 优先评估不存在传统替代方案，或 AI/ML 能显著提升系统性能的用例。
- **proposal** 10.3.3.1 — 已注意到为 AI/ML 评估建立复杂度指标集合的建议，包括 normalized FLOPs、space complexity 和 derived energy consumption profiles。下次会议提交 use case 时可考虑提供用例描述、性能增益及评估方法、复杂度评估、benchmark 和输入/输出；LCM aspects 未讨论。
- **proposal** 10.3.3.1 — RAN2 将研究适用于 6G AI/ML 不同 use cases 的统一 LCM procedure。
- **proposal** 10.3.3.1 — 同意将 5G 中面向 UE-sided model 的 LCM procedure 作为起点。该流程包括网络查询能力、UE 指示能力、网络指示 inference configuration、UE 判断并报告 functionality applicability，以及网络/UE 功能激活或去激活。
- **proposal** 10.3.3.1 — RAN2 将研究 6G Day1 中 two-sided model 的 LCM 影响；待 R20 AI-PHY WI 取得充分进展后再开始详细讨论。该议题未讨论。

## 6GR 通用设计与新业务（32 条）

- **agreement** 10.2.3 — 确定 eMBB（包括 immersive communication）、Voice、ISAC 和 IoT 的需求需从 Day 1 得到满足和支持；Voice fallback 先在 plenary 讨论。假设 emergency calls、与 emergency call 相关的 positioning（如 ECID）及 PWS 的 regulatory requirements 从 Day 1 满足，并将移动 AI 流量特征列入研究，是否研究 tokenized traffic 尚未确定。
- **observation** 10.2.3 — 确定 6G radio protocol 应将满足 mobile broadband services 的需求作为高优先级。
- **observation** 10.2.3 — 确定 Voice service 必须在 6G standalone architecture 中得到支持。IoT、sensing 和 AI applications 等其他服务从 Day 1 获得支持，需有明确的 market needs 和 use cases 作为依据。
- **observation** 10.2.3 — 预计 token consumption 将快速增长。
- **observation** 10.2.3 — 6G study phase 中，RAN1、SA1 和 SA2 正在研究 tokenized AI 的 traffic characteristics，以及各工作组可能受到的 standard impacts。
- **observation** 10.2.3 — Tokenized AI 被认为是 NTN network 的一项有前景的服务，其原因是 transmission bit rate 较低，并且对 voice 和 video 的 packet loss 具有 resilience。
- **observation** 10.2.3 — Tokenized AI 的 traffic pattern 中，一个 source file（如 video frame、picture 或 text）可用于生成多个 tokens。用于 tokenization 的 source files 至少包括 non-real-time 和 real-time audio/video、picture 与 text，token 的 arrival rate/interval 等 traffic pattern 依赖 source file 的 traffic pattern。
- **observation** 10.2.3 — Tokenized AI 的 transmission requirements 包括 error-tolerance，即无需所有 tokens 都正确传输；不同 tokens 具有不同的 transmission reliability requirement，例如 token error rate。
- **observation** 10.2.3 — 提出 6G RAN computing resources deployment 有三种不同选项，并应进一步研究。
- **proposal** 10.2.3 — 6GR 应从 Day-1 优先支持 mobile broadband 和 voice services，同时采用共同设计以支持广泛服务，避免要求单独解决方案。讨论中，Samsung 将“优先”解释为其他服务不影响 eMBB 性能。
- **proposal** 10.2.3 — 6GR 应满足 emergency voice calls、positioning 和 PWS 的所有 regulatory requirements。Nokia 提出至少支持 ECID 和 emergency broadcasts，且要求应来自 A1。
- **proposal** 10.2.3 — 应向 6GR 提供 FWA devices 的特定特征（例如较大的 RF components、external power supply），并在设计中加以考虑，以优化对 FWA services 的支持。
- **proposal** 10.2.3 — RAN WGs 应等待 SA4 完成 Media Aspects for 6G Systems 研究后，再启动与 AI traffic 相关的讨论，其中包括但不限于 tokenization。
- **proposal** 10.2.3 — RAN2 应研究对 ISAC、AI/ML-based services、token communication 和 immersive communication 等新服务的支持，并考虑 NW 与 UE energy consumption 以及 User experience (QoS/QoE) improvement。
- **proposal** 10.2.3 — 关于 tokenized AI traffic 的研究存在不同意见：有观点主张等待 SA4 的结论，也有观点主张与非 tokenized AI traffic 一并研究。下次会议将了解是否存在 RAN2 specific requirement 及需向 SA4 提出的具体问题。
- **proposal** 10.2.3 — RAN2 研究 AI 和 sensing services 支持时，应考虑不同的 computing resources deployment options，包括部署在 RAN 和 CN 的情形。
- **proposal** 10.2.3 — RAN2 应进一步研究 Digital twin service，例如其 traffic model 和潜在的 specification impacts。
- **proposal** 10.2.3 — RAN2 需要进一步研究如何支持 6G vertical services，至少涵盖 protocol flexibility、suitability 和 simplification。该条目标记为 Not treated。
- **proposal** 10.2.3 — 6GR 的 RAN2 研究应覆盖所列 use cases，包括 NTN、HRLLC、SON/MDT、Slicing、Relays（包括 repeaters 和 RIS）、UAV、HST、AI/ML 及 Sensing scenarios。
- **proposal** 10.2.3 — 对 5G 现有用例，RAN2 study 应尽早识别可复用的 5G functionality 作为 baseline，以尽量减少这些领域的额外工作。示例包括 SON/MDT、TSN 和 Slicing，具体取决于 SA2 output。
- **proposal** 10.2.3 — 针对 AI 和 sensing 的新及增强 6G 用例，RAN2 study 应支持 AI based enhancements，同时确保有无这些增强时系统均能 optimal operation。待 RAN1 initial design 稳定后，应设计 signalling，以支持 UE based sensing modes 用于 sensing services 和 sensing assisted communication。
- **proposal** 10.2.3 — RAN2 6G system design 应以 RedCap 和 eMBB requirements 为 baseline，包括 peak data rate（10Mbps-Gbps）、battery life（few years）、coverage 和 low cost。
- **proposal** 10.2.3 — 新旧 services 的 requirements 只应在 RANP 讨论；RAN2 应聚焦 RANP 已同意的 services，包括 Mobile broadband、Immersive Communication、Massive Communication (IoT)、Sensing、AI、Voice 和 Regulatory services。Digital twin、Non-Terrestrial Network、Aerial、FWA、Vehicles、Mission Critical Communication、Positioning and/or Navigation、TSN、HRLLC 等新 services 的 requirements 应在 RANP 讨论。
- **proposal** 10.2.3 — 对于 network AI data collection、sensing、mobility、paging、UP、capability 等 E2E architecture 相关 features，RAN2 study 以 UE->RAN->CN 的 general architecture 为 baseline。无需重复讨论其他 WGs 涉及的 RAN/CN architecture，例如 CU/DU split、P2P、SBI 和 new core。
- **proposal** 10.2.3 — RAN2 仅在 RAN 和 RAN1 定义 device types 后，才开始讨论各类型的具体 requirements 和 features；UE capability signalling、RRC signaling modular design 和 system information design 则待 RAN2 与其他 WG 完成各类型的 requirements 和 features 后再处理。原文同时记录 Xiaomi 认为许多相关议题与 device types 无关，并质疑为何要等待。
- **proposal** 10.2.3 — 对 idle-mode features 的 forward-compatible design 应予以特别考虑，例如 system information scheduling/transmission 和 cell barring。
- **proposal** 10.2.3 — RAN2 6GR design 假设所有 6GR devices 都支持一组 common minimum functionality，使其能从任何 6G network 获得 basic connectivity。
- **proposal** 10.2.3 — RAN2 将遵循全会关于 common minimum functional capability 及相关参数和影响 device design envelope 的因素的决定。Scalability、extensibility 和 future-proofness 将以该 common minimum 为下限。
- **proposal** 10.2.3 — 只有在明确需要时，才应在 connection time 引入 device differentiation，并将其对规范的影响降至最低。
- **proposal** 10.2.3 — 从 RAN2 角度看，UE capability signalling 中捕获假设的“device type”概念的替代方式不受限制。推进这一方面的讨论前，等待 RAN plenary guidance。
- **proposal** 10.2.3 — 6G 采用统一的 capability framework，不随潜在的“device type”概念而变化。该条目标记为 Noted。
- **proposal** 10.2.3 — RAN2 角度提出研究适用于单一网络中所有设备类型的 scalable design，考虑降低对 eMBB devices 的性能影响、原生支持通用功能以及减少通用配置的 signalling overhead。后续会议等待 RANP 推进，并以 RANP agreements 为基线聚焦 RAN2 impacts。

## 6GR MAC 与调度（30 条）

- **agreement** 10.3.1.3 — RAN2 将研究提升 scheduling（包括 contention based schemes）时延和 UL resource efficiency 的方案。CB UL 研究以至少现有 normal SR/BSR functionality 为比较基线，并可说明方案与 5G 机制的异同；进一步假设取决于已识别方案，仍待讨论。
- **agreement** 10.3.1.3 — 为支持 voice 等周期性业务，基线支持 DL SPS。UL 继续研究 CG like mechanisms，以适配 voice、bursty traffic 和其他周期性业务。
- **agreement** 10.3.1.3 — 研究提供 scheduling information 的机制，至少包括 buffer status reporting 和 delay status reporting；是否需要其他信息取决于 traffic/services，仍待确定。详细功能取得进展后，目标是在可能时统一 framework。
- **observation** 10.3.1.3 — 依赖 HARQ coordination 可能加快 RLC recovery loop。RLC Sequence Number-window based mechanism 可保证最终纠正所有 HARQ errors，且使 NW 能在 latency、spectral efficiency、power、overhead 和 processing 等 design KPIs 之间权衡。
- **observation** 10.3.1.3 — 如果 UE 获得 UL transmissions 的 HARQ feedback，UL data 就可以可靠传输。
- **observation** 10.3.1.3 — 在 NR 中，发送 BSR/DSR MAC CE 前需通过 SR 或 RACH 经历多个步骤和信令交互以获取 UL grant。这会增加 UL transmission latency。
- **observation** 10.3.1.3 — Contention-based UL transmissions 不应成为发送 SR/BSR 的唯一选项，因为其时延不确定，并可能取决于 transmission occasions 的周期性、contention levels 等因素。
- **observation** 10.3.1.3 — BSR 和 DSR 存在重复，导致 signalling overhead，甚至造成 inefficiency。
- **observation** 10.3.1.3 — application context awareness 和 adaptive QoS 等新的 6G use cases 要求 LCP 比 NR 更具适应性。
- **observation** 10.3.1.3 — legacy LCP procedure 会导致 LCH starvation、resource inefficiency，以及处理动态 traffic requirements 时缺乏灵活性，尤其影响 delay-sensitive applications。
- **proposal** 10.3.1.3 — Sequence number-based L2 recovery mechanism 是 ARQ 的基线；ARQ 保留独立于 HARQ、实现最高 100% reliability 的要求。讨论指出，即使禁用 HARQ，ARQ 仍可启动。
- **proposal** 10.3.1.3 — 支持基于 STATUS reporting 的 ARQ retransmission。
- **proposal** 10.3.1.3 — RAN2 将研究由 HARQ status 和 feedback 在 transmitter side 本地触发 ARQ retransmissions 的机制。
- **proposal** 10.3.1.3 — RAN2 将研究基于 HARQ status 或 feedback 触发更快 RLC retransmission 的机制，包括 transmitter side 本地触发 ARQ retransmissions，以及由 network indications 显式启动本地 NACK procedures。
- **proposal** 10.3.1.3 — 建议 RAN2 研究 UL fast ARQ mechanism，由 lower layer signalling（例如 DCI）触发，使 upper layers 能立即进行类似 ARQ 的 retransmission。并建议通知 RAN1 支持 DCI signalling。
- **proposal** 10.3.1.3 — UE 获得显式 HARQ feedback，以指示 UL transmissions 的 decoding result。
- **proposal** 10.3.1.3 — 一致认为 ARQ 支持 sequence number-based L2 recovery，并研究基于 HARQ process status、由 transmitter side 更快触发 ARQ retransmissions 的机制，先从 UL 开始，也可考虑 DL。RAN2 认为 gNB 提供显式 UL HARQ process status 有益，其具体细节待进一步研究。
- **proposal** 10.3.1.3 — 为降低 UL latency，RAN2 将支持 contention-based CG resources，至少用于直接传输 BSR/DSR MAC CE。
- **proposal** 10.3.1.3 — SR/BSR 使用哪类 UL resources（例如 CBUL、CG 或 PUCCH）可由 network configuration 决定。将研究降低不同 UL resources 上 SR transmission latency 的技术。
- **proposal** 10.3.1.3 — 建议将 contention-based UL PUSCH resource 用于 early BSR reporting，并通知 RAN1 考虑该设计要求；讨论支持研究和比较方案，同时指出需评估相对现有方案的收益及碰撞概率。讨论还提出 UE ID、DMRS 是否专用或共享，以及 CB 是否仅限 BSR 等待研究的问题。
- **proposal** 10.3.1.3 — 6G 应支持 dedicated SR，用于请求 UL resource，并支持类似 BSR/DSR 的机制报告 buffer status 和 delay information；无论是否引入 CB-PUSCH。
- **proposal** 10.3.1.3 — 当 UE 没有可用于向 RAN 发送 scheduling information 的 UL-SCH resource 时，UE 向 RAN 发送 scheduling request，以请求用于发送该信息的 UL-SCH resource。
- **proposal** 10.3.1.3 — 以 5G 中 Type 1/2 configured grant 为起点，进一步研究 6GR 的 resource efficiency enhancements，用于低时延上行资源分配。
- **proposal** 10.3.1.3 — RAN2 应研究 CG 的 radio resource configuration 和 adjustment enhancement，以支持突发流量业务。
- **proposal** 10.3.1.3 — 提出研究统一的 CG framework，至少满足 RRC-based configuration、Flexible CG activation，以及使用 DCI 进行 Flexible modification。讨论中对是否统一 Type 1/2 CG、采用何种基线及如何适配 bursty traffic 存在不同意见。
- **proposal** 10.3.1.3 — RAN2 应研究统一的 buffer status reporting，报告 total buffered data volume 和 buffered data 的 delay status。
- **proposal** 10.3.1.3 — 提出为 6G 定义统一的 buffer status 和 delay status reporting procedure，并覆盖新类型数据的报告。讨论涉及是否采用统一 DSR/BSR、统一 signaling 或 procedure，以及报告内容、触发条件和格式。
- **proposal** 10.3.1.3 — 提出研究新的 LCP designs，以 cohesive 方式支持多个 performance objectives（如 throughput 与 delay），并增强对 application context awareness 和 adaptive QoS 等新用例的适应性。
- **proposal** 10.3.1.3 — 提出研究增强型 LCP mechanism，使 LCP parameters 能够动态调整。
- **proposal** 10.3.1.3 — 以 5G 的 LCP design 为起点，RAN2 进一步研究 LCP enhancements，并考虑 delay、importance 及 inter-QoS flow/packet correlation 等 traffic characteristics。

## 6GR 移动性（25 条）

- **agreement** 10.4 — NR cell (re)selection framework（包括 best cell principle、cell ranking 和 inter-freq/RAT prioritization 等）作为 6G cell reselection framework 的基线。后续研究 6G 相关方面对 cell selection/reselection 的影响，并待其他 WGs 在 cells、reference signals 和 measurement framework/requirements 等方面取得进展后继续讨论。
- **agreement** 10.4 — 对于 5G 与 6G 的 inter-RAT mobility，起步方案支持 RRC_CONNECTED 状态下的 handover 和 re-direction，并可向 UE 提供 inter-RAT cell reselection information。进一步增强需求待 intra-RAT 方案的后续讨论后再评估，并考虑 MRSS。
- **observation** 10.4 — 5G mobility 设计的关键经验包括：不同 3GPP releases 中存在针对不同 handover types 的冗余设计；提升 HO performance 的方案往往仅适用于特定 handover types。
- **observation** 10.4 — NR mobility 存在碎片化和复杂性，且与服务无关。6G 应面向多样化服务和设备，目标是建立单一、稳健、低时延且可扩展的框架。
- **observation** 10.4 — 5G NR 中，L1 和 L3 measurement 使用分开且重复的 RS configurations。
- **observation** 10.4 — 在 5G NR 中，UE 应先执行 L3 measurement，以确保目标小区是已知小区，然后再执行 L1 measurement。
- **observation** 10.4 — 在 5G NR 中，L1 measurement results 作为 L3 measurement results 的中间输入。
- **observation** 10.4 — 网络可利用 L1 measurement results，有效推导 cell/beam-level measurements 和 L3-filtered measurements。
- **observation** 10.4 — 5G 的一个痛点是多个额外的 MG 相关功能（如 NeedforGap Pre-MG、Con-MG、NCSG）未纳入 5G Day-1，增加了支持不同功能的复杂性。6G Day-1 应支持简单且灵活的 MG signaling procedure。
- **proposal** 10.4 — 提出为所有支持的 handover types 设计统一的 6GR mobility framework，目标包括采用相同的 configuration signaling structure，并尽可能复用同一组 building blocks（functions/procedure steps）。该提议被记录（Noted）。
- **proposal** 10.4 — 提出将 L3 HO 和 LTM 整合为单一 mobility framework，支持基于 L3/L1 measurements 和 L3/L2/L1 signalling 的 network-triggered 与 conditional mobility。
- **proposal** 10.4 — 提出统一 L3 HO 和 LTM（包括 network-triggered 和 conditionally triggered）的 signalling 与 procedural framework，同时允许分别配置各自的 triggering 和 reporting conditions/parameters。讨论认为可整合共同部分，但记录中对统一信令类型、保留 L3 与较低层信令等仍有不同意见；提议被记录（Noted）。
- **proposal** 10.4 — 提出 6G unified mobility mechanism 应覆盖两类流程：网络不经预配置而配置并触发 mobility、UE 随即执行；以及网络向 UE 预配置候选配置后，由 NW/UE 触发 mobility。原文还指出 NW-triggered mobility 和 UE-initiated mobility 适用于不同目的和场景；提议被记录（Noted）。
- **proposal** 10.4 — 提出 6G unified mobility 支持基于 L1 和 L3 measurement 的 mobility、NW-triggered 和 UE-initiated mobility，以及 immediate 和 subsequent cell switch。还提出支持 RACH-less、early UL/DL sync、early CSI 和 early RRC processing；提议被记录（Noted）。

## 6GR 用户面架构（36 条）

- **observation** 10.3.1.1 — 大多数 NR UP functions 被认为是连接 L2 以上 upper layers 与 physical layer 所必需的。
- **observation** 10.3.1.1 — NR UP protocol stack 存在多组重复功能。
- **observation** 10.3.1.1 — 考虑到 6GR 将支持的 service types，radio bearer 和 logical channel 仍可能有助于满足 latency、error recovery 等特定要求。
- **observation** 10.3.1.1 — NR 中引入了多种 compression mechanisms，包括 ROHC、UDC 和 EHC；这些机制虽独立引入，但具有共同点。
- **observation** 10.3.1.1 — 在 5G 中，每个 PDCP SDU 生成的 MAC-I 会带来额外 signalling overhead，并占用 UE processing capability，从而影响 UE transmission bit rate。
- **observation** 10.3.1.1 — Data concatenation 可能导致大小可变、bit positions 不固定的 headers，不利于硬件处理。
- **observation** 10.3.1.1 — Data concatenation 可能增加 segment handling 和 reassembly delays。
- **observation** 10.3.1.1 — 同一 SN 用于 ARQ 与 (re-)segmentation 功能，以及 security 与 re-ordering 功能，有利于降低 L2 overhead 并提升效率。
- **observation** 10.3.1.1 — 在 NR 中，单个 code block (CB) 失败可能延迟其他 CB 中 PDU 的交付；在 TB 大得多的 6G 中，这一问题可能更严重。
- **observation** 10.3.1.1 — 在 TB 中包含关于 MAC CEs 或 MAC subPDUs 的 metadata，可以帮助接收端加快 TB 处理。
- **observation** 10.3.1.1 — 6G 中的 MAC CEs 可以采用更结构化的设计，以实现高效处理并满足预期更严格的 6G timing requirements。
- **observation** 10.3.1.1 — NR UP headers 的长度可变，尤其是在 MAC 和 RLC 中，这不利于硬件实现。
- **observation** 10.3.1.1 — 导致 header length 动态变化的因素包括 RLC 中 segmentation 的有无，以及 MAC 中的 LCID 和 L field。
- **observation** 10.3.1.1 — 统一 header length 的一种简单方式是始终采用较长的 header；但应避免这样做，因为这会增大 Message 3 等消息的尺寸，而这些消息是 coverage bottlenecks。
- **observation** 10.3.1.1 — 在 NR 中，通过 RACH partitioning 提前指示 feature combinations 会导致 RACH resources 的利用非常低效。
- **observation** 10.3.1.1 — 在 NR 中，RACH resources 难以适应接入负载的短期变化，常导致高争用和接入失败。
- **proposal** 10.3.1.1 — 6GR 应在 UP protocol stack 的高层支持 QoS flows（或由 SA2 设计的 sub flows）到 UL 和 DL radio bearer 的映射，以及 security protection、data PDU 的 sequence numbering、ROHC Header and Data compression、延迟 PDU 的 timer-based discard 和 duplicate detection and discard。原文还指出 Header compression 应根据 plenary 暂缓，data compression 是 UDC 且尚未商业化；ZTE 认为 data compression 也可适用于 DL，且不意味着需要对所有内容启用。
- **proposal** 10.3.1.1 — 6GR 应在 UP 协议栈的低层支持按物理层 grant 大小分段、逻辑信道优先级处理与复用、调度请求，以及带或不带软合并的传输和重传（HARQ、ARQ）。
- **proposal** 10.3.1.1 — 列出了被视为 6GR UP 必需基本功能的 NR UP 功能，包括数据传输、序列编号、重复检测与丢弃、PDU 丢弃、重传、分段与重组、MAC 复用与解复用、优先级处理、压缩、安全协议及有序和无序交付。
- **proposal** 10.3.1.1 — 提出 6G Day1 至少应支持所列 UP 功能，具体支持方式可进一步研究。清单涵盖 QoS flow 与 DRB 映射、SN 维护、压缩、安全、丢弃、重复处理、交付顺序处理、重分段、L2 ARQ、复用、调度信息报告、HARQ 和 LCP。
- **proposal** 10.3.1.1 — 提出 QoS（重）映射、SN 维护、重复丢弃、（重）分段和（解）复用等功能应在 UP 中支持且不可禁用；并列出 UP 至少支持的数据传输、安全、序列编号、头压缩、SDU 丢弃、重复检测与丢弃、有序和无序交付、重排序、分段与重组、逻辑信道优先级处理与复用、调度信息报告及传输和重传。
- **proposal** 10.3.1.1 — 提出可将多个 PDCP SDU 拼接为单个 PDCP PDU。讨论涉及目标服务、硬件适配、grant 预测、MAC-I 开销，以及拼接后再分段可能带来的时延和内存缓冲需求。
- **proposal** 10.3.1.1 — 提出 6G 用户面协议栈的数据处理单位仍保持为逐包粒度，与 NR 相同。
- **proposal** 10.3.1.1 — 建议在高数据率、短到达间隔或时延要求宽松等有明确收益的场景研究 6GR packet concatenation，同时尽量减少对低层运行的约束并保留 QoS 和优先级隔离。还提出研究发送侧逐包预处理；讨论记录了拼接的处理开销、时延、硬件加速器利用及安全相关考量，并决定待 UP 协议和安全理解进一步完善后再讨论拼接。
- **proposal** 10.3.1.1 — 提出 RAN2 研究 joint sequence numbering，以提升 6G L2 transmission efficiency。讨论认为该方案可能与 PDCP 和 RLC 是否合并有关，可进一步研究。
- **proposal** 10.3.1.1 — 提出研究跨 PDCP 和 RLC 层统一 packet 的 SN，并研究适用于 standalone operation 的单一 sequence numbering 功能设计。讨论提及该方案与层间关系及相关功能有关，意见包括可行性、硬件适配性和研究时机。
- **proposal** 10.3.1.1 — 提出研究新的 MAC PDU 格式，例如独立 CB，以及包含 TB 中 MAC CE 或 MAC subPDU 元数据的格式，以支持接收端更快处理。
- **proposal** 10.3.1.1 — MAC CEs 应设计为灵活且多用途的信令机制，同时保持易于处理和组装。
- **proposal** 10.3.1.1 — 为支持硬件友好处理，6GR UP protocol 追求为每个 upper layer SDU 使用固定大小的 header。
- **proposal** 10.3.1.1 — RAN2 研究尽量减少 header length 的动态变化，重点关注 RLC 中的 segmentation 以及 MAC 中的 LCID 和 L field，同时避免统一为更长的 header。
- **proposal** 10.3.1.1 — 提出设计统一的 Random Access procedure，以尽量减少对 RA partitioning 的需求，并与 RAN1 一同研究 RA PUSCH payload size 可能存在的问题。
- **proposal** 10.3.1.1 — 提出研究更高效利用资源的 RACH designs，例如除非确有必要，否则避免 RACH partitions，并动态或按需分配 RACH resources。意见指出，preamble partitioning 应仅用于严格需要的功能，例如 coverage enhancements。
- **proposal** 10.3.1.1 — 6GR RA procedure 从一开始就支持 2-step 和 4-step RA procedures，以及 coverage enhancement。
- **proposal** 10.3.1.1 — 提出 6GR 不考虑 Reflective QoS。
- **proposal** 10.3.1.1 — 6G 保留使用 End-Marker 将 QoS flow 重新映射到 RB 的机制；Reflective QoS 在 6G 中是否仍有必要将进一步讨论。
- **proposal** 10.3.1.1 — 提出 RAN2 研究以 UP control signalling（例如 PDCP control PDU）替代 5G Reflective QoS mechanism 的新 QoS flow 到 DRB remapping mechanism。另有提案提出考虑 L4S、优先传输 L4S feedback、研究在 L2 protocol layers 中区分 L4S 与非 L4S traffic，以及考虑对 L2 buffer 支持 AQM。

## 6GR RRC（62 条）

- **agreement** 10.3.2 — 拟研究 6G RRC 的连接管理流程，包括建立、重配置、重建立和释放，并研究 UE 发起的 RRC connection release；6G RRC 采用单一 sublayer（no upper/lower split）。此外，研究 inactive mode 或 sub-state 对快速进入 data exchange 和 network controlled transitions 的支持，并进一步评估 state/sub-state 建模及 single paging mechanism。

- **observation** 10.3.2 — 原文指出，支持 RRC split（例如允许 DU 直接向 UE 发送 CellGroupConfig）可能需要 RAN-CU 与 RAN-DU 进行更多协调。
- **proposal** 10.3.2 — 提议 6G 采用基于 5G RRC_IDLE、RRC_INACTIVE 和 RRC_CONNECTED 功能的三态 RRC state model，并进一步研究改进这三种状态的功能。
- **proposal** 10.3.2 — 提议研究 RRC_INACTIVE 能否支持独特的增值功能，或能否增强现有 inactive 功能以使其更简单。
- **proposal** 10.3.2 — 提议 RAN2 研究 RRC state behaviour，包括 paging mechanisms、identifier usage、location update procedures 及相关端到端时延，并研究改进 RAN Notification Area 规划和部署以及 UE context management 的方法。记录中还提出 connected mode 子状态是否需要 RAN notification area 的问题。
- **proposal** 10.3.2 — 提出仅保留 RRC_CONNECTED 和 RRC_IDLE 两个顶层 RRC states，并引入 sub-states（modes）处理不同活动水平及功耗与性能权衡，同时允许按 UE 定制 RRC sub-state machine 以保持 UE 精简。
- **proposal** 10.3.2 — 提议考虑适用于 idle、inactive、connected 及状态转换机制的 model agnostic functionality，并假设所讨论功能可用于两态或三态模型，且两种模型中的“inactive”均指中间状态。
- **proposal** 10.3.2 — 提议重新审视 state model，并在功能明确后决定 inactive 作为 connected sub-state 或独立 RRC state 哪一种更能表达该功能。
- **proposal** 10.3.2 — 讨论提出为 inactive 到 connected 的快速转换定义时延目标（例如 10ms），并围绕 Energy Efficient Sub-state 的适用问题、移动性、功耗和信令等展开讨论。提案包括增强 RRC_INACTIVE、支持小数据传输，以及研究基于 CG 的 RACH-less resume；各方意见仍在讨论中。

- **proposal** 10.3.2 — 提议研究适用于 RRC_CONNECTED 无数据传输场景的 Energy Efficient Sub-state。该子状态包括预配置 cell-list 和相关配置、UE based mobility、用于网络和 UE 节能的 UL/DL WUS，以及低状态转换时延。

- **proposal** 10.3.2 — 提议 RAN2 研究 UE based mobility：在“DRX-off”/“no-data”期间，UE 可依据 RRM measurement results 执行 cell switch，而非由网络 HO command 触发。在小范围内（例如数个小区）切换后，UE 可以不通知网络。
- **proposal** 10.3.2 — 提议 RAN2 研究通过 UE dedicated layer-1 signalling（例如 DL WUS）进行下行唤醒，以替代 RAN paging。此举旨在节省 paging message 的调度和接收时延。
- **proposal** 10.3.2 — 提议 RAN2 研究降低数据传输准备时延，包括通过 CFRA、2-step RA、configured grant 或 RACH-less 降低 UL access latency，通过 early measurement/CSI acquisition 降低测量相关时延，以及通过预配置 UE context/configuration 降低配置相关时延。
- **proposal** 10.3.2 — 提议研究 suspend/resume procedure，作为降低 IDLE 到 CONNECTED 转换时延、简化 6GR UE 和简化整体 6G system 的潜在方法。
- **proposal** 10.3.2 — 提议 RAN2 研究 non-connected mode 的单一 location tracking management，例如同时适用于 IDLE 和 INACTIVE。
- **proposal** 10.3.2 — 提议 RAN2 研究在 CN 管理 non-connected mode 的 UE RAN context，包括 UE 从 connected 转为 non-connected 时将 context 上传至 CN，以及为 paging 向 base station 传递 context。讨论还涉及单一 paging 机制、CN paging 和减少对 Xn 的依赖。
- **proposal** 10.3.2 — 将以下 5G RRC procedures 作为 6GR connection management 的基线：RRC connection establishment、resume、reconfiguration、re-establishment 和 release。原文列明了 establishment、resume 与 release 对应的 RRC 状态转换。
- **proposal** 10.3.2 — RAN2 将推迟讨论 RRC layer split，直到 RAN3 或 RAN 就是否支持 CU-DU split 作出决定。在此之前的设计决策应基于 single RRC layer。
- **agreement** 10.3.2.2 — Delta configuration 仍被认为有助于降低 signalling overhead；目标是解决其实现复杂度、兼容性以及功能性必需参数缺失或初始配置后不应修改的参数被更新等问题。会议预期识别可能的解决方式并记录其他观察。
- **agreement** 10.3.2.2 — 已指出 UE 只能应用部分 RRC reconfiguration 的问题，并注明这与 IODT issue 无关。将研究如何解决该问题。
- **observation** 10.3.2.2 — 跨状态转换存储并复用 RRC configurations 可降低 signalling overhead 和功耗。原文指出这可带来更快的状态转换、更好的功耗节省以及更可预测的时延，并使 UE 和网络受益。
- **observation** 10.3.2.2 — 6GR RRC 设计应包含避免在每条 reconfiguration message 中显式配置 UE 全部 RRC 参数的 signalling technique(s)，例如 delta configuration。
- **observation** 10.3.2.2 — 对 UE 当前配置应用 Delta configuration，在连续进行后续 reconfigurations，或因 service(s) 或 hardware profile 变化而显著改变 UE configuration 时，可能效率低下。
- **observation** 10.3.2.2 — 对 UE 当前配置应用 Delta signalling 可能容易出错，因此一些 network implementations 可能选择优先使用 full configuration。
- **observation** 10.3.2.2 — 检测到 RRC reconfiguration failure 后触发 RRC connection reestablishment 会带来显著负面影响。
- **observation** 10.3.2.2 — 并非所有 configuration errors 都会影响当前传输。
- **observation** 10.3.2.2 — 指出网络无法完全保证配置正确性。
- **observation** 10.3.2.2 — 在 NAS procedure 和 CHO candidate configuration procedure 中，如果出现错误，UE 无需中断当前连接并启动 RRC reestablishment procedure。
- **observation** 10.3.2.2 — 在 5G 中，若 UE 无法应用网络提供配置的一部分，通常会导致整个配置不可用；遇到问题配置或 reconfiguration failure 时，UE 当前会启动 connection re-establishment procedure。
- **observation** 10.3.2.2 — 指出相当一部分 reconfigurations 中 UE 无法应用整个配置；此类问题在技术刚部署、尚不成熟时更常见，尤其是在配置需要时间稳定且 UE 必须实现定向 workarounds 的新市场。
- **observation** 10.3.2.2 — 指出 dynamic capability updates 和 UAI 均无法有效解决这些问题，导致不必要的 reestablishment procedures、service interruptions 和 RLF statistics 增加。
- **observation** 10.3.2.2 — 指出 UE 与 NW 之间对 (re)configuration 进行适当同步非常重要。
- **observation** 10.3.2.2 — 指出现场 UE re-establishment 的总体概率约为 2% 至 3%；由 UE 无法遵循 partial reconfiguration messages 引起的 re-establishment 仅占总量的一小部分。
- **proposal** 10.3.2.2 — 提议在 RRC configuration 中定义 functional modules，以“functional modules”而非“layers”组织协议；示例包括 Mobility Management、Access Control、L2 Data Handling 和 Physical radio resource configuration 模块。
- **proposal** 10.3.2.2 — 提议将 RRC ASN.1 内容划分为基本模块（一个通用模块及若干交叉耦合较弱的共用模块，如 mobility、measurement）和特性模块（如 NTN）。讨论认为需先明确要解决的问题并提供实例，包含 ASN.1 modularization；预期成果包括梳理问题及讨论模块方案。
- **proposal** 10.3.2.2 — 提出研究模块划分规则，包括按 feature 维度区分基本/共用/强制模块与可选模块、按通信对象对以及按 WG 维度划分，并考虑将 physical configuration 作为独立模块及由 RAN1 维护的可能性。还提出研究 6G ASN.1 modularization 的划分层级，例如 IE structure、RRC message、ASN.1 module 或 specification 层级。
- **proposal** 10.3.2.2 — 6G RRC 模块化研究考虑三项原则：基本 CP/UP 通信功能所需的配置参数放入 common module；非基本功能参数可放入 feature-/functionality-specific module；彼此独立的功能参数应放入不同的专用模块。讨论指出 delta configuration 可减少 signaling overhead，而 Need codes 等额外约束和条件是实现复杂度及兼容性问题的主要来源。
- **proposal** 10.3.2.2 — RAN2 研究改进 delta configuration，以减少歧义和实现复杂度，例如将 optional signaling（如 Need codes）的处理与 configuration guideline 信息分离。讨论提出研究 ASN.1 方法，包括为初始配置和后续重配置定义不同的 ASN.1 IE，并分别用 mandatory fields 承载功能必需参数、排除不应修改参数的字段；此提案被记录，尚未定案。
- **proposal** 10.3.2.2 — 6G RRC 配置和信令设计应允许基于 configuration modules 重用已存储配置。
- **proposal** 10.3.2.2 — 设计 6G RRC 时，考虑针对不同 use cases 优化的多个已存储配置，并支持网络按需激活。
- **proposal** 10.3.2.2 — 支持相对于多个 UE 和网络已知的 reference configurations 之一进行 delta signalling。
- **proposal** 10.3.2.2 — 支持通过指示（例如使用 MAC CE 或 RRC message）多个已存储配置或 reference configurations 之一来进行重配置。
- **proposal** 10.3.2.2 — 在 RRC reconfiguration procedure 中，如果 UE 无法遵从部分配置，且该部分不影响当前传输，则允许 UE 应用可用的配置部分，而不启动 connection re-establishment procedure。
- **proposal** 10.3.2.2 — 6G 设计将允许 UE 保留或应用可用的配置部分，以尽量减少 re-establishment procedures 的次数。
- **proposal** 10.3.2.2 — 研究在允许 UE 保留或应用部分配置的同时，如何保持 UE 与 NW 之间的 (re)configurations 同步。
- **proposal** 10.3.2.2 — RAN2 先研究由 UE 无法遵从配置导致的失败概率，再确定是否需要 partial success/failure mechanism。
- **proposal** 10.3.2.2 — 提出在 6G signaling 中引入 constraint subtypes。
- **proposal** 10.3.2.2 — 为降低 UE processing 和 network configuration provision 的难度，考虑优化 RRC configuration structure。建议将具有相同属性的配置归组，并将需要关联的参数置于同一结构中，或以相同方式/位置描述其关系。
