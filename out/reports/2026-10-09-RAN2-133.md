# RAN2 #133 增量简报

> 共 471 条事件 · [会议目录](https://www.3gpp.org/ftp/tsg_ran/WG2_RL2/TSGR2_133/)

## 6GR 能效（17 条）

- **agreement** 10.3.3.3 — 提出一次仅激活一个 DRX configuration，并研究是否需要多个配置及其 use case；同时研究三种 C-DRX 与 DL WUS 组合。目标是定义统一的 discontinuous monitoring framework，涵盖 UE 对 wake up signalling 的周期监测及后续 PDCCH monitoring，并考虑与 NW sleeping opportunities、cell DTX/DRX 的交互。
- **agreement** 10.3.3.3 — 研究网络休眠时，UE 在所有 RRC states 下运行所需的信息。初步提出 UL 侧至少需知道 UL resources 及可发送时机，DL 侧需知道网络可能发送下行内容的时机，例如 resources 和用于测量的 reference signals。
- **observation** 10.3.3.3 — 原文提出，6G 预计会引入更多类型的业务流量，各自具有不同的时延、周期性、数据量和突发性特征，因此需要 differentiated 或 service aware 的 CDRX configuration，以多个参数值适配多种流量模式。
- **proposal** 10.3.3.3 — 提出 RAN2 在 6G 中考虑为 UE 配置并启用多个 DRX configurations（多于两个）；关于是否同一时间只激活一个 DRX configuration，意见存在分歧。该提议被记录（Noted）。
- **proposal** 10.3.3.3 — 提出支持单个 DRX configuration，并为其设置多个参数值以适配某一业务的不同流量模式；讨论意见包括无需同时运行多个 DRX、多个配置可能增加复杂度且不利于省电，以及可根据 traffic flow 调整 timers。该提议被记录（Noted）。
- **proposal** 10.3.3.3 — RAN2 研究 RRC_CONNECTED UE 的两种 DL-WUS 方案：一种与类似 c-DRX 的机制协同，在检测到 DL-WUS 后于 c-DRX on-duration timer 内监测 PDCCH；另一种与该机制解耦，在检测到 DL-WUS 后于新定义的 timer 内监测 PDCCH。该事项被记录（Noted）。
- **proposal** 10.3.3.3 — 提出可考虑三种用于 RRC_CONNECTED UE 省电的 DL-WUS use cases：在 drx-onDurationTimer 前配置时机的 DCP-like DL-WUS、C-DRX active period 内动态 PDCCH monitoring 的 DL-WUS，以及触发额外或非周期 on-duration timer 的 LP-WUS option 1-2-like DL-WUS。该提议被记录（Noted）。
- **proposal** 10.3.3.3 — 记录了从 RAN2 角度进一步研究三种配置的优先选择：C-DRX without DL WUS、DL WUS together with C-DRX，以及 DL WUS without C-DRX。
- **proposal** 10.3.3.3 — 记录了研究 C-DRX 与 dynamic wake-up mechanism；是否引入 DCP 或 DL-WUS，应在 DL-WUS 设计细节确定并经 RAN1 讨论评估后论证。讨论意见包括支持研究所有选项、以 DL WUS with DRX 为基线，以及担忧 DL WUS without C-DRX 的可靠性和多方案复杂度。
- **proposal** 10.3.3.3 — 记录了 6G 支持 cell DTX 和 UE C-DRX；还支持 cell DTX/DRX 与 UE CDRX 对齐，同时允许二者的 active time 长度不同。
- **proposal** 10.3.3.3 — 记录了对于 RRC_Connected UEs，UE DRX configuration 与 cell DTX configuration 对齐。
- **proposal** 10.3.3.3 — RAN2 将 5G Cell DTX/DRX mechanism 作为 6G 实现 Network sleeping opportunities 的起点，即由 NW 配置明确的周期性 active/inactive pattern。详细机制仍待进一步研究。
- **proposal** 10.3.3.3 — 记录了 6G 中 Cell DTX/DRX 可配置为与 UE CDRX 配合或不配合，以提高 UE 和 NW 的灵活性。讨论涉及周期模式、与 UE active times 对齐、idle/inactive/connected mode 支持，以及 delay sensitive traffic 下 UE 唤醒网络等事项。
- **proposal** 10.3.3.3 — RAN2 将研究 flexible cell DTX 与 flexible UE C-DRX 的联合且简化的设计，例如避免功能重复。
- **proposal** 10.3.3.3 — 记录了 connected state 下 joint UE/network power saving 的考虑方向：固定模式的 UE/network sleeping cycles 应对齐，例如一个周期为另一个的倍数；动态模式则应设计节能 signaling，以触发 cell 和 UE 的 active/non-active periods。
- **proposal** 10.3.3.3 — 进一步研究 cell DTX/DRX-like mechanism 时，cell DTX 不必像 NR Rel-18 那样仅与 UE C-DRX 紧密耦合，并应考虑 DL WUS；DL WUS 可在有或没有 UE C-DRX 时工作。
- **proposal** 10.3.3.3 — RAN2 将研究在网络启用 sleeping opportunities（例如 Cell DTX/DRX）时，如何确保 UE 的 QoS。

## 6GR AI/ML 协议支持（31 条）

- **agreement** 10.3.3.2 — 研究 UL traffic prediction，可采用 non-AI 或 AI-based 方法；研究可预测的内容及其收益，并研究网络需要对预测具备何种程度的 confidence。相关讨论在 UP 继续。
- **proposal** 10.3.3.2 — 认定 5G-A 研究中结论为可行的 temporal domain cell level prediction、frequency (co-located) domain cell level RRM prediction、event prediction 和 L3 beam level prediction，在 6G 中也被认为可行且有益，因此无需重复仿真，可直接研究潜在方案。对 L3 beam level prediction 的仿真范围和覆盖子场景是否充分，以及是否仅评估 network side 等意见存在讨论。
- **proposal** 10.3.3.2 — 研究 AI Mobility use-cases 时，Rel. 20 SI 至少应遵循四项原则：尽量减少与 ongoing Rel. 20 5G WI on AI Mobility 的重叠；明确所研究 AI enhancements 对应的 6G Mobility procedure 假设；明确 data collection 和 model transfer/delivery framework 假设；并在 6G AI/ML mobility evaluation 中考虑 Rel-20 的 6G evaluation assumptions。
- **proposal** 10.3.3.2 — 建议 RAN2 优先评估新 use cases 引入 AI/ML 的动机和潜在性能增益，并初步认为 model complexity 和 memory footprint 并非关键障碍，可在详细规范阶段处理。讨论中提出，对于 energy saving，应考虑模型推理能耗可能抵消节能收益；对新 use cases，复杂度评估可由公司开展但不强制。
- **proposal** 10.3.3.2 — RAN2 应基于 RAN1 已同意的 inter-cell 和 inter-frequency L1/L3 beam measurement prediction use cases 开展 AI/ML-based mobility 研究。RAN2 可研究 cell-level measurement、L3 beam measurement prediction 及 L1/L3 event predictions。
- **proposal** 10.3.3.2 — 该条目请参阅 Table 2 获取 justification，并参阅其他表格内容了解 Table 1 所列的 additional sub-use cases。
- **proposal** 10.3.3.2 — 建议 6G 研究 non-co-located 场景下的 RRM measurement prediction，包括 non-co-located inter-frequency inter-cell prediction，以及采用不同 beam patterns 的 non-co-located inter-frequency intra-cell prediction。
- **proposal** 10.3.3.2 — 建议在 6G SI 中考虑以下 AI mobility use cases：RRM Measurement prediction、Measurement event prediction、Spatial domain RRM measurement prediction 和 L3 beam prediction。
- **proposal** 10.3.3.2 — 对于时域和频域（同址）L3 小区/波束级预测以外的 RRM prediction use cases，RAN2 负责 mobility performance gain evaluation、LCM enhancement、data collection 和 AI mobility enhancement 的规范影响；RAN4 负责 prediction accuracy evaluation、requirements、testability 和 interoperability。RAN2 将 RRM prediction use cases 研究推迟至 RAN4 完成 prediction accuracy evaluation 后。
- **proposal** 10.3.3.2 — 将 RRM measurement prediction 和 mobility event prediction 作为待研究用例，研究时机为 6G 的 L1、L3 measurement 和 mobility framework design 更明确之后。
- **proposal** 10.3.3.2 — 将 AI/ML 扩展到 LTM 场景，支持 AI/ML based LTM 作为 6G AIML use case 纳入 RAN2 研究。
- **proposal** 10.3.3.2 — 对于 AI/ML-assisted LTM，为减少 measurement efforts 并提升 handover performance，RAN2 支持基于 UE-side model 和 NW-side model 的 AI/ML based L1 measurement prediction，以及基于 UE-side model 的 AI/ML based L1 measurement event prediction；NW-side model 的 L1 event prediction 可由网络实现决定。相关预测需要进行 simulations，且应考虑 6G mobility framework 的研究进展。
- **proposal** 10.3.3.2 — 提出 AI/ML-assisted LTM 支持 early downlink sync prediction（预测 activated/deactivated TCI state）、early uplink sync prediction（预测 TA value）和 target cell prediction。关于 TA prediction 的结论为 FFS。
- **proposal** 10.3.3.2 — RAN2 认为 5G-A study 中已确认可行且有益的时域小区级、频域（同址）小区级 RRM、Measurement Event（A1-A6）及限定范围内的 L3 beam level prediction 用例，在 6G 也可行，无需重复 simulation，可直接研究潜在方案。RAN2 至少以 Rel-20 AI Mobility 支持的用例为起点，并将机制适配 6G mobility framework；RRM measurement prediction 和 mobility event prediction 待 6G 测量与 mobility framework 更明确后研究。
- **proposal** 10.3.3.2 — 将 UL traffic prediction 用于 L2 scheduling enhancement 列为 RAN2 主导的 6G AI/ML use case，采用 UE-side model。预测的 UL traffic information 至少用于携带预测流量信息的 BSR 以降低 scheduling latency，以及避免 LCH starvation；其他 L2 feature 为 FFS。
- **proposal** 10.3.3.2 — 针对用于 L2 scheduling enhancement 的 UL traffic prediction，RAN2 研究基于一致 traffic model 的 prediction accuracy evaluation，以识别适用流量类型和性能；采用 3GPP 指定 traffic model 还是不同流量类型的 field dataset 仍为 FFS。研究内容还包括预测粒度、除 BSR 和 LCP 外的其他 L2 features（考虑 6G UP 最新进展）以及潜在规范影响。
- **proposal** 10.3.3.2 — RAN2 将讨论如何研究用于 UE/NW energy efficiency（例如增强 UE CDRX 和 Cell DTX/DRX）的 DL traffic prediction，包括预测在 UE 还是 NW 执行、是否及如何评估性能，以及 NW/UE power consumption model 等跨工作组影响。
- **proposal** 10.3.3.2 — RAN2 将研究 6G traffic prediction，CP 用例包括 carrier aggregation 的设置、释放、激活和去激活，RRC 状态或 battery saving mode 间的转换，以及用于负载均衡的 mobility decision；该类预测可基于 AI 或非 AI，并适用于 UL 和 DL。离线讨论还提出将非同址 L3 measurement prediction、L1/L3 beam prediction、conditional mobility 相关 measurement event prediction、RLF prediction/recovery 和 AI/ML based TA prediction 纳入用例表，其中部分事项待协调或仍需讨论。
- **proposal** 10.3.3.2 — RAN2 根据 5GA Rel19 AI for mobility study 的进展恢复 RLF prediction 研究。输入至少可包括 PCell 的 measured/predicted L1 SINR。
- **proposal** 10.3.3.2 — RAN2 根据 5GA Rel19 AI for mobility study 的进展恢复 MOF prediction 研究，聚焦成功切换后不久发生 RLF 的 “too early handover” 和 “handover to wrong cell” 子场景。输入至少可包括候选目标小区的 measured/predicted L1 SINR。
- **proposal** 10.3.3.2 — RAN2 研究 BFD prediction 用例，并考虑将相关小区的 measured/predicted L1 SINR 至少作为输入信息。
- **proposal** 10.3.3.2 — 建议在 6G RRM mechanisms 定义前，复用 Rel-19 RRM measurement prediction 和 measurement event prediction 的评估结果开展 5G legacy use cases 研究。当前暂不纳入 RLF prediction study。
- **proposal** 10.3.3.2 — 研究 6G 中基于 AI/ML 的 TA prediction。预测的 TA values 可用于降低所有 RRC states 对基于 RACH 的同步的依赖，例如 RACH-less handover、STAG TA establishment 和 CG-SDT。
- **proposal** 10.3.3.2 — 6G AI/ML LCM framework 应支持 one-sided 和 two-sided model。
- **proposal** 10.3.3.2 — 6G AI/ML LCM framework 应支持 functionality-based LCM 和 model ID-based LCM。
- **proposal** 10.3.3.2 — 对于 UE-sided model，6G AI/ML LCM framework 应支持 UE-based 和 NW-based management。
- **proposal** 10.3.3.2 — 可考虑统一的跨 WGs AI/ML framework；如有必要，与 RAN3 和 SA 协调。
- **proposal** 10.3.3.2 — Network 应能控制 UE 是否应用可能影响 network QoS requirements、user experience 或 overall system performance 的 AIML based functionality。
- **proposal** 10.3.3.2 — 所有 AIML use cases 中，网络需要能够评估 AIML functionality 的性能，并尽快停用表现不佳的 AIML functionalities。
- **proposal** 10.3.3.2 — 对于 NW-sided models，沿用 5G-A 的做法：除 network-side data collection（例如用于 training）外，不规定其他 LCM functions，由网络实现决定。
- **proposal** 10.3.3.2 — RAN2 应研究 online training 对 AIML procedures（如 data collection 和 functionality management）的影响。

## 6GR 控制面其他议题（12 条）

- **observation** 10.3.2.5 — UE 在一个 carrier 上驻留并在同一 carrier 上发起 RA，不存在 capacity issue。
- **observation** 10.3.2.5 — 在 multiple CC deployment 中，从网络和 UE 角度看，期望 IDLE/INACTIVE 状态的 UE 驻留在 coverage layer，并在 capacity layer 上进行 UE dedicated data transmission。
- **observation** 10.3.2.5 — 原文指出，若 IDLE/INACTIVE UE 均驻留在 coverage layer，并在进入 CONNECTED 后切换到 capacity layer 进行专用传输，会造成 coverage layer 初始接入拥塞，以及切换延迟长、信令开销高。
- **observation** 10.3.2.5 — 在 MRSS 和 CA 部署中，若 PCell 位于 coverage layer，UE 连接和数据传输主要在 SCell 上。原文提出应考虑将 NR 中部分 PCell 功能卸载到 SCell，例如用于 SR 的 RACH。
- **observation** 10.3.2.5 — 在 MRSS 和 CA 部署中，若 PCell 位于 capacity layer，由于覆盖问题，恢复场景会比 NR 更频繁。原文提出应考虑通过 coverage layer（SCell）进行 PCell recovery。
- **proposal** 10.3.2.5 — 原文提出，对于 IDLE/INACTIVE UE，没有必要驻留在一个载波的同时在另一个载波执行 RA。
- **proposal** 10.3.2.5 — 原文提出 IDLE/INACTIVE UE 不需要支持 multi-carrier operation。所列 5G NR 经验指出，多载波部署中各 serving cell 均需发送自身的 SSB/SIB1，可能导致 always-on common signalling 的能耗和系统开销、UE 额外功耗及碎片频谱聚合支持不足。
- **proposal** 10.3.2.5 — RAN2 确认 6GR multi-carrier deployment 中 always-on common signalling aggregation mechanism 的收益，例如网络能耗和 UE 功耗节省。该机制由 reference carrier frequency 广播 SSB/SIB1，并为其他载波提供同步参考和初始接入相关配置，例如 PRACH config、CSS。
- **proposal** 10.3.2.5 — RAN2 6G study 应支持 cross-CC initial access procedure，并研究 UE 和网络在三个阶段的操作：初始接入前驻留 coverage layer、执行 cross-CC initial access，以及进入 CONNECTED 后在 capacity layer 保持连接。非连接态方面已同意 UE 无需在多个载波监测 paging；初始接入是否使用与驻留载波相同或不同的载波仍为 FFS，后续研究等待 RAN1 进展。
- **proposal** 10.3.2.5 — 对于 CONNECTED mode 的 spectrum aggregation，RAN2 目标是形成统一的 carrier level resource aggregation 方案，并以 5G CA 为基线。可继承的 5G CA 增强包括 Early measurement report、Dormancy SCell、Fast SCell activation、Fast SCell beam recovery 和 CA with Tx switching。
- **proposal** 10.3.2.5 — 原文提出在 6G 进一步研究 CA 增强：UL/DL decoupling、PCell 与 SCell 间快速角色变更（也旨在改善 inter-frequency handover），以及 cross-carrier HARQ operation。讨论指出，统一方案不意味着必须纳入所有功能，且 cross-carrier HARQ 属于 RAN1 讨论范围。
- **proposal** 10.3.2.5 — RAN2 6G CA study 应考虑在 SCell 支持更多功能（例如 RLM、RA-SR），以及通过 SCell 进行 PCell failure recovery。讨论中有观点认为，监测 SCell 并报告可避免完整重建；相关提案及测量方法列为讨论内容。

## 6GR 数据与模型传输（22 条）

- **agreement** 10.3.3.1 — 数据传输框架应至少支持两类用例：总数据量大且时延要求宽松，以及总数据量小且时延要求宽松。总数据量按 UE 累积存储的数据与最小 UE AS buffer 比较，区分为 Large 和 Small。
- **proposal** 10.3.3.1 — 提议 RAN2 认可两个定义：‘termination point’ 是 UE 与 NW entity 间 E2E data transfer transport protocol stack 的端实体；‘data consumer’ 是可处理所收集数据的实体，可位于 MNO 内部或外部。数据应仅由 data consumer 解码和处理。
- **proposal** 10.3.3.1 — QoS 特征分析区分 ‘Non-real time’ 与 ‘Real-time’：前者允许先累积数据再上报，后者要求立即向网络上报。数据量分为 UE 可累积的 ‘Accumulated data size’，以及考虑数据相关性、需在同一报告中一起上报的最小 ‘One-shot report data size’。
- **proposal** 10.3.3.1 — 提出进一步明确时延类别、termination points 和 RAN 对标准化数据内容的可见性，并将移动性期间的连续性与无损传输作为数据传输的附加方面；相关定义包括切换期间不重新启动传输过程，以及传输过程中不丢失任何数据位。该条目记录为 Not treated。
- **proposal** 10.3.3.1 — 提出适用于 AIML、sensing、SON/MDT 和 QoE 等应用及 UE-side、NW-side 数据收集的基线要求，包括保障数据安全、完整性和机密性，尊重用户隐私、匿名性与同意，并由 MNO 全面控制标准化数据收集传输过程且具备标准化数据的完全可见性。还要求设计可扩展，并尽量减少对 UE 电池、处理、内存、用户流量传输及省电功能的影响。
- **proposal** 10.3.3.1 — RAN2 研究数据传输方案时，应避免重复收集可由 RAN 利用的数据，并使其可由 RAN nodes 解码。方案还应支持单次或多次报告中从 tens of Kbits 到 several Gbits 的数据量、从 msecs 到 days（或无时延要求）的时延范围，并提升数据传输效率。
- **proposal** 10.3.3.1 — RAN2 旨在设计统一框架和架构，以管理 6G 中 AI/ML、Sensing、SON/MDT、QoE 及未来新兴服务的各种数据类型。
- **proposal** 10.3.3.1 — 提议按每报告的数据大小和时延定义数据特征类别：large 为大于 9 kB，small 为不大于 9 kB；时延类别为 relaxed（分钟、小时、天或无时延要求）和 near-real-time（数十毫秒至数秒）。该条目记录为 Noted。
- **proposal** 10.3.3.1 — 数据传输框架应支持高数据量（例如最高 hundreds of MB）与宽松时延（例如分钟至小时），至少以 RAN 和 UE-side server 为端点。
- **proposal** 10.3.3.1 — 数据传输框架应支持低数据量（例如最高 several hundred kB）与较低时延（例如 100ms 至数秒），至少以 RAN 和 OAM 为端点。该条目记录为 Noted。
- **proposal** 10.3.3.1 — RAN2 采纳 Table 1 用于 data transfer 分析。
- **proposal** 10.3.3.1 — 请求 RAN2 考虑 Table 1，用于分析 AI/ML Data 数据收集的不同方面，包括 QoS requirements、termination entities、consumers 和 RAN decodability。
- **proposal** 10.3.3.1 — 请求 RAN2 考虑 Table 2，用于分析 SON、MDT 和 QoE Data 数据收集的不同方面，包括 QoS requirements、termination entities、consumers 和 RAN decodability。
- **proposal** 10.3.3.1 — 对于给定的数据源和数据消费者，可能存在多个 termination point 组合；数据传输路径上不透明转发数据的中间节点（例如处理或重新格式化数据）也可视为 termination node。RAN2 暂定将 data consumer 定义为可消费、解码和处理所收集数据的实体，将 termination point 定义为 UE 与 NW 之间端到端数据传输协议栈中、可按需解码数据以供查看的网络实体。
- **proposal** 10.3.3.1 — 通过 data transfer framework 收集的数据不一定需要由 RAN 解码；当 RAN 是数据消费者时例外。
- **proposal** 10.3.3.1 — 6G RAN 节点可以配置为解码收集后以其他实体为终止点的数据。
- **proposal** 10.3.3.1 — RAN2 应研究采用哪种 data transfer 方案：增强 control plane、增强 user plane，或新方案（例如 new data plane、new entity/protocol layer 或 new RB）。
- **proposal** 10.3.3.1 — 6G 中的 model transfer 应满足 awareness 和 controllability 要求：MNO 可获知模型存在，并能控制模型传输/交付流程，包括启动、暂停、恢复和停止。

## 6GR UE 能力框架（23 条）

- **observation** 10.2.1 — Dynamic capability应避免因重新生成 supported BC list 而增加开销，并通过报告实际状态的 UE capability 兼顾 UE 与网络利益；网络可根据 UE capability 变化决定配置，也可考虑同时指示变化根因。

- **observation** 10.2.1 — 在 5G 中，UE capabilities 采用紧密耦合、深层嵌套的结构（如 per-band 和 per-band-combination capabilities），限制了通用 capability information 的复用，并导致不同频段和组合重复传送相同值。

- **proposal** 10.2.1 — RAN2 对 commercialization challenges 提出两种后续路径：发送 LS 向 RAN 汇报进展，或不再继续该议题并交由 RAN 讨论。Mandatory feature 未要求网络实现、导致难以跟踪 3GPP ecosystem 支持的 features 并保证 forward compatibility 的根因，以及等待“slowest” network vendor 后再部署的根因，留待 RAN 讨论；两项其他根因不予考虑，且 Root cause 3 是否纳入尚无共识。
- **proposal** 10.2.1 — Dynamic capability 支持因 overheating、power consumption constraints 和 hardware requirements 变化（例如 MUSIM、IDC、AI/ML processing unit）而改变 UE capabilities；Table 1 作为 RAN2 讨论和识别 6G capability change justification 与 requirements 的起点，其他 use case 尚待研究。
- **proposal** 10.2.1 — RAN2 确认 UAI 不足以报告 UE capability change：UE 上报受网络配置控制，网络收到 UAI 后应有的行为未明确，UAI 报告的是 RRC configuration preferences 而非 capability change，且按 feature 上报。

- **proposal** 10.2.1 — 研究如何在一份 technical specification 中涵盖所有 capability aspects，以简化 6GR UE capabilities 的规范、维护和实现。
- **proposal** 10.2.1 — 研究可扩展的 UE capability signalling 设计，目标是使 UE capability container 能装入单个 UL RRC message。
- **proposal** 10.2.1 — RAN2 研究灵活的 signaling design：UE 以 coarse granularity 报告 typical/common capability，并通过 optional signaling 以 finer granularity 表示相对于 common baseline 的差异。
- **proposal** 10.2.1 — RAN2 研究通过 UE capability message compression 降低 capability signaling overhead。
- **proposal** 10.2.1 — 6GR UE capability 设计应包含所有 UE 支持的 minimum baseline capability set，以及按 device type 区分的 mandatory capability sets。
- **proposal** 10.2.1 — 可使用 optional feature indicators，相对于 baseline device-type capability set 指示差异（“delta”）。
- **proposal** 10.2.1 — 支持基于 delta 和 reference profiles 的 module-based capability reporting and configuration procedures。

- **observation** 10.3.1 — NR 的 SDAP layer 需要投入 operational effort，以确保 handover 期间正确转发数据；发生 QoS flow remapping 时，也无法保证 in-order delivery。

- **observation** 10.3.1.0 — Real-time mobile AI traffic 的流量特征与 XR applications 的流量模型相似：具有周期性，但 burst size 高度可变，并有严格的时延要求。
- **observation** 10.3.1.0 — Non-real-time mobile AI traffic 与 legacy eMBB traffic 特征相似，同时具有非周期、突发、UL 负载较高等特点，并使用 HTTP 和 TCP/QUIC、短时连接更多。其 delay budget 灵活，但 latency 对用户体验至关重要。

- **observation** 10.3.1.0 — AI traffic 的传输特性包括突发和非周期流量模式、多模态数据类型、增强可靠性，以及严格的端到端时延和往返时延要求。

- **observation** 10.3.1.0 — 现有系统假设和业务模型主要以 UE 为中心，未能充分体现 multi-device AI services 的特征与需求。
