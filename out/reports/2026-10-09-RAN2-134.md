# RAN2 #134 增量简报

> 共 461 条事件 · [会议目录](https://www.3gpp.org/ftp/tsg_ran/WG2_RL2/TSGR2_134/)

## 6GR 能效（25 条）

- **observation** 9.3.3.3 — 指出静态 CDRX timer operations 会在四种情形导致不必要的 PDCCH monitoring：无数据活动、无后续传输、重传无效，以及不能支持单连接内多种业务或动态时延要求。
- **observation** 9.3.3.3 — 为适应 DL 和 UL traffic 的动态变化，可考虑采用 NW-initiated 或 UE-initiated solution 来实现 6G CDRX timer adaptation。
- **proposal** 9.3.3.3 — 提出为 connected mode 设计 single discontinuous monitoring framework：UE 在收到 DL WUS 或到达 periodic CDRX occasion 时，启动配置时长的 PDCCH monitoring。若 UE 在该时长内被 PDCCH 调度，则保持唤醒一段时间，并开始监测可能的 retransmission scheduling。
- **proposal** 9.3.3.3 — 定义一个同时适用于 DL WUS 和 CDRX 的 single timer；当 UE 被 PDCCH 调度时，该 timer 使其保持唤醒一段时间。
- **proposal** 9.3.3.3 — 当 UE 被 PDCCH 调度时，用于监测 retransmission scheduling 的 timer（例如 retransmission timer）也同时适用于 DL WUS 和 CDRX。
- **proposal** 9.3.3.3 — 对 C-DRX 与 DL WUS 配置组合的研究，假设 C-DRX 参数包括 DRX cycle、onDuration-like Timer x 和 inactivityTimer-like Timer y；WUS 参数包括 WUS cycle、PDCCH monitor Timer x 和 inactivityTimer Timer y。UE 未收到 WUS 时的行为、两类 cycle 是否相同，以及两类 timer 是否相同仍为 FFS。
- **proposal** 9.3.3.3 — single discontinuous monitoring framework 基于 C-DRX-like mechanism 设计；DL-WUS 被视为可选功能，并应与 C-DRX-like mechanism 配合工作。
- **proposal** 9.3.3.3 — 对于支持 DL-WUS 的 UE，网络可配置 DL-WUS 与 C-DRX cycle 对齐或不对齐，也可配置不使用 C-DRX cycle，供 PDCCH monitoring 使用。
- **proposal** 9.3.3.3 — 作为起点，UE C-DRX 可配置为依据 C-DRX onDuration timer、inactivity timer、HARQ RTT timer 和 HARQ retransmission timer 周期性监测 PDCCH。
- **proposal** 9.3.3.3 — 认为 5G C-DRX 的一个痛点是静态定时器操作导致不必要的 PDCCH 监测。CDRX 定时器值配置后保持固定，不随数据调度活动、后续传输、重传有效性或业务类型变化。
- **proposal** 9.3.3.3 — 支持在有或无 DL WUS 的 6G discontinuous PDCCH monitoring procedure 中动态调整 CDRX timer(s)，具体可调整的定时器及方案细节待研究。研究如何减少不必要的 PDCCH 监测，并考虑网络复杂度和信令开销等因素。
- **proposal** 9.3.3.3 — RAN2 应考虑配置多个 DRX patterns，以更好适配具有不同业务特征的 multi-flow 并提升 energy efficiency。
- **proposal** 9.3.3.3 — RAN2 应考虑支持快速 DRX pattern switching，以响应 traffic pattern 变化和动态 QoS requirements。
- **proposal** 9.3.3.3 — RAN2 研究如何减少 onDuration time 期间所有 serving cells 上不必要的 PDCCH 监测。
- **proposal** 9.3.3.3 — 考虑按 DRX group 或 serving cell 应用 DRX configuration。还提出研究基于 UE 活动、触发事件、service type 和近期调度活动的 UE-specific monitoring configurations，以及 connected mode DRX 的监测窗口、活动窗口切换和 UL/DL Inactivity Timers 等事项。
- **proposal** 9.3.3.3 — 对于 idle/inactive state，若网络在进入或离开 sleeping opportunities 时要改变小区中的 SSB/paging/SI/RACH configurations，采用隐式机制，例如依靠 SI update 或 layer 1 signaling。
- **proposal** 9.3.3.3 — 支持为 6G RRC_CONNECTED UEs 至少提供显式 NW TX/RX sleeping pattern。
- **proposal** 9.3.3.3 — 对于 6G 显式 NW TX/RX sleeping pattern 的信令，支持通过 RRC configuration 和 UE group common lower layer indication 进行动态激活/去激活。connected mode 的讨论包括网络睡眠期间静默的信号、UE 行为及显式与隐式机制所用信令等事项。
- **proposal** 9.3.3.3 — 若 6G 网络在 DL 睡眠，connected UEs 至少无需监测 DL semi-persistent scheduling，也无需监测新传输的 PDCCH。对于 non-connected UEs，提出两种选项：无需监测 common reference signal、paging 和 system information，或以稀疏周期监测这些内容。
- **proposal** 9.3.3.3 — 当 6G network 在 UL 休眠时，RAN2 考虑适用于所有 UE 状态的两种选项：不发送任何数据或信号；或除发起 Random Access procedure 外不发送任何数据或信号。
- **proposal** 9.3.3.3 — 为实现 energy efficiency 并协调 NES 与 UE power saving，可按 traffic 和 UE 维度考虑 resource management。
- **proposal** 9.3.3.3 — 支持根据 NW energy saving operation 调整 UE power saving configuration。
- **proposal** 9.3.3.3 — UE 调整 C-DRX cycle configuration，以与 active cell DTX/DRX configuration 对齐。
- **proposal** 9.3.3.3 — 对于 connected state，以 legacy time-domain periodic/fixed cell DTX/DRX pattern 为基线。RAN2 将进一步研究是否需要依据 network indications 动态控制 cell DTX/DRX，以兼顾 network energy saving 和 delay-sensitive traffic 的性能。
- **proposal** 9.3.3.3 — 研究在 RRC_CONNECTED mode 的 cell DTX non-active period 内，使用 DL WUS 触发 on-demand PDCCH monitoring。

## ISAC 通感一体（25 条）

- **agreement** 9.5 — 从 RAN2 角度，研究所有 modes 下由 UEs 和 TRPs 作为 TX 和/或 RX sensing entities（SEs）运行，并进一步研究由 SF/aNB 执行的 radio aspects/configuration/report 和 control aspects。还需研究 SE selection 的 criteria、参与节点及所需信息、aNB 与 SF 的协调，以及 moving target mobility 下的 sensing entity selection/re-selection 和 UE sensing entity 移动时的 service continuity；RRC states 视时间允许情况研究。
- **proposal** 9.5 — 已记录支持 UEs 和 TRPs 作为 Tx 和/或 Rx SEs 运行。
- **proposal** 9.5 — 按 sensing mode，UE 可作为 sensing signal transmitter 和/或 sensing signal receiver；sensing procedures 的研究分为 UE as sensing signal transmitter 与 UE as sensing signal receiver。
- **proposal** 9.5 — 提出 RAN2 按优先级研究 UE-involved sensing：先研究 UE as sensing Rx 的 DL sensing reference signals 测量，再研究 UE as sensing Tx 的 UL sensing reference signals 发送，随后研究 UE-to-UE sensing。另有意见认为初期不应优先区分 bi-static 与 mono-static sensing。
- **proposal** 9.5 — 提出 sensing protocol design 应服务于 sensing procedure，并研究 RAN 与 Sensing Function (SF) 各自所需功能及 SF 位于 CN 还是 RAN。另有提案认为 Sensing Function 是位于 Core Network 的 Network Function。
- **proposal** 9.5 — 提出 Sensing Function 控制 sensing service procedures，包括 Rx SE 的 reception/measurement configuration；serving aNB 控制 Tx UE SE 的 radio resource allocation。
- **proposal** 9.5 — 提出参与 sensing session 的 Rx 和 Tx Sensing Entities（UE 和/或 TRP）由 Sensing Function (SF) 选择和控制。讨论意见涉及 SF 与 aNB 的功能划分、实体选择和 sensing data processing 等，但未形成明确结论。
- **proposal** 9.5 — 提出讨论 UE ISAC capability reporting 是否可复用 unified 6G UE capability framework。原文仅列出讨论议题，未给出结论。
- **proposal** 9.5 — 提出 RAN2 可先基于 5G-Advanced 的成果识别基本 ISAC UE capabilities，例如 sensing modes 和 reporting levels，再结合正在进行的 6G 讨论进一步扩展。
- **proposal** 9.5 — 提出 RAN2 研究 UE sensing capability reporting procedures，使网络能够判断 UE 是否可参与 sensing-related procedures，同时避免将能力报告直接绑定到特定 sensing modes 或 service models。
- **proposal** 9.5 — 提出 UE capability reporting 时应向 SF 报告 higher-layer sensing capabilities（如 supported sensing modes、calculation capabilities）和 AS-layer sensing capabilities（如 RS-related capabilities）；并将 AS-layer sensing capabilities 作为 UE AS capability 的一部分报告给 RAN。
- **proposal** 9.5 — 提出 UE 经 Uu interface 向 serving aNB 发送 sensing capability；如有需要，SF 可经 aNB 或 AMF 获取 UE sensing capability。
- **proposal** 9.5 — RAN2 将研究 UE-SF 之间通过类似 LPP 的协议进行交互，以支持例如 sensing configuration signalling。
- **proposal** 9.5 — RAN2 将研究 UE-gNB 之间通过 RRC signalling 进行交互，以支持 RAN 根据动态无线条件动态调整 sensing configurations。该条目标注为 Noted。
- **proposal** 9.5 — RAN2 将研究通过 RRC signaling 或 higher-layer application protocols 配置、激活、修改、停用或释放 sensing configurations。该条目标注为 Noted。
- **proposal** 9.5 — 条目提出 sensing configuration 可由 SenF/RAN node 通过请求或非请求方式发送给 sensing UE，并可采用 broadcast signalling 或专用信令；该条目标注为 Noted。讨论涉及 sensing data 的消费者、协议及终止点，以及广播和专用传输等问题。
- **proposal** 9.5 — 条目提出 sensing configuration 由 aNB 提供，包括 sensing resources、sensing signals 的配置，以及 measurement data report 的内容和触发条件等配置。内容还列有 Measurement and reporting。
- **proposal** 9.5 — RAN2 将讨论 sensing measurement 使用 6G RRC measurement framework，还是设计类似 LPP 的 sensing measurement framework。
- **proposal** 9.5 — UE 将 sensing measurement data 发送至 aNB，且数据在 aNB 可见。aNB 如何处理这些数据，以及是否或如何将其转发至 SF，属于 RAN3 范围。
- **proposal** 9.5 — 关于 UE 向 RAN 报告 sensing measurement data 的方式，RAN2 应等待 RAN1 对 measurement data 内容的讨论。
- **proposal** 9.5 — 条目指出 sensing data 的大小取决于 sensing version 和报告的数据，latency 要求较宽松，终止点为 SF，数据消费者为 sensing service consumer（AF、UE 和 NF）。sensing report 通过 CP、UP 或 data plane（若定义）传输，取决于数据大小和 latency 要求。
- **proposal** 9.5 — 关于 service continuity，RAN2 将研究移动目标的 sensing continuity，以及移动 sensing UE 的 sensing continuity，并考虑 connected 和 idle/inactive UE。该条目标注为 Noted。
- **proposal** 9.5 — 支持通过 UE capability reporting procedures（包括 reactive response 和 proactive unsolicited procedures）进行 Sensing Entity (re)selection，以确保 Sensing Entities 或 sensing objects 移动期间的服务连续性。
- **proposal** 9.5 — RAN2 研究如何在 RRC_IDLE/INACTIVE（或其 6G 等效状态）中启用 ISAC procedures，且不预设最终的 6G RRC state model。
- **proposal** 9.5 — RAN2 假设参与 sensing procedures 的 UE 处于 RRC_CONNECTED；待其他 UE (sub)states 的定义及 sensing procedures 取得足够进展后，再研究这些状态。

## 6GR 非地面网络（14 条）

- **agreement** 9.6 — 针对 GNSS-free，研究非 UE-location-based mobility（包括 HO、cell selection/reselection 和 measurements）；对于 GNSS-degraded operation，等待 RAN1 进展。NTN 预计会有类似 5G 的 L2 timer 影响，待 RAN1 进一步进展后讨论，并涉及 multi-orbit operation。
- **observation** 9.6 — 对于 GNSS-free，优先采用 non UE-location-based solutions，因为这符合 6G 的 TN/NTN harmonization 目标。
- **observation** 9.6 — 在 NR-NTN 中，RACH 和 C-DRX 的关键 MAC timers 高度依赖基于 GNSS 的 RTT calculations。
- **proposal** 9.6 — 在 RAN plenary 就 NTN 中支持 RAT-dependent positioning 取得进一步进展前，RAN2 假设不具备 GNSS capability 的 UE 无法在 NTN 中获取其位置。
- **proposal** 9.6 — RAN2 等待 RAN1 关于 GNSS-degraded operation 的进展。
- **proposal** 9.6 — RAN2 研究 non-location-based mobility，以及 UE location 可在不依赖 GNSS 等 non-3GPP systems 的情况下确定的 location-based mobility solutions。
- **proposal** 9.6 — 对于 GNSS-less/degraded operations，6GR NTN 支持 time-based mobility 和 beam-level RSRP-based mobility 作为替代触发条件。
- **proposal** 9.6 — RAN2 将研究支持 6G NTN GNSS-independent RTT estimation 的机制；估计的 RTT 至少用于延后 RA 相关定时器的启动，并延长 C-DRX 相关定时器。讨论中提出计时器可纳入 work item 阶段，也提及可基于 DL 启动计时器；该议题记为 Noted。
- **proposal** 9.6 — 针对 multiorbit mobility 和 NTNTN mobility，将研究 QoS-based cell reselection，使 RRC IDLE mode UE 可优先驻留 GEO cell，并在 MT 或 MO data arrival 触发时根据 service requirements 选择接入小区。该议题记为 Noted。
- **proposal** 9.6 — 多轨道议题达成一致：在 TN session 继续讨论 multi-carrier idle mode，并将 multi-orbit 纳入讨论场景；至少研究 inter-frequency 场景下的 service-based reselection。还将结合 TN session 后续讨论，了解相较于 Option 1 的收益，以及特定 NTN 问题或顾虑。
- **proposal** 9.6 — 针对 intra-RAT 6G TN-NTN cell reselection，将至少考虑以下测量启动机制：TN 到 NTN 时，以 RRM-based S-measure 作为基线；NTN 到 TN 时，可考虑 UE 与 reference location 的距离或 serving NTN cell 的 serving time。
- **proposal** 9.6 — 针对 TN/NTN 与 NTN/NTN mobility，将研究 idle/inactive 和 connected 状态下 NTN 特定的 measurement relaxation/initiation trigger conditions，例如 S-measure、reference location 和 time。原文列出了 TN 到 NTN 与 NTN 到 TN 的 measurement report 条件。
- **proposal** 9.6 — 6G NTN 的 SMTC 和 measurement gap 设计将复用 5G NTN 的 multiple SMTC/MG、RRC IDLE UE-based SMTC adjustment，以及 RRC CONNECTED UE 的 PDD report。另将研究 beam-based SMTC configuration，以减少 signalling overhead 和 GNSS dependency。
- **proposal** 9.6 — 将研究基于 serving cell reference location 的方案，以在 6G NTN 测量定时中考虑不同卫星之间的 UE-aNB propagation delay difference。

## 6GR AI/ML 协议支持（12 条）

- **proposal** 9.3.3.2 — 对于 UE-sided model，network 需要知道传输对象是 model，但无需知道其内容或详细 meta info，以避免对其他 traffic 造成影响。Network 可以控制是否以及何时向 UE transfer/delivery 该 model。
- **proposal** 9.3.3.2 — 对于 one sided UE models，模型存储在 3GPP 之外时，model transfer 可对 3GPP 保持透明；存储在 3GPP 内时，网络应具备部分可见性（知晓 model 与 non model）以及 transfer controllability。
- **proposal** 9.3.3.2 — RAN2 将 transparent/OTT approach 作为 6G UE-side model transfer 的基线；其他基于 UP 的方案仍待研究。
- **proposal** 9.3.3.2 — RAN2 将研究 UE server 到 UE 的 model transfer 是否需要受 RAN2 影响的 network controllability mechanism，以及其功能。初步提出网络可允许或禁止 transfer procedure，并可停止、暂停或恢复该 procedure。
- **proposal** 9.3.3.2 — 就 UE-sided model transfer，RAN2 记录的共识是 MNO 应能知晓经 3GPP 进行的 model transfer，以便区分 user traffic 与 model transfer traffic，并可调整优先级；无需了解模型内容，也无意由 MNO 禁止 UE 进行 transfer。如何实现不在 RAN2 范围内，可能由 CN mechanisms（如 QoS、PDU session management）实现，并已批准向 SA2 发送 LS。
- **proposal** 9.3.3.2 — 对于 NW-sided models，沿用 5G-A 的做法：除 network-side data collection（例如用于 training）外，不规定其他 LCM functions，相关功能留给 network implementation。
- **proposal** 9.3.3.2 — RAN2 将考虑把 Rel-19 AI/ML PHY 定义的 common procedures（UE capabilities、applicability determination、inference、performance monitoring、data collection）作为 unified LCM framework 的基线。各 6G AI/ML use case 的详细 signaling messages 和 parameters 分别研究。
- **proposal** 9.3.3.2 — Functionality-based LCM 应作为 6G 的基线。
- **proposal** 9.3.3.2 — RAN2 将研究由 network 或 UE 发起的 LCM decision 方案。备选方式包括 network 决策（network-initiated 或 UE-initiated 并请求 network），以及 UE 决策（由 network 配置事件触发或 UE-autonomous，且 UE decision 会报告给 network）。
- **proposal** 9.3.3.2 — 研究低时延（fast, one signalling step）的 fallback mechanisms 可行性，以支持 AI/ML-enabled configuration 与 non-AI/ML-enabled configuration 之间的双向切换。
- **proposal** 9.3.3.2 — performance monitoring 的后续研究方向包括：NW-sided model 的 UE assisted performance monitoring，以及 UE-sided model 的五种场景，涵盖 NW 或 UE 执行监测、management decision 由 NW 或 UE 作出，以及 decision 是否发送至 NW 或用于 alignment。
- **proposal** 9.3.3.2 — 6GR applicability reporting 应避免 NW 在没有先验适用性信息时盲目配置 formal inference configuration，并支持向 NW 报告单个 inference configuration 的适用性变化。

## 6GR 数据与模型传输（23 条）

- **agreement** 9.3.3.1 — UE-side data collection 中，RAN 不解码或解释数据内容，但应了解传输数据的类型以支持 controllability 和 forwarding；standardized data 的 decodability 将在 CN 或 OAM，具体位置待定。拟于 August meeting 发送 LS，RAN awareness 的实现方案仍待研究。
- **proposal** 9.3.3.1 — RAN2 将明确 visibility 与 decodability 是不同概念：decodability 指解码并解释数据内容的能力，visibility 指判断收到的数据应如何处理的能力。
- **proposal** 9.3.3.1 — 条目提出 termination point 应具备 full visibility，以决定路由、处理或本地终止数据，并以此为基线研究至少适用于 AI/ML 的 standardized data collection framework。要求还涉及数据安全与隐私、MNO 对传输过程的控制、可扩展性，以及降低对 UE 和用户流量的影响；术语说明 full visibility 包含 decodability 和 controllability，并将在 MNO。
- **proposal** 9.3.3.1 — standardized UE-side data collection 指 UE 侧数据收集的数据类型/格式和数据传输过程均实现标准化。
- **proposal** 9.3.3.1 — 认为网络复用 UE 侧数据采集的数据进行网络侧模型训练是合理的。Qualcomm 提出，UE 实现可能导致数据粒度不同，并询问这是否限制 UE 能力。
- **proposal** 9.3.3.1 — 原文认为，若在 RAN 终止 UE 侧数据采集，基于 5G-A 用例中的标准化测量结果（如 L1/L3 measurement results 或 CSI channel information）不存在安全或隐私风险，也没有将这些数据在 CN 终止的必要或益处。会议记录同时指出，对所有用例是否可复用数据尚未达成结论，并提出了标准化与厂商特定数据范围及商业化价值方面的关注。
- **proposal** 9.3.3.1 — 提出标准化 AI/ML UE-side data collection 的终止点不在 RAN，终止点由 SA2 决定。Huawei 询问是否支持标准化和非标准化数据；Qualcomm 与 MediaTek 认为传输非标准化数据也很重要。
- **proposal** 9.3.3.1 — 决定向 SA2 和 SA5（抄送 RAN3、SA3）发送 LS，说明 RAN 不是 AI/ML UE-side data collection 的终止点，即 6G 不支持 UE 经 gNB、OAM 到 server 的 Option 3。关于非标准化数据，讨论涉及数据验证责任、数据类型可见性，以及标准化数据应可解码的意见。
- **proposal** 9.3.3.1 — 提出 UE-side data collection 的终止点可依数据是否供 RAN 使用而定：供 RAN 复用时由 RAN 终止并可查看数据，否则由 CN 终止且 RAN 不可查看；基线考虑 RAN 为终止点，涉及 CN 的情况需 RAN2 与 SA2 进一步协调。讨论中对单一采集方案、RAN 与 CN 终止点及数据复用等问题存在不同意见。
- **proposal** 9.3.3.1 — 提出 RAN 侧 decodability 可按用例配置；所有类型的采集数据都必须在 RAN 具备 identifiability，以便 MNO 控制高效数据传输。另提议向 RAN3 通报 RAN2 关于 SON、MDT 和 AI/ML 数据采集用例的数据消费者与终止点的讨论或协议。
- **proposal** 9.3.3.1 — UE 与 RAN 间数据传输优先考虑 non-IP 方案，理由是开销较低且不需要 IP routing。潜在方向包括增强型 CP 方案或新 data plane；原文认为 UP-based solution 不适用于 UE-RAN 数据传输。
- **proposal** 9.3.3.1 — UE 与 CN 间数据传输方面，RAN2 应聚焦由 SA2 架构进展触发的 Uu 传输协议，并区分用例特定的 UE-CN 高层协议与低层传输协议。传输协议候选包括 CP、UP 和 new plane；IP 或 non-IP 取决于 SA2 架构。
- **proposal** 9.3.3.1 — 提出 RAN2 不应采用基于 NR UP 和 NR CP 的数据传输框架，理由是这两种方案均存在已识别的根本性限制。
- **proposal** 9.3.3.1 — 提出 RAN2 应研究一种新型 radio bearer，支持可配置的 decodability、所有用例下 RAN 侧的 identifiability，以及 QoS differentiation。QoS differentiation 用于支持具有不同数据量和时延要求的数据传输。
- **proposal** 9.3.3.1 — RAN2 应研究支持新 radio bearer 所需的机制，例如 logical channels 和 scheduling framework。

## 6GR 通用设计与新业务（13 条）

- **observation** 9.2.2 — 256-bit AEAD algorithm 有三种 operating modes：Confidentiality（仅 ciphering）、Integrity 和 Combined。
- **observation** 9.2.2 — combined mode AEAD 使用同一把 cryptographic key 进行 integrity protection 和 ciphering，并可将两者合并为一次操作。编码端先执行 ciphering，再执行 integrity protection（Encryption-then-MAC）。
- **observation** 9.2.2 — 基于 5G NR 的 RRC configurations，BWP、CORESET 和 SearchSpace 的可能配置规模巨大。原文指出，在不了解专用 RRC configuration 的情况下，对 MAC CE 发起攻击会有较大挑战。
- **observation** 9.2.2 — RAN2 视角提供的技术事实和分析可支持 SA3 分析 MAC CEs 的 threat risks。原文提出仅保护 essential MAC CEs，以降低相应 processing overhead。
- **observation** 9.2.2 — All MAC CEs 的 threat range 被分类为适用于“group of UEs”。原文指出，SA3 如何作出该分类尚不清楚。
- **observation** 9.2.2 — 所有 uplink MAC CEs 本质上都来自 single UE，因为每个 UE 都发送自己的 UL-SCH MAC PDU。
- **observation** 9.2.2 — DL MAC CEs 包含在发往 C-RNTI 或 T-CRNTI 的 DL transmission 中，且这些 transmission 面向 single UE。MSG2/MSGB 虽面向 group of UEs，但不包含 MAC CEs。
- **proposal** 9.2.2 — RAN2 表示，只要 COUNT 和 MAC-I 保持 5G 的长度，AEAD 对 PDCP PDU format 就没有影响；其理解是 SDU 为 plaintext、整个 PDCP header 为 associated data，ciphering 作用于不含 MAC-I 的 data 部分，而 integrity protection 覆盖 PDCP header 和 data 部分。RAN2 向 SA3 提出有关 AEAD 模式、算法共存、输入配置、MAC-I 长度及处理顺序等澄清问题。
- **proposal** 9.2.2 — RAN2 反馈称，combined mode AEAD 采用单次调用和 Encryption-then-MAC 顺序，相较 5G 的 MAC-then-Encrypt 可在解密前进行完整性验证；并提出复用 5G-legacy 输入参数、将 PDCP Header 映射为 AAD、将 PDCP SDU 映射为 IBS/Plaintext。RAN2 倾向于将 6G AS-layer 的 MAC_BYTES 固定为 4 bytes，并就 Cipher-only/Integrity-only 配置和 48-bit EXTRA_IV 同步方式向 SA3 提问。
- **proposal** 9.2.2 — RAN2 向 SA3 说明 MAC CE 安全分析应考虑网络处理复杂度、MSG3 的开销限制，以及篡改、重放和利用标识符的威胁复杂度与恢复方式。原文举例指出，MSG3/MSGA 中不匹配预分配 C-RNTI 的内容会被基站忽略，且 C-RNTI 是可经 RRC reconfiguration 更新的临时标识。
- **proposal** 9.2.2 — RAN2 提议告知 SA3，UL 或 DL 中都不存在面向或来自 group of UEs 的 MAC CEs，并请 SA3 在适当时据此修订 threat range classification。原文说明该确认针对 5G。
- **proposal** 9.2.2 — RAN2 旨在仅支持 RRC_CONNECTED 状态下使用的 MAC CE 安全保护。初始接入及其他连接失败（如 RLF 和 HO failure）过程中的 MAC CE 不在范围内。
- **proposal** 9.2.2 — 从 RAN2 signaling 角度，支持可配置的 MAC CE security 是可行的，以确保部署灵活性。最终安全方案仍取决于 SA3 的决定。

- **proposal** 9.3.1.3.2 — RAN2 将研究 UE 如何指示已使用或未使用的 CG PUSCH resources，以提高 spectral efficiency。6G 不需要采用与 5G NR 相同格式的 UTO-UCI。
- **proposal** 9.3.1.3.2 — 为提高 resource efficiency，RAN2 将研究由 UE 发起 advance indication，通知 aNB 即将发生的 CG utilization。
- **proposal** 9.3.1.3.2 — 关于以 NR UTO-UCI 作为提升 resource efficiency 的基线，讨论中存在不同意见；记录指出 RAN2 不预期在这些方面提交贡献。已批准向 RAN1 发送 LS，要求其考虑 RAN2 协议，并研究支持 dynamic grant、configured grant、CG 资源立即激活、动态激活/去激活、资源分配动态调整及更高资源效率的 L1 scheduling。

## 6GR 移动性（29 条）

- **agreement** 9.4 — 除 CFRA baseline 外，RAN2 研究 UE 使用预配置 preamble 的 CBRA-based early UL synchronization 的可行性；支持 NW-triggered early UL synchronization，并进一步研究 UE-triggered 的潜在收益和可行性。NW-triggered baseline procedure 包括 source cell 向 UE 发命令、UE 向 target cell 发 RACH preamble、target cell 计算并传送 TA 给 source cell、source cell 将 TA 交付 UE，之后 UE 使用有效 TA 执行 RACH-less mobility；还考虑 network-triggered mobility 中 target cell initial access resources 在 cell switch command 前提供或随命令提供的两种情形。
- **observation** 9.4 — UE 处理时间（Tprocessing，RAN4 定义）主要取决于 UE 收到 HO command 后需要执行的实际操作。它与 HO 期间变更的 IE/参数数量或 HO command 的大小没有直接相关性。
- **observation** 9.4 — RAN2 认可，在某些痛点场景中，legacy handover mechanisms 可能有较高概率发生非预期事件。例如，快速 RSRP 下降时 measurement event 未能正确触发。
- **observation** 9.4 — UL-based mobility measurement 可在网络侧执行：UE 向潜在目标小区发送上行信号（如 PRACH preamble/SRS），目标小区再基于这些信号进行测量。
- **observation** 9.4 — 降低 interruption time 是 mobility 的 KPI 之一。因此，UL-based mobility 可与 candidate configurations、DL sync、UL signal transmission 和 RACH-less HO 等预配置技术集成。
- **observation** 9.4 — UL-based mobility 可减少访问目标小区的资源消耗：只有接受 UE 的候选小区才指示资源分配（如 CG、CB-PUSCH）。它也可改善上行服务质量，例如 uplink-heavy interactive AI applications。
- **proposal** 9.4 — 应用目标小区参数时的关键时延包括：Physical layer configuration 的 RF retuning 和 BWP switching，MAC configuration 的 MAC reset，RLC configuration 的 RLC entity re-establishment，以及 PDCP configuration 的 PDCP entity re-establishment 和 security update。
- **proposal** 9.4 — 不同 handover 场景中持续变化的配置范围不同：Intra-DU/Intra-CU 涉及 physical layer configuration；Inter-DU/Intra-CU 涉及 physical layer、MAC 和 RLC configuration；Inter-CU 还涉及 PDCP configuration 和 security。条目还提出请 RAN4 研究两类场景是否可定义更低的 interruption requirements：无 RF 和 baseband change configuration update 的同频 mobility，以及基于 multi-carrier configuration 的异频 mobility。
- **proposal** 9.4 — RAN2 应由 RAN4 为不同 HO 场景定义适当的 UE processing time（Tprocessing）要求，不应按 HO 期间配置变更的多少区分要求。会议同意向 RAN4 发 LS，说明已识别的无 RF 和 baseband configuration change 的同频 mobility 场景，并询问该场景是否可降低 UE processing delay。
- **proposal** 9.4 — RAN2 将研究一种 small-size HO command 方案，该命令仅包含源小区与目标小区之间发生变化的参数。该方案主要适用于 RF/BB-impacting parameters 不变的场景。
- **proposal** 9.4 — RAN2 将向 RAN4 发送 LS，询问对于 RF/BB-impacting parameters 不变的 HO 场景，能否定义更低的 RRC procedure delay（T_RRC）和 UE processing time（T_processing）要求。
- **proposal** 9.4 — RAN2 将研究减少 HO command 处理时间和数据中断的机制，包括 RF/BB 参数不变时使用 small-size HO command、在 target configuration 应用前继续与 source cell 通信，以及结合使用 pre-configuration 和 fast RRC processing。该议题先在线下会议讨论。
- **proposal** 9.4 — 支持 NW-triggered early UL synchronization；进一步研究 UE-triggered early UL synchronization 和 UE-based TA acquisition 的潜在收益与可行性。
- **proposal** 9.4 — 在采用 pre-configuration 的 mobility 中，source cell 可在 cell switch command 中指示 initial access 资源，例如 CFRA、CG 或用于 RACH-less 的 SR，前提是已与 target cell 协调。协调可在 cell switch 前进行，也可更早进行，由 source cell 决定。
- **proposal** 9.4 — 在采用 pre-configuration 的 mobility 中，source cell 与 target cell 协调 initial access 资源时，target cell 可为 UE 提供新配置，而不使用预存配置；source cell 可触发 normal L3 handover。
- **proposal** 9.4 — 为提高 6G mobility 的 resource reservation efficiency，可使用 shared resource pool 避免为 UE 预留专用资源，例如 contention based PUSCH transmission 或 shared CFRA/SR resource pool。
- **proposal** 9.4 — 为提高 6G mobility 的 resource reservation efficiency，采用 dynamic resource allocation/activation 以避免长期资源预留；例如基于 NW coordination 或 UE assistance info 分配/激活 CG、CFRA 或 SR 资源。该议题先在线下会议讨论。
- **proposal** 9.4 — 6G Early UL synchronization 的基线为 network-controlled：网络向 UE 发送命令，UE 向指示的 target cell 发送 RACH preamble，target cell 计算 TA 并发送给 source cell，再由 source cell 将 TA 交付 UE。获得有效 TA 后，UE 执行 RACH-less mobility procedure。
- **proposal** 9.4 — RAN2 将同时考虑 NW-triggered 和 UE-triggered early UL synchronization。
- **proposal** 9.4 — 对于 early UL sync，RAN2 将研究使用 CFRA resource 和 CBRA resource。
- **proposal** 9.4 — Early UL synchronization 将研究两种方向：对 RA-based early UL sync，通过优化 early measurement reporting 的 event configurations（例如 MR 的 event thresholds）减少不必要的同步；对 UE-based TA measurement，研究将其扩展到 asynchronous network 场景，包括向 UE 提供 source/target cell 的 reference timing difference 或可用于计算 target cell propagation delay 的 assistance information。另有提案考虑 UE 在 RRC_CONNECTED 且无数据期间基于预配置自行切换小区、不报告测量结果或通知网络，并在离开预配置 cell-list 时通知网络；该提案被 noted。
- **proposal** 9.4 — 为降低 RRC connected mode 下 delay-sensitive、bursty traffic 的功耗，研究两项彼此独立且不捆绑的功能：基于 DL/UL (LP)WUS 的 wake-up mechanism，以及以 CLTM/CHO-like pre-configuration 为基线的 UE-based mobility，并进一步研究 measurement relaxation 和 measurement reporting reduction。
- **proposal** 9.4 — UE 应在每次 cell switch 后通知 network，以便 network 维护 UE 的 cell-level location。这样可避免在所有 candidate cells 预留 UE-dedicated resources，以及向所有 candidate cells 发送 UE-dedicated WUS 所带来的 signaling overhead。
- **proposal** 9.4 — 针对 delay-sensitive、bursty traffic，UE 应在每次 cell change 后通知 network，以维护有效的 TA 和 beam，并确保 UE context 已准备好，从而快速恢复 data transmission。
- **proposal** 9.4 — 针对 RRC connected state 下与 mobility 和 connection management 相关的 UE power saving，重点研究降低 5G measurement 和 reporting overhead 的增强方案，包括 S-measure、dynamic measurement and report configuration Act/Deact、RLM/BFD relaxation，以及目前仅允许 RedCap 使用的 RRM relaxation。
- **proposal** 9.4 — 支持 network-triggered early DL sync，并以 5G 中由 source cell 触发 candidate cell 的 TCI-state activation 机制为基线；进一步研究 UE-triggered early DL sync 的可行性。对于无 pre-configuration 的 mobility，支持仅预配置 DL RS 和 candidate cell(s) 的 TCI-state configuration，以触发 early DL sync。
- **proposal** 9.4 — Early DL sync（TCI state activation）有益且可以支持；其可行性由 RAN1 负责。RAN2 角度关于简化方案的进一步讨论，可在 RAN1 取得更多进展后进行。
- **proposal** 9.4 — RAN2 将研究 mobility enhancements，以解决真实网络部署特定“pain point”场景中已知的 mobility issues，例如 ping-pongs、unnecessary HOs 和 RLFs；场景示例包括 TR 38.914 定义的 urban grid scenario。
- **proposal** 9.4 — RAN2 应研究 connected mode UE 的 UL-based mobility，以减少 UE 执行 DL measurements 和 reporting 的负担及功耗，并降低访问 target cells 的资源消耗：仅接受 UE 的 candidate cell 提供资源分配指示，例如 CG、CB-PUSCH。该研究还旨在改善 uplink-heavy interactive AI applications 等场景的 UL service quality。

## 6GR 寻呼（6 条）

- **agreement** 9.3.2.4 — UE 在每个 UE paging cycle 监测一个 paging occasion。6G PF/PO design 目标是使用一个 PF/PO distribution formula，同时支持 clustered 和 uniform PF/PO；下一次会议将整理 paging formula 的 requirements 及需解决的 shortcoming/limitations，详细公式设计留待 WI phase。
- **agreement** 9.3.2.4 — 原文提出 paging cluster 可包含一个或多个 PF/PO，并支持 cluster 内 PO 间隔、每个 paging frame 配置多个 paging occasions，以及每个 UE paging DRX cycle 配置一个或多个 paging clusters。6G paging 应支持 idle 和 inactive UE 的 paging、向至少处于 RRC Idle/Inactive 的 UE 通知 system information change 与 ETWS/CMAS，并使 paging capacity（包括 paging records）至少达到 5G 水平；同时提出研究基于 UE paging-related capabilities 分配 paging occasions。
- **observation** 9.3.2.4 — Paging cluster 内的 paging occasions 需要更密集排列。相比 NR Rel-19，每个 paging cluster 应包含更多 POs。
- **proposal** 9.3.2.4 — 提出 6G 的 PF/PO bundling 应支持所有 paging DRX cycle lengths，而不局限于特定周期，并允许更小的 N（如 T/64、T/128、T/256）。会议记录了对 signaling overhead、最低周期以及配置延迟的不同意见，结论为 Noted。
- **proposal** 9.3.2.4 — RAN2 的目标是确保在单个 PF 内增加 POs 时，PO configurations 的 signaling overhead 不会显著增加。Nokia 和 Apple 认为该问题应予考虑，但指出其处于 stage 3；结论为 Noted。
- **proposal** 9.3.2.4 — 提出支持在单个 DRX cycle 内配置一个或多个 paging clusters。每个 cluster 包含一个或多个 Paging Possibility；结论为 Noted。

## 6GR QoS/QoE 与服务感知（51 条）

- **agreement** 9.3.1.2 — RAN2 研究在 QoS profile 不变或变化时，基于预配置范围/值动态调整 L2 参数；QoS profile 变化时需要与 SA2 协调。待讨论的事项包括适用于动态调整的功能、UE 切换条件与行为，以及 DRB 内的粒度和启用建模方式。
- **agreement** 9.3.1.2 — 可向 scheduler 报告的数据突发信息包括 AS buffer 中已有数据、尚未进入 AS buffer 的当前数据，以及尚未生成的预期数据的突发大小。突发时间信息可包含首个数据包预计可供传输的时间；如何向网络发送这些信息仍待研究。
- **observation** 9.3.1.2 — 对于 Scenarios 2 和 3，QoS adaptation 需要在 user plane 按 per-PDU 或 per-burst 时间尺度发生。基于 control plane 的 reconfiguration 至少慢一个数量级。
- **observation** 9.3.1.2 — 基于 user plane 的 QoS indication 可让 transmitter 按 per-PDU 从一组预配置 QoS profiles 中选择，以支持全部三个已同意的 dynamic QoS scenarios，同时保留 QoS flow baseline。
- **observation** 9.3.1.2 — 通过 higher-layer signaling 频繁进行 QoS reconfiguration 可能增加时延和信令开销，从而限制对快速 traffic 或 channel 变化的响应能力。
- **observation** 9.3.1.2 — Traffic characteristics（例如 burstiness、latency sensitivity）和 application requirements 的变化时间尺度可能短于典型 RRC reconfiguration procedures。
- **observation** 9.3.1.2 — 6GR 维持 target QoS 的能力会受到动态变化的 radio 和 network conditions 影响，例如 load、interference 和 mobility。
- **observation** 9.3.1.2 — 在没有针对 dynamic QoS handling 的进一步增强时，1:1 和 N:1 “mapping to RBs” 不足以或至少效率不高，无法处理 6G 中动态变化的 QoS requirements。
- **observation** 9.3.1.2 — 尚未进入 Layer-2 buffer 的突发信息可用于 scheduling；无论突发是预测的，还是已存在于 higher-layer buffer 但尚未完全可供传输（例如由于 congestion control）均适用。
- **observation** 9.3.1.2 — UE 通常更适合估计 downlink burst 的到达时间和大小，这有助于网络实现更多 UE power savings。
- **observation** 9.3.1.2 — 在 AI glass、car、high-speed train、UAM、FWA 等场景中，service 可能并非由 UE 发起或终止，而是由通过 non-3GPP link（如 WiFi 和 BT）连接到 UE、并与 DN 通信的 tethered device 发起或终止。
- **observation** 9.3.1.2 — 系留设备经历的 QoS 取决于该设备与 Data Network 之间的端到端路径。
- **observation** 9.3.1.2 — 5G PIN 的 non-3GPP delay 方案无法充分利用数据包在 non-3GPP link 上经历的动态变化时延，也无法及时适配。
- **observation** 9.3.1.2 — E2E reliability 由 non-3GPP link PER 和 3GPP link PER 共同决定。RAN/CN 需要获知 non-3GPP link PER，以便适当设置 3GPP link PER；5G PIN 不支持这一点。
- **observation** 9.3.1.2 — 在当前 5GS QoS framework 中，RAN/UE 不具备对 PDU Set 内 AL-FEC structure 的 awareness，这会导致显著的 resource inefficiency。
- **observation** 9.3.1.2 — 提出在 RAN 中支持可配置的 AL-FEC，以满足 application layer 的要求；原文指出这有助于缓解拥塞并降低时延。
- **observation** 9.3.1.2 — 原文指出，接收端不同 SDF 间的 HOL blocking 最常见于 default QoS flow（即 default DRB），原因是运营商网络未部署 AF 时 CN 无法获取 packet filter。
- **observation** 9.3.1.2 — 对于 Default QoS flow，一个 SDF 可以代表一个应用的流量；原文指出，保持 SDF 内的 in-order delivery 至关重要。
- **observation** 9.3.1.2 — 原文指出，RX 可能难以判断收到的 packet 是否可在不等待 reordering timer 的情况下交付给 upper layer，因为这可能需要新的 signalling。
- **proposal** 9.3.1.2 — 提出从 RAN2 角度考虑 dynamic QoS 的方面：QoS Profiles 和 L2 Parameters 的选择与动态调整、多个 QoS flow-to-DRB mappings 及 L2 parameters 的配置流程和粒度，以及 RAN 与 UE 间的动态切换方案。
- **proposal** 9.3.1.2 — 提出研究动态调整多个 QoS profiles 或选择 L2 parameter sets 的责任归属，并逐项讨论 L2 parameters 的适配方式，以及修改后哪些需要 RAN 与 UE 配置对齐、哪些可单边更新。ATT 认为 QoS switching 在 CN 侧，研究应聚焦 L2 parameters switching。
- **proposal** 9.3.1.2 — 提出 RAN2 研究基于预配置 L2 parameter sets 或 ranges 的 dynamic QoS adaptation。
- **proposal** 9.3.1.2 — 提出研究基于 user-plane 的 dynamic QoS adaptation：通过 RRC 预配置 QoS attribute profiles，在 user-plane header 中携带 per-PDU 或 per-PDU-set QoS attribute indication，且该指示独立于 QFI。
- **proposal** 9.3.1.2 — 提出研究基于 user-plane 的 dynamic QoS adaptation 的 UL 方面，包括 UE 如何确定 UL 的 per-PDU QoS attribute，以及是否需要 BSR enhancement 来支持更细粒度调度。
- **proposal** 9.3.1.2 — 6GR 支持 QoS parameter ranging，并通过动态网络控制适用配置，以实现快速且低开销的 QoS 调整。
- **proposal** 9.3.1.2 — 6GR 支持 UE 在网络配置的范围内或依据适用条件自主选择 QoS 参数，以改善时延和响应性。讨论提出需明确网络配置范围、L2 参数类别及自主选择条件，并平衡 UE 自主性与网络控制。
- **proposal** 9.3.1.2 — RAN2 应评估面向 Mobile AI traffic 的 dynamic QoS 机制，同时考察 QoS 性能与 RAN efficiency，包括 spectral efficiency、signaling overhead 和 UE power consumption。讨论区分了 QoS profile 变更与仅调整 L2 parameters 的场景，并涉及 UE 自主决策及 CN 通知。
- **proposal** 9.3.1.2 — 提出支持一个 QoS flow 映射到多个 DRB（1:N mapping），并支持 per PDU 或 per PDU set level 的 RAN handling granularity。相关观察指出，多 DRB 映射可能导致上层重排序；对于频繁 IP 地址变化场景，RAN2 应等待 SA2 进展，仅在 SA2 要求时进行 AS 增强。
- **proposal** 9.3.1.2 — 提出不倾向于 1:N QoS flow to DRB mapping，并向 SA2 发送 LS 说明 RAN2 的偏好。
- **proposal** 9.3.1.2 — RAN2 应考虑支持 dynamic 1:N DRB to LCHs mapping，以处理同一 QoS flow 内的可变 QoS。讨论还提出需进一步确认 1:N DRB、1:N LCH 和 per PDU 动态处理等方式。
- **proposal** 9.3.1.2 — aNB 和 UE 的 QoS treatment granularity 定为 PDU set level，PDU level 为特殊情况。RAN2 应考虑四种 dynamic QoS adaptation 选项：在多个 LCH 间选择、切换预配置 QoS profiles、在预配置范围内动态调整参数，或将 QoS flow 映射到多个 DRB 并选择 DRB。
- **proposal** 9.3.1.2 — RAN2 应使 RAN 能够获知 burst time information，包括 burst arrival time 和/或 inter-arrival time，以及 burst delay budget。
- **proposal** 9.3.1.2 — 提出支持 UE 报告两类 uplink burst：应用尚未生成但预计稍后到达的 burst，以及应用已发送但尚未完全可供传输的 burst（例如因 congestion control）。
- **proposal** 9.3.1.2 — UE 可报告任一类型的 uplink burst，并至少提供其 Expected arrival time（time window），即 burst 可供初始传输的时间。Application-layer burst size 和关联的 Logical channel 为可选信息。
- **proposal** 9.3.1.2 — 提出 UE 可报告 downlink burst 及其 expected arrival time。讨论认为该机制面向 interactive scenario，并提及 UE 可能基于 application layer 信息进行预测。
- **proposal** 9.3.1.2 — RAN2 确认 burst information 包括 burst size 和 time information，UE 侧 UL traffic awareness 由 UE implementation 实现。Burst information 可由 UE 经 MAC CE 和 UAI 上报至 aNB。
- **proposal** 9.3.1.2 — RAN2 应考虑 UE 向 RAN 暴露 QoS-related、QoE-related、E2E latency-related 和 transport layer-related information。提案指出，用于 RAN service differentiation 的 service characteristics and properties 应具有 QoS differentiation 意义、可由 UE 检测，并由网络通过 network-configured rules 控制；提议讨论 relative service priority、traffic characteristics 和 application/service requirements。
- **proposal** 9.3.1.2 — RAN2 同意研究支持 service characteristics differentiation，以改善 E2E user experience。
- **proposal** 9.3.1.2 — 支持 service characteristics differentiation 以改善 E2E user experience 时，应考虑 tethering case。
- **proposal** 9.3.1.2 — 对于 tethering case，E2E user experience 应考虑 tethered device 与 Data Network 之间的 end to end path。
- **proposal** 9.3.1.2 — 为确保 tethered device 与 DN 之间的 E2E user experience，至少需要考虑 latency 和 reliability。
- **proposal** 9.3.1.2 — 为确保 tethering case 的 E2E latency，RAN2 同意研究在 AN PDB 中补偿 non-3GPP delay（tethered device 与 UE 之间的 delay）的 service awareness solutions。RAN2 已就此决定向 SA2 发送 LS。
- **proposal** 9.3.1.2 — Dynamic QoS framework 应能够应对 tethering link 随机 jitter 导致的单个 traffic flow 中 effective PDB 变化。
- **proposal** 9.3.1.2 — RAN2 将研究引入 AL-FEC aware L2 protocol stack，并研究相应增强，以根据 application-layer reconstruction requirements 对 source 和 repair packets 进行 differentiated handling。
- **proposal** 9.3.1.2 — 若 RAN2 同意研究 AL-FEC awareness mechanisms，研究应聚焦于达到 reconstruction targets 后主动丢弃冗余 PDUs，以及通过将同一 AL-FEC frame 的 packets 映射到不相关 radio resources 的 cross-PDU multiplexing strategies，以增强 transmission diversity。
- **proposal** 9.3.1.2 — 研究支持对 AL-FEC 相关数据包进行差异化处理，并向 SA4 发送 LS，澄清 AL-FEC 相关信息（如组信息、恢复阈值及源/冗余指示）能否配置给 UE 并在 AS 层可用。
- **proposal** 9.3.1.2 — RAN2 研究从 CN 和 UE 向 RAN 提供 AL-FEC 相关信息，并研究 UL 和 scheduler 支持 DL 与 UL 中 AL-FEC 所需的内容；必要时可通过 LS 征询 SA4 意见。
- **proposal** 9.3.1.2 — 为解决 default DRB 的 PDCP 接收端 HOL blocking，RAN2 考虑设置额外的 default DRB，即支持 default QoS flow 到 default DRB 的 1:N 映射。
- **proposal** 9.3.1.2 — 由 UE 实现决定将 default QoS flow 映射到多个 default DRB。
- **proposal** 9.3.1.2 — RAN2 研究 UE 是否可在 aNB 配置的最大数量范围内动态建立或释放多个 default DRB。材料指出，HOL blocking 可通过将服务映射到不同 QoS flow 并配置 out-of-order delivery 来避免，并提出在需要时研究由运营商控制的 selective out-of-order delivery。
- **proposal** 9.3.1.2 — RAN2 研究 HOL blocking 的三种方案：QoS flow 与 DRB 采用 1:1 映射；由发送端指示接收端是否直接向上层交付 SDU；或由接收端引入短于 t-Reordering 的定时器，在定时器到期时交付连续缓存的 SDU且不更新重排序窗口。

## 6GR 频谱聚合（42 条）

- **agreement** 9.3.2.5 — RAN2 需研究 FR1+FR2 非共址场景中最高 10ms backhaul delay 对 CA 和 DC 的协议、接口、性能以及 UP/CP 的影响，并评估可满足的需求和简化 DC 的可行性。工作分为阶段一影响分析和阶段二协议层评估及方案比较，期限为 Long。
- **observation** 9.3.2.5 — 在 5G CA 中，UL CC 数量不得超过 DL CC 数量的限制，使系统难以适应不同的 UL/DL 流量负载，尤其是 UL 流量较重时。
- **observation** 9.3.2.5 — 在 5G CA 的某些情况下，例如将 serving SCell 切换为 PCell，执行 HO 会造成不必要的中断和 signaling overhead。
- **observation** 9.3.2.5 — 在 5G CA 中，即使 SCell 仍可用，PCell RLF 也会导致 RRC re-establishment。由此会造成不必要的中断和 signaling overhead。
- **observation** 9.3.2.5 — 在 NR 中，各频段的 duplex mode（TDD 或 FDD）及 uplink/downlink directions 被严格规定。SUL 严重依赖已定义的 SUL carriers，且 NR CA 不支持 UL-only SCell。
- **observation** 9.3.2.5 — 对于 backhaul latency 较高（例如 10ms）的部署，single scheduler operation 在 HARQ、CSI 和 ARQ 运行方面存在显著问题。该方式也不适用于 inter-vendor deployment。
- **observation** 9.3.2.5 — 节点未共址但 backhaul latency 不大时，central scheduler 可通过提前若干 slots 管理时延，使通常的 co-located CA operation 可运行。何时根据 backhaul delay 使用 single 或 dual scheduler 可由 NW implementation 决定。
- **observation** 9.3.2.5 — 10ms backhaul latency 会因 HARQ RTT 增加而显著提高 L2/HARQ memory buffer 的需求。
- **observation** 9.3.2.5 — 10ms backhaul latency 会使 centralized scheduling decisions 效率显著降低，因为 BSR、CQI、PHR 等关键状态信息到达 central MAC entity 时已过时。
- **observation** 9.3.2.5 — 在 10ms backhaul 下依赖 single scheduler，会严重降低时延敏感 MAC procedures 的性能，包括 SCell activation/deactivation 和 MAC CE transmissions。
- **observation** 9.3.2.5 — 对于低 backhaul latency（例如 2ms）的非共址部署，single-scheduler Carrier Aggregation architecture 可能可行；对于最高 10ms 的时延则可能不可行。
- **observation** 9.3.2.5 — 在具有较大 backhaul delay 的 dual/independent scheduler 场景中，转发至 FR2 cell 的 user data 应至少位于 MAC layer 之上。
- **observation** 9.3.2.5 — 若多个 NW schedulers 控制同一 UE 不同 cells 的调度，它们需要紧密协调；否则会增加 UE HARQ requirements，并对 HARQ/ARQ 和 RLC performance（如 (re)segmentation）产生负面影响。
- **observation** 9.3.2.5 — 在 4G/5G CA 中，不同 DL transmission points 间的 backhaul latency 假定为 ideal，即微秒量级。对于涉及多个 eNB/gNB/DU 向同一 UE 传输的 non-ideal backhaul，使用 DC。
- **observation** 9.3.2.5 — NR CA 已支持用于 non-collocation scenarios 的 PUCCH SCell 和 sTAG。该支持可应用于采用 non-ideal backhaul 的 non-collocated CA。
- **observation** 9.3.2.5 — 在 NR non-collocated CA 中，BSR、PHR、RACH 和 SCell activation 等 time-critical MAC functionalities 可能因 backhaul delay 而性能下降。
- **observation** 9.3.2.5 — 为 non-collocated CA 配置多个 PUCCH cell groups 和多个 TAGs 时，MAC entity 仍是单一逻辑实体，RLC 和 PDCP 层对底层 CC 拓扑透明。因此，co-located 与 non-collocated CA 的 UP handling 保持一致。
- **observation** 9.3.2.5 — 6G UP 中，RAN2 正在研究采用 unified SN 的 UP architecture，以及基于 HARQ feedback 的 L2 ARQ handling。尽管该研究中部分已同意的设计假设可能影响 non-collocated CA operation，RAN2 应避免为其定义相较于 6G SA 的独立 UP architecture。
- **observation** 9.3.2.5 — 在 5G-like DC 中，flow control 和 separate RLC buffers 相较于理想 CA throughput 会导致至少约 20% 的 throughput reduction。
- **observation** 9.3.2.5 — 采用 10ms 时，non-collocated CA performance 仍属合理，并且优于 single carrier performance。
- **observation** 9.3.2.5 — Table-2 对比了采用 dual PUCCH group 的 CA 与 DC operation：CA 在 configuration/control operation 方面效率更高，但 deployment 和 operational flexibility 较低。
- **observation** 9.3.2.5 — CA 的功能效率会受到 single RLC 和 MAC functionality 的影响，原因包括 backhaul 带来的 L2 ARQ traversal delay，以及某些 MAC runtime operation 相关参数的传递延迟。若 UL 限制为 one leg（non-split bearer operation），尤其选用无需 BH traversal 的 leg，CA operation 会优于 DC。
- **observation** 9.3.2.5 — 每个 FR1 cell 支持的 FR2 cells 数量限制了可与每个 FR2 cell 聚合的 FR1 spectrum 数量，从而限制 FR1-FR2 spectrum aggregation 的收益。
- **observation** 9.3.2.5 — 通过 FR1 与 FR2 aNBs 之间 10ms non-ideal backhaul 聚合 FR1 和 FR2 spectrum，会影响整体 performance。额外的 packet re-ordering delay 会影响 achievable throughput 和 latency。
- **observation** 9.3.2.5 — 聚合 FR1 和 FR2 上不对称的 data rates 可能进一步降低 TCP performance，整体表现也可能低于仅使用 FR2。
- **proposal** 9.3.2.5 — RAN2 将在研究 CONNECTED mode 下的 multi-carrier operations 时考虑 5G CA 的若干不足：PCell 与 SCell 的配置和操作分离、PCell RLF 后无法 recovery、PCell/SCell role change 困难、SCell（及 CA）激活或添加较慢，以及载波组合（UL/DL）静态。材料还指出，PCell change 会触发 HO，PCell RLF 会触发 RRC re-establishment，造成不必要的中断和 signalling overhead；PCell re-establishment 会丢弃所有 SCells。
- **proposal** 9.3.2.5 — 工作列表列出 6G PCarrier/PCell 与 SCarrier/SCell 各自拟支持的功能，包括初始接入、移动性、随机接入、PUCCH、RLM 等；功能清单仍在讨论中。还提出功能不应隐式绑定主辅小区，而应通过专用信令显式配置到各载波/小区。
- **proposal** 9.3.2.5 — 提出研究通过向 SCell 报告 PCell failure 来实现无需 RRC re-establishment 的 PCell failure recovery，并研究基于 PCell 与 SCell(s) 上 RLM 的 Radio Link Failure。6G 可研究除 RLF detection 和 RRC re-establishment 外的额外恢复触发与 UE 动作。
- **proposal** 9.3.2.5 — 提出考虑灵活的 UL/DL carrier decoupling，以补充上行覆盖并适应 UE 流量特征；信令设计需考虑该需求，并研究快速载波/小区添加、修改、激活和去激活方案。
- **proposal** 9.3.2.5 — 对于 aNB 实现可隐藏 inter-node backhaul delay ‘X’、使 UE 侧 CA 操作透明的情况，RAN2 假设 6G SA UE 无额外要求；是否研究 ‘X’ 的取值仍待定。
- **proposal** 9.3.2.5 — 非共址场景的 single scheduler 方案中，MAC/PHY 间分拆因两者紧耦合而难以实现，PHY 内分拆则因需传输量化 I/Q 频域样本而对回传带宽要求高。模拟 RF 信号透明转发的时延通常为微秒级且无需类似 NTN 的方案，但其功能限制较大，尤其在 FR2。
- **proposal** 9.3.2.5 — 提出降低非共址场景下 single scheduler 方案的研究优先级。
- **proposal** 9.3.2.5 — 对于非共址 FR1-FR2 部署场景，提出仅研究支持上下行 FR1 与 FR2 频段聚合、且站点间回传时延最高 10 ms 的频谱聚合方案。
- **proposal** 9.3.2.5 — 6G 协议设计应支持多厂商 FR1-FR2 非共址部署。
- **proposal** 9.3.2.5 — 提出将 NR-DC 作为评估非共址 FR1-FR2 场景下 6G-6G 频谱聚合方案的基线。
- **proposal** 9.3.2.5 — 提出将 5G CA framework 作为基线，用于理想/共址回传的仅 intra-aNB 6G-6G FR1-FR2 聚合，且 UE 侧 MAC/RLC 操作透明。另确认 DC 可用于非理想回传下的 intra-aNB 与 inter-aNB 部署。
- **proposal** 9.3.2.5 — RAN2 将在 6G-6G spectrum aggregation 中采用简化的 Dual Connectivity，同时保留 Dual Connectivity framework。
- **proposal** 9.3.2.5 — RAN2 将研究增强的 CA framework，其中各 distributed scheduler 独立处理 time-critical MAC functionalities，例如 BSR、PHR、RACH 和 SCell activation。
- **proposal** 9.3.2.5 — 条目提出，RAN2 将得出结论：即使存在 10ms BH latency，non-collocated CA performance 仍合理。讨论中指出 FR1-FR1 范围及仿真假设仍需考察。
- **proposal** 9.3.2.5 — CA 方案优选采用两个 PUCCH groups，且 uplink 使用 non-split bearer，并将 PUSCH 发往不受 backhaul delay 影响的节点。DC 方案优选相较 5G NR DC 简化：无 SRB3、采用 SN-based mobility 和 single security context，并支持 dynamic leg-switching。
- **proposal** 9.3.2.5 — 若 FR1-FR2 spectrum aggregation 确有需要，即使 single MAC entity 内有 separate schedulers，仍可使用 CA。RAN2 认为规范化 single MAC entity 内的 coordination 有挑战且不理想。
- **proposal** 9.3.2.5 — 提出将通过 enhanced mobility procedures 在 FR1 与 FR2 间快速切换，作为利用 6G 非共址部署的方式之一，尤其考虑 inter-vendor 场景，细节待研究。讨论涉及 CA 在不同 backhaul latency 下的适用性、性能与部署限制，以及与单载波 FR2 的比较。

## 6GR 初始接入与系统信息（10 条）

- **agreement** 9.3.2.3 — 研究按每条 SI message 配置 SI-window width，并在方案研究中考虑 UE impacts、避免频繁 SI updates。还将研究显式或隐式的 window start positions，及其与每条 SI window width 和 UE calculations 的配合。
- **observation** 9.3.2.3 — 原文指出，flexible SI scheduling 带来的 UEPS 收益有限，因为现有 scheduling mechanism 运作良好，且 UE 只需在相对较长的周期内接收一次 SIBs。

- **proposal** 9.3.2.3 — RAN2 将研究结合 explicit window start positions（per SI message configurable position）与基于 scheduling list 顺序的 implicit window start positions。原文指出，每个 SI window 仅支持 SI window granularity offset 可能增加 common signalling 总发送时长；结合该 offset 与适用于所有 SI windows 的 SFN 或 slot granularity offset 可使首个 SI window 紧接 SIB1 或其他 common signals 开始，并减少开销。
- **proposal** 9.3.2.3 — RAN2 将研究在 per-SI-window、SI window granularity start position 之外，为所有 SI windows 配置 SFN 或 slot granularity start position，以便将 SI transmission 与其他 common broadcast signalling 聚集。关于 per-SI-message SI-window width 的讨论意见不一，原文未给出结论。

- **proposal** 9.3.2.3 — RAN2 将进一步研究解决未广播 SI message 预留 SI window 问题的三种方案：有 SI 未广播时将 SI windows 前移、将 on-demand SI 的 SI windows 配置在 SI transmission period 末尾，以及在 SI request 后提供 dynamically allocated windows 的 SI scheduling information。
- **proposal** 9.3.2.3 — Paging DCI 包含指示哪些 SIB(s) 已修改或更新的 SI-modification information，使 UE 仅在更新的 SIB(s) 与其相关时获取信息。原文还提出进一步讨论同一 SI window 内多个 SI messages 的 TDM 方案（通过 PDCCH 动态指示下一条传输）和 FDM 方案（在载波带宽不同部分传输）。
- **proposal** 9.3.2.3 — RAN2 应将 SI scheduling study 拆分为两个目标：优先建立 extensible、unified SI scheduling baseline framework，并考虑 R17 configurable starting position；另一个目标是研究更短时间内接收 SI 的机制，并重新评估 power-saving gains、相关影响及与其他 NES features（如 OD-SIB）的比较。

## 6GR UE 能力框架（36 条）

- **agreement** 9.2.1 — UE capability change message 在 RRC connected mode 发送给 network，并预期在 mobility 时转发给 target aNB；UE 进入 Idle/Inactive 后如何处理以及是否存储最新信息仍待讨论。下次会议前鼓励各公司线下形成对流程的整体看法，且只预期 co-sourced contributions。
- **observation** 9.2.1 — 网络实现或 operational policies 可能不处理其未考虑的 use cases 的 capability change requests，也可能不处理 capability change 影响不显著的请求。
- **observation** 9.2.1 — 收到 UE capability change indication 后，network 可影响 UE 对 problematic situation 的响应；若未收到 indication，network 只能面对 UE 自主恢复行为带来的影响。
- **observation** 9.2.1 — 与 capability updates 相关的 network KPIs 有害影响，主要来自 network 未能或无法更新配置时被迫依赖 autonomous solutions 的 UE。
- **observation** 9.2.1 — 发生 capability change 时，UE 已有必须解决的问题，network 此时无法阻止问题发生，只能选择不予理会。
- **observation** 9.2.1 — capability update 若报告整个 capability container，会阻止 network 执行 delta configuration，并需要 full configuration，造成 service interruption，违背在 RRC_CONNECTED 引入 capability update 的目的。
- **observation** 9.2.1 — 报告完整的 capability container 来进行能力更新会引入不必要的大量信令开销，并降低资源效率，从而打消运营商部署该功能的意愿。
- **observation** 9.2.1 — Proposal 2提出：UE在能力变更请求发送后启动的定时器到期时执行能力变更，并评估最新的 L12 setting 和 RRC (re)configuration 是否满足请求。若不满足，UE应用 default/SIB1 configuration，并在该事件发生时向网络报告。
- **observation** 9.2.1 — RAN2无需进一步讨论 RACS ID（即 CN based ID，与 5G 相同，定义为表示完整 UE capabilities 的 ID）；其协调挑战和网络维护负担（存储问题）明显，后续讨论交由 SA2。
- **observation** 9.2.1 — 在 5G 中，UE capabilities 采用紧密耦合、深层嵌套的结构（如 per-band 和 per-band-combination capabilities），限制了通用 capability information 的复用，并导致不同频段和组合重复传送相同值。
- **proposal** 9.2.1 — 允许在未事先进行 network reconfiguration 时报告能力更新的机制，仅适用于独立于网络实现且对性能有显著影响的用例。
- **proposal** 9.2.1 — UE因 overheating 和/或 power saving 时，允许在没有事先 network configuration 的情况下报告能力更新。该提案被记为 Noted。
- **proposal** 9.2.1 — 进一步讨论 UE 更新网络不支持的 capability field 的可能性，目的是了解如何避免此类问题。
- **proposal** 9.2.1 — 需确认：若由网络控制 UE 是否可调用 capability update mechanism，发生问题且更新未获允许时，UE 将必然在没有任何指示的情况下应用 autonomous fallback mechanisms。
- **proposal** 9.2.1 — 提案允许 UE 在所有用例中无需事先网络许可即可指示能力更新，相关参数（如 timers）的网络配置可另行讨论；提案被记为 Noted。讨论指出更新频率需谨慎考虑，不同用例不应一概而论，且网络响应、UE 实现及能力变化原因也受到关注。
- **proposal** 9.2.1 — 提议将 UE 在 connected mode 下进行 dynamic UE capability change 时报告完整 UE radio capability 作为 baseline solution；该提案被记为 Noted。
- **proposal** 9.2.1 — 提议 dynamic capability reporting 允许 UE 针对不同情形报告不同能力，且每种情形仅报告关键参数而非完整能力集合。power saving 和 overheating 情形保留 envelope capability reporting mechanism；该提案被记为 Noted。
- **proposal** 9.2.1 — RAN2 同意，动态 UE capability reporting 仅考虑相关的 UE capabilities。
- **proposal** 9.2.1 — RAN2 将进一步研究不同 capability container，以及采用 delta signaling 的相同 capability container，并依据 signaling overhead 和 future extensibility 进行评估。
- **proposal** 9.2.1 — 各 use case 的标准将定义可更新的 capability parameters。6G capability update study 将复用 5G 中定义的参数。
- **proposal** 9.2.1 — 为指明变更的 capability information 以支持网络执行 delta reconfiguration，并降低 capability update 的 signaling overhead，仅报告已变更的 capability parameters。讨论意见涉及参数范围、container、使用场景及连接状态等方面。
- **proposal** 9.2.1 — aNB 收到 capability update request 后，应向 UE 发送 RRC reconfiguration message 或包含 reject cause 的 reject message。
- **proposal** 9.2.1 — 网络响应消息不提供网络拒绝 capability update 的选项。
- **proposal** 9.2.1 — supervisory timer 规定 UE 可预期收到 capability update 网络响应的时间；timer 是否由网络配置仍需进一步讨论。

## 6GR 用户面架构（53 条）

- **agreement** 9.3.1.1 — 分别设置 PDCP 和 RLC 时，PDCP 至少承担安全、按序交付、头压缩、重复检测和重传，RLC 至少承担分段与重组、重复检测和 ARQ；合并层至少承担前述 PDCP 功能，分段与重组方式仍待研究。RAN2 旨在针对 RAN plenary 确定的所有支持场景和架构采用共同协议栈，部署选项不应影响协议栈；Single SN 的开销、处理、分离承载 DC、控制 PDU 分段及 CU-DU split 相关事项仍有待研究或决定。
- **agreement** 9.3.1.1 — 记录 5G PDCP 重排序机制在 DL 峰值吞吐时导致接收端内存需求高、延迟，并缺乏适应 QoE 的能力这一不足。研究简单的重排序机制以解决该问题。
- **agreement** 9.3.1.1 — 与 NR 相同，重传有两种触发：RLC retransmission 用于处理 Uu 数据丢失，PDCP reestablishment/recovery；SDU 和 SDU-segment 都需要支持重传。共同的 L2 retransmission function 仅在采用 single SN 时可行，具体方案及 CU-DU split 下的窗口操作、不同终止点时的共同状态报告仍待讨论。
- **observation** 9.3.1.1 — 原文认为 UDC 是具成本效益且成熟的特性，符合 6G 核心需求，包括 IMS service（含 TN/NTN）支持、UE 节能和上行覆盖增强。UDC 是 6G Day‑1 部署的必要特性。
- **observation** 9.3.1.1 — NR 的 PDCP reordering framework 可能导致接收端 PDU 的重排序延迟不确定，延迟范围可在一个至两个 reordering timer 周期之间变化。
- **observation** 9.3.1.1 — 5G PDCP reordering 机制在 DL 峰值吞吐量下会导致较高的 Rx 内存需求，且无法适应 QoE。
- **observation** 9.3.1.1 — 原文指出，切换期间若将 L2 retransmission 集成到 RLC，需要 DU 与 CU-UP 之间复杂且紧密的交互，并预计会出现许多问题；若全部集成到 PDCP，则可能没有问题。
- **observation** 9.3.1.1 — 原文认为，带有 HARQ failure indication 的 Fast ARQ 不能证明将 L2 retransmission 集成到 RLC 是合理的。
- **observation** 9.3.1.1 — PDCP retransmissions 与 RLC ARQ 的触发条件和目的不同。
- **observation** 9.3.1.1 — 若 6GR 中 PDCP layer 与 RLC layer 合并为单一层，则自然支持一份 status report。
- **observation** 9.3.1.1 — 若 6GR 中 PDCP layer 与 RLC layer 保持分离，可进一步研究是否以及如何统一两份 status reports。
- **observation** 9.3.1.1 — 原文指出，NR 基于 timer 或 feedback 的 data discarding 可能不足以满足 6G 多样化服务需求，并提出考虑 per-QoS flow discarding、基于 QoE 的 discarding、queue/congestion-based discarding，以及由 RAN 控制、UE 修改或选择配置参数的适配机制。另列出既有拥塞管理机制及观点：R19 UL rate control 可及时直接地支持应用层调节速率；L4S 和 SA2 congestion information exposure 存在应用对拥塞指示理解不同的问题。
- **observation** 9.3.1.1 — 原文指出，当前 UE 和 NW 已支持 L3 Congestion management 的 ECN marking。
- **observation** 9.3.1.1 — 原文指出，Congestion management 是 per-flow 操作；由于中间路由器与流的源/目的端之间没有其他控制信令，它在 IP layer 的 header 中实现，并指出 RAN 的情况不同。
- **observation** 9.3.1.1 — 原文指出，legacy AM 和 UM 面向差异明显的服务，且在 window operation、PDU header format 等方面完全不同。目前尚未识别出统一 RLC transmission mode 的明确收益和动机。
- **proposal** 9.3.1.1 — 提出将 UDC 作为 6G compression framework 的一部分进行研究，并研究其在 6G protocol stack 中的支持方式，要求涵盖 IMS services（包括 TN/NTN）、改善 UE power saving 和增强 uplink coverage。原文还指出 SCHC 可作为 6G PDCP layer 中 ROHC 的补充，适用于 ROHC 不适合的特定 IoT traffic patterns。
- **proposal** 9.3.1.1 — RAN2 将 SCHC 作为 PDCP compression mechanism 候选，并研究在 6G Study 中支持 SCHC 对 RAN2 的影响；相关提案认为 SCHC、ROHC、UDC 和 EHC 互为补充，建议纳入 6G SI 研究。讨论记录了对 UDC 处理开销、加密数据支持、SCHC 与 ROHC 关系等问题的意见，并记载下次会议聚焦 UDC、ROHC 相对 5G 的不足。
- **proposal** 9.3.1.1 — RAN2 研究如何消除同一 PDU 多个 reordering timer 实例造成的过度 reordering delay。记录的讨论涉及 TCP、RTP、当前配置下是否存在问题，以及识别可乱序交付数据包的方式。
- **proposal** 9.3.1.1 — RAN2 考虑增强 reordering，包括结合 in-order delivery 与 out-of-order delivery，以及增强 PDCP reordering procedure。
- **proposal** 9.3.1.1 — RAN2 将研究增强 6G 中的 PDCP reordering，以适配 application QoE、降低高 DL throughput 下的内存使用，并支持同一 DRB 中具有不同 reordering requirements 的多个 flows（如可行）。讨论涉及 HOL、FARQ、DL 扩展、乱序交付及高接收内存问题，尚未给出解决方案。
- **proposal** 9.3.1.1 — 决定不支持 unified L2 retransmission。PDCP 与 RLC retransmissions 保持分离。
- **proposal** 9.3.1.1 — AM DRB 仅支持用于 PDCP 和 RLC retransmission 的 RLC status report。
- **proposal** 9.3.1.1 — 提出将所有 L2 retransmission mechanisms 集成到 PDCP，以实现 common L2 retransmission functionality。
- **proposal** 9.3.1.1 — 6GR 中，PDCP retransmissions 与 RLC ARQ 是分离的 procedures。
- **proposal** 9.3.1.1 — 6GR 支持 unified L2 status report。
- **proposal** 9.3.1.1 — 建议将 R19 引入的 UL rate control mechanism 作为 AS 侧 congestion control 的基线，并研究 6G DL rate control。还建议询问 SA2 是否支持 6G 中的 L4S。
- **proposal** 9.3.1.1 — RAN2 聚焦于不引入 per-packet overhead 的 congestion management 方案，并可进一步研究用于指示 flow congestion 的 control signaling 及其性能收益。另有提案研究 6G RLC 的 AM 和 UM common framework，可在配置时基于 FARQ 或 polled RLC status reporting 触发 retransmissions。
- **proposal** 9.3.1.1 — Legacy AM 和 UM 可作为 6G data transfer modes 的基线。可按具体情况研究对 AM 或 UM 的进一步增强。
- **proposal** 9.3.1.1 — RAN2 研究一种 single non-transparent RLC mode，以支持不同的 retransmission 和 feedback behaviour。
- **agreement** 9.3.1.4 — 研究中无需专门处理 RLC/PDCP control PDUs 的 HOL blocking；应从 RX 和 TX 两个角度研究其他 HOL blocking 问题。若为 upper layer data 设计解决方案，可将其应用于 PDCP/RLC control PDUs，并需考虑 QoS framework，由 RAN2 评估是否还需其他措施。
- **observation** 9.3.1.4 — 在 5G NR 机制中，单个 CB 或 CBG 不被视为可靠；未经 TB CRC verification 成功，不能独立交付给 MAC layer。
- **observation** 9.3.1.4 — 允许通过 CB-level CRC verification 的 CB/CBG 交付给 MAC，可部分解决 PHY layer HOL blocking；位于错误 CB/CBG 之前的 CB/CBG 将不再被阻塞。
- **observation** 9.3.1.4 — 从 RAN2 角度，要完全解决 PHY layer HOL blocking，MAC 需要识别每个交付的 CB/CBG 中 MAC subPDUs 的边界。
- **observation** 9.3.1.4 — TB-level CRC verification 是否可以移除或忽略，以及 CBG 是否会在 6G 中保留，需要与 RAN1 确认。
- **observation** 9.3.1.4 — 当前 5G NR 准备和转发 MAC subPDUs 的方式不支持提前转发 control 或 data subPDUs。在相关 CB 已正确解码的 HARQ 重传场景中，这会导致显著时延。
- **observation** 9.3.1.4 — 提前转发 MAC CEs 和/或其他 control messages 与 PDCP HOL blocking issue 无关。
- **observation** 9.3.1.4 — ARQ 仅对 AM mode PDUs 有益，因此 FARQ 应仅应用于 AM mode PDUs。
- **observation** 9.3.1.4 — FARQ 可能使 TB 中包含的部分 MAC CEs 受益，但并非所有 MAC CEs 都需要此机制。部分 MAC CE 内容在重传前可能需要重构。
- **observation** 9.3.1.4 — Type 3（RLC Tx 侧 PDCP data PDU 阻塞 PDCP control PDU 的 Intra-DRB HOL blocking）在 5G 中并非问题，因为 UE 实现始终可以优先发送 PDCP control PDU。6G 中是否存在该问题，可根据 single SN 讨论进一步确认。
- **observation** 9.3.1.4 — 大多数 Type 4（RLC Tx 侧 PDCP data PDU 阻塞 PDCP control PDU 的 Inter-DRB HOL blocking）可通过适当的 NW configuration 处理。需要 RAN2 关注的特殊情况是 MAC LCP procedure 中 Bj<0，导致 PDCP/RLC control information 无法发送。
- **observation** 9.3.1.4 — Type 4 HOL blocking issue 可能无需解决，因为高优先级 LCH 的 L2 control/data PDU 应始终优先于低优先级 LCH 的 L2 data/control PDU。
- **proposal** 9.3.1.4 — 已记录向 RAN1 发送 LS，询问是否有必要且可行：无论 TB CRC verification 结果如何，将成功解码的 CB 或 CBG 交付给 MAC layer。
- **proposal** 9.3.1.4 — 已记录向 RAN1 发送 LS 以澄清 lower layer HOL blocking issue，并询问能否将通过 CB-level CRC verification 的已成功解码 CB/CBG 交付给 MAC layer。
- **proposal** 9.3.1.4 — 需研究提前转发对 MAC CEs、Other control messages 和 User Data 等不同 payload types 的收益。还需研究此类转发应对所有 TB 始终启用（“always on”），还是仅在认为有益时对部分 TB 启用（“opportunistic”）。
- **proposal** 9.3.1.4 — 讨论了基于 MAC PDU preparation 的 early forwarding，要求不影响 TB-to-CB splitting 或其他 RAN1 定义的 PHY mechanisms；其收益、适用场景、可解析且可信的数据单位及方案仍需研究。还记录了 UL HARQ process status 对 RLC UM 的潜在益处，包括避免不必要的资源浪费，以及尽早发送 MAC CE 和 RLC control PDU。
- **proposal** 9.3.1.4 — 提出 HARQ status indication 可应用于 RLC UM。
- **proposal** 9.3.1.4 — 提出收到 UL HARQ process status 的 NACK 时，若对应 MAC PDU 包含 MAC CE 和 RLC control PDU，则 MAC entity 重新触发 MAC CE，RLC entity 重新触发 RLC control PDU。
- **proposal** 9.3.1.4 — 提出 fast ARQ 仅适用于 MAC PDU 中 AM mode 的 MAC SDUs；TB 中 MAC CEs 的处理仍待研究，并留给 stage 3。
- **proposal** 9.3.1.4 — 提出收到 FARQ NACK indication 后，来自配置了其他约束（例如 delay budgets）的 AM-like bearers 的 uplink HARQ buffer 数据，只有在满足这些约束时才考虑重传。
- **proposal** 9.3.1.4 — 提出 FARQ 重传候选数据不适用特定优先级规则，LCP 定义的规则除外。
- **proposal** 9.3.1.4 — RAN2 观察到，Type 3 Intra-DRB HOL Blocking 可完全由 UE implementation 处理，且 5G 中没有该类型在现场造成问题的实例。RAN2 将研究 Type 4 Inter-DRB HOL Blocking：当 LCP 长时间导致 Bj<0 时，PDCP 和 RLC control PDUs 的阻塞可能造成该 DRB 停滞和吞吐量下降。
- **proposal** 9.3.1.4 — 提出降低对 higher layer 的 Type 4 HOL blocking 问题研究优先级。
- **proposal** 9.3.1.4 — 提出 RAN2 研究将控制相关信令（包括 TCP/UDP feedback 和 PDCP/RLC control PDUs）映射到专用 radio bearer 和 LCH，以缓解 HOL blocking。讨论中对 UE implementation 是否能处理相关问题、是否应遵循 LCP，以及是否需要允许加速控制数据包存在不同意见。

## 6GR RRC（49 条）

- **observation** 9.3.2.1 — 指出 “inactive” state 与 RRC idle state 在以下方面有根本区别：AS context storage、适用区域内 RRC resume/setup 的 UE identification、AS security requirement，以及 data transfer requirement。
- **observation** 9.3.2.1 — 从“inactive”状态和 RRC idle state 转至 RRC connected state，应执行不同流程；从 RRC connected state 转至“inactive”状态和 RRC idle state，也应执行不同流程。
- **observation** 9.3.2.1 — 低频流量且高时延容忍度的 IoT cases 明确适合 inactive operation。
- **observation** 9.3.2.1 — 部分 agentic AI background traffic 可能适合 inactive operation，但此类活动未来的流量模式尚不明确。
- **observation** 9.3.2.1 — 面向人类用户的 Generative AI traffic 不太可能适合 inactive operation。
- **observation** 9.3.2.1 — Smartphone/eMBB/FWA foreground traffic 不适合 inactive operation。
- **observation** 9.3.2.1 — 部分 Smartphone/eMBB/FWA background traffic 可能适合 inactive operation，但很多情况下流量密度和时延敏感性可能与 inactive 不兼容。
- **observation** 9.3.2.1 — Wearables、trackers 等设备可能从 inactive operation 获益；它们通常需要短 DRX，但在 active 时可能只有少量数据交换。
- **observation** 9.3.2.1 — SDT 与 state transition 的能耗差异集中在 RRC signalling 和 link adaptation：前者在 state transition 中存在，在 SDT 中不存在。
- **observation** 9.3.2.1 — 对于“Inactive” state，可通过基于 UE 和 network 两端存储的 UE AS context 的 resume-like procedure，实现满足 CP latency requirement 的快速状态转换。
- **observation** 9.3.2.1 — NR 中 SDT 受数据量、DL RSRP、后续传输盲调度效率或可靠性、专用 RACH/CG 资源、TA 有效性及小区重选期间连续性等限制。Proposal 1a 提出以从“Inactive”经 resume-like procedure 快速转至 RRC connected 作为快速开始数据传输的基线；Proposal 1b 提议 RAN2 研究是否需支持“Inactive”状态下的数据传输，并考虑突发流量的数据量、到达规律及设备移动性。
- **observation** 9.3.2.1 — 网络无法确定 UE 将在 paging area 内何时何地恢复连接，因此向处于 “Inactive” state 的 UE 提供 candidate cells 预配置会很困难，并会大幅降低 resource efficiency。
- **observation** 9.3.2.1 — LTE 在 baseline RRC_IDLE state 上定义了 “IDLE with suspend” 子状态：UE 的 CN-RAN connection suspended，以支持需要时快速恢复；UE AS context 保存在网络和 UE。该状态还支持通过 EDT/PUR 传输 unicast data/signaling。
- **observation** 9.3.2.1 — 在 6G 使用 single CN-triggered paging mechanism 和 single paging area 时，Idle 与 “Inactive” state 的差异可能包括 CN-RAN connection 是否保持 established 或 suspended（由 RAN3/SA2 讨论）、UE AS context 是否存储于网络和 UE。差异还可能包括是否能通过 SDT 在不进行 state transition 的情况下传输 unicast data/signaling（若引入 SDT）。
- **observation** 9.3.2.1 — RRC connection release 是严格由网络主导的过程，state transition 的最终决定权完全由网络掌握。
- **observation** 9.3.2.1 — DataInactivityTimer 可触发自主转换到 RRC_IDLE state，但随后 NAS recovery 会触发返回 RRC_CONNECTED state。
- **observation** 9.3.2.1 — 现有 NR UAI mechanism 在实践中无法保证及时 state transition，因为网络完全控制是否允许 reporting，并决定是否响应（power saving）或何时响应（MUSIM）。
- **observation** 9.3.2.1 — 对 proprietary workarounds（例如 local RRC connection release）的依赖，体现了 6G 通过引入 standardized UE-initiated RRC connection release procedure 解决当前限制的机会。原文称这是基于前一节讨论提出的方案。
- **proposal** 9.3.2.1 — 提议 RAN2 澄清：UE 处于 “inactive” state 时，paging 是用于触达 UE 以接收 incoming DL data/signaling 的 signaling。Nokia 询问 paging 指 paging concept 还是 RRC signaling；Samsung 认为 idle 或 inactive 可使用相同的 paging RRC message。
- **proposal** 9.3.2.1 — 提议 UE 在 “inactive” state 下的 mobility 与 idle state 相同，即基于 cell (re)selection framework，例如 best cell principle、cell ranking 和 inter-freq/RAT prioritization。其进展可沿用 mobility topic 中的 cell (re)selection 工作。
- **proposal** 9.3.2.1 — 提议仅使用 RRC signaling 来启动从 “inactive” state 到 RRC connected state 的 state transition。Fraunhaufer 认为应研究 random access 等其他机制。
- **proposal** 9.3.2.1 — 提出为 6G 定义独立的 RRC inactive state。该状态下 UE-based mobility 与 idle state 相同，采用 cell (re)selection framework。
- **proposal** 9.3.2.1 — 提出 inactive state 支持 MT 和 MO 两种情形的 small data transmission（SDT）。
- **proposal** 9.3.2.1 — inactive state 下的 SDT 无需网络在邻区为 UE 预留专用无线资源。MT 和 MO 情形在 SDT 前均无需专用资源配置信令。
- **proposal** 9.3.2.1 — 提出研究 inactive state 下 SDT 的灵活时长与突发大小、能效，以及 SDT 期间由 UE 控制的 mobility。
- **proposal** 9.3.2.1 — 提出将 inactive operation 主要用于 IoT traffic，也考虑 wearable、tracker，以及可能的 AI traffic patterns。
- **proposal** 9.3.2.1 — SDT 的规范化以证明其相较于转入 RRC_CONNECTED 能节能为条件，适用情形为不频繁的小流量突发。
- **proposal** 9.3.2.1 — 提出继续研究 SDT 流程及 RRC 状态转换信令的能耗，以判断是否值得规范 SDT；评估需覆盖能效、signaling overhead、mobility、coverage 和 maximum TBS size。inactive state 的协议要点包括沿用 idle 的 paging model 和 cell (re)selection mobility，并以 RRC-based mechanism 作为 UE 发起转入 RRC connected 的基线。
- **proposal** 9.3.2.1 — 提出 inactive state 可支持 UE-based mobility，且无需预配置 candidate cells。
- **proposal** 9.3.2.1 — 提出在 6G 采用单一 CN-triggered paging 时，可考虑将 Inactive 建模为 IDLE 的子状态，即“IDLE with suspend”。
- **proposal** 9.3.2.1 — 提出研究 6G 标准化的 UE-initiated RRC connection release procedure。
- **proposal** 9.3.2.1 — 研究 UE-initiated/request RRC connection release，了解其痛点和适用用例，并关注功能及对 UE 和 NW 的可能影响。
- **agreement** 9.3.2.2 — RAN2 不推进 UE 在 6G 中应用部分 (re)configuration 的规范方案，并研究通过跳过部分操作来简化 (re)configuration failure handling、减少 UE service interruption；具体跳过操作及所用 RRC procedure 尚待讨论。
- **agreement** 9.3.2.2 — 研究 stored configurations 的使用，至少涵盖 INACTIVE 到 CONNECTED 的转换、UE 处于 CONNECTED 时的 reconfiguration，以及 UE 留在同一小区的情况；暂不考虑 UE 在 IDLE 时使用 stored configuration。
- **observation** 9.3.2.2 — 仅依靠在 RRC reestablishment procedure（legacy 或 simplified）期间报告失败配置，无法从 UE 角度达到 service interruption avoidance 的设计目标。
- **observation** 9.3.2.2 — 商用网络中，能力和服务类型相似的 UE 收到的 RRC configuration parameters 经常相同或近似，因此网络会在 initial access、不同小区间及频繁的 UE-dedicated reconfigurations 中重复发送相同参数集。
- **observation** 9.3.2.2 — 通过 reference、default 或 stored configurations 框架代替显式发送完整参数列表，可显著降低 initial configurations、state transitions 和重复 reconfigurations 的 RRC signaling overhead 与 latency。
- **observation** 9.3.2.2 — 仅使用 delta configuration 在不同 profile（如 eMBB、XR、RedCap）的典型配置间切换，可能无法实现信令效率。
- **proposal** 9.3.2.2 — RAN2 考虑多种 reconfiguration failure information 报告方式，包括报告错误配置所在的 RRC module、参数索引、RRCReconfiguration 消息中的 bit-stream 位置，或包含错误参数及其值的 RRC container。
- **proposal** 9.3.2.2 — RAN2 讨论并筛选 UE 报告 partial reconfiguration failure 的方案，包括单一标志、未能应用的字段或字段组 ID、收到与已应用配置的 delta，或已应用的完整配置。讨论提出以较细粒度报告失败配置，并在 ASN.1/RRC 结构更明确后研究可行方式。
- **proposal** 9.3.2.2 — RAN2 研究简化的 (re)configuration failure handling procedure，通过跳过部分操作（例如 cell search、security key derivation）来减少 UE service interruption；具体跳过哪些操作尚待讨论。
- **proposal** 9.3.2.2 — RAN2 继续讨论简化流程是否基于“RRC Re-establishment”流程（RACH+CCCH）或其他 RRC 流程。Nokia、Vivo、Apple 和 Oppo 对相关流程的复杂性或中断机会表达了关注，议题记为 Noted。
- **proposal** 9.3.2.2 — RAN2 确认，6GR 的 (re)configuration failure handling 研究应尽可能避免 UE service interruption。
- **proposal** 9.3.2.2 — RAN2 继续研究如何在 6GR 的 (re)configuration failure 时避免 UE service interruption 并支持 UE 报告 erroneous/inapplicable configurations，候选方案包括 partial (re)configuration success，以及 UE fallback 后报告失败配置。方案中包含继续使用当前配置、采用 NW 配置的 fallback/default configuration，或在特定情况下触发 RRC re-establishment。
- **proposal** 9.3.2.2 — CMCC 的 5G NR real network test statistics 显示，由 reconfiguration failure 导致 re-establishment 的概率约小于 0.0004。原文提出 6GR 设计应优先考虑 state machine consistency 和 robustness，而不是引入过多 UE autonomous partial application 复杂度。
- **proposal** 9.3.2.2 — RAN2 应考虑在 6GR 中不支持 UE autonomous partial application of RRC configuration，因为它会导致不可接受的 cross-layer state mismatches 和巨大的规范复杂度。
- **proposal** 9.3.2.2 — RAN2 可确认，当 UE 只能应用部分 critical RRC reconfiguration 时，RRC connection re-establishment 仍是触发的基线流程。另有提案建议至少支持 full configuration fallback，并进一步讨论是否支持 partial configuration。
- **proposal** 9.3.2.2 — RAN2 将研究一种配置方法：网络通过指示 Identifier (ID) 或 Index 引用已知的 baseline parameters 集合，而不发送完整配置。
- **proposal** 9.3.2.2 — RAN2 支持研究相对于指示的 reference 或 stored configuration 进行 delta signaling，使网络能在同一消息中激活特定 baseline parameters 并只发送相应参数修改。讨论还涉及 UE 如何获得 stored configuration、处理时间与 signaling 或 latency 收益，以及目标使用场景。
