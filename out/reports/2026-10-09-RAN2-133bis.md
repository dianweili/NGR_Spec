# RAN2 #133bis 增量简报

> 共 459 条事件 · [会议目录](https://www.3gpp.org/ftp/tsg_ran/WG2_RL2/TSGR2_133bis/)

## 6GR 能效（17 条）

- **agreement** 9.3.3.3 — 下次会议基于这些基线步骤继续研究共同点，以及如何启用相关功能，以定义单一 discontinuous monitoring framework。下次会议公司应重点对这项工作的建模；两个方案的细节仍待研究，包括 PDCCH monitoring 定时器、监测周期及其是否相同或对齐。
- **observation** 9.3.3.3 — DLWUS Option 1-2 可独立于 C-DRX 配置其周期，并实现类似 C-DRX 的周期性 PDCCH monitoring 功能。
- **observation** 9.3.3.3 — DLWUS option 1-1 可指示 UE 是否需要为下一个 CDRX period 唤醒，其 power saving gain 优于 DCP。
- **proposal** 9.3.3.3 — 采用不带 DL-WUS 的 C-DRX 作为基线 UE power saving solution。RAN2 将聚焦于理解网络配置不带 DL-WUS 的 C-DRX-like mechanism 在 6G 中的形态。
- **proposal** 9.3.3.3 — 对于 DL WUS 与 C-DRX 结合的方案，支持研究 option 1-1 和 option 1-2。
- **proposal** 9.3.3.3 — RAN2 将研究带有 dynamic wake-up mechanism 的 C-DRX。是否引入 DCP 或 DL-WUS，应在 DL-WUS 设计细节确定并由 RAN1 讨论评估后再论证。
- **proposal** 9.3.3.3 — 提出为 6G 研究并定义单一 discontinuous monitoring framework，明确 unified DL WUS 与 C-DRX 的交互，覆盖三种基线工作模式。基线行为包括 UE 周期性监测 DL WUS 或 PDCCH；收到面向该 UE 的 DL WUS 后，启动一段时间的 PDCCH monitoring，未收到或非面向该 UE 时可回到休眠，C-DRX 下则监测 PDCCH 并在相应条件下休眠或保持唤醒。
- **proposal** 9.3.3.3 — DL WUS 不带 C-DRX 时，其操作可类似 LP-WUS operation 的 Option 1-2，同时移除 C-DRX cycle。相关提案为 DL-WUS 按自身周期监测，并可指示启动 active timer，在此期间 UE 监测 PDCCH。
- **proposal** 9.3.3.3 — 是否支持不带 C-DRX 的 DL-WUS，应考虑不同工作组的规范工作量以及 RAN1 在 signalling design 上的进展。
- **proposal** 9.3.3.3 — RAN2 优先研究“C-DRX without DL WUS”和“DL WUS together with C-DRX”，除非由 RAN1 触发，否则推迟研究“DL WUS without C-DRX”。Rel-19 LP-WUS option 1-2 类似方案应纳入“DL WUS together with C-DRX”方向研究。
- **proposal** 9.3.3.3 — 6GR Cell DTX/DRX机制将包含Active Duration概念，定义UE接收下行信号、获得已调度上行资源并发送上行信号的时段。
- **proposal** 9.3.3.3 — 6GR Cell DTX/DRX机制将采用基于周期的框架，在Active Duration与non-Active Duration之间交替运行，类似NR。
- **proposal** 9.3.3.3 — 为支持网络休眠机会并避免UE与网络不同步，原文提出RRC_CONNECTED UE需要获知时域cell DTX/DRX pattern及可能的动态触发，以确定可用UL/DL信号和资源。讨论中也提出研究implicit与explicit机制及相应UE行为，尚未形成机制结论。
- **proposal** 9.3.3.3 — RAN2将研究与UE discontinuous monitoring framework及DL WUS协同设计的Cell DTX。
- **proposal** 9.3.3.3 — RAN2将研究用于网络与UE联合节能的clustered UL/DL data transmission。提案还提出在connected mode灵活配置对齐的DL和UL传输时机，可按UE配置，也可跨UE或UE组配置。
- **proposal** 9.3.3.3 — RAN2将研究UE DRX与网络休眠机会（例如Cell DTX/DRX）之间的高效对齐机制。该条目标记为Not treated。
- **proposal** 9.3.3.3 — 原文提出在6G考虑多种DRX配置，以适配不同流量特征的multi-flow并提升能效；另有提案主张采用单一DRX配置。相关提案意见并存，未给出一致结论。

## ISAC 通感一体（25 条）

- **agreement** 9.5 — RAN2 可假设存在 sensing function，并研究支持 sensing functionalities/procedures 所需内容；sensing function 的位置由其他 WGs 决定，研究可考虑相关功能和程序的逻辑位置。至少研究 UE capability reporting、sensing configuration/reporting、data/control signaling transport，以及 Sensing Entity Selection（含 re-selection）等方面；该条目记为 Not treated。
- **observation** 9.5 — 已同意 6GR 的 ISAC 至少支持被动对象的 detection 和/或 tracking 用例，至少包括 UAVs、human、vehicles 和 AGVs，并支持 communication assistance。
- **observation** 9.5 — 不同 sensing modes 和 interaction assumptions 对 RAN2 的影响不同，尤其是在引入 UE involvement 后。
- **observation** 9.5 — aNB monostatic 和 aNB-aNB bistatic sensing modes 对 RAN2 没有影响；相关研究交由其他工作组。UE-UE bistatic 和 UE monostatic sensing modes 的研究待其他工作组进展后确定。
- **proposal** 9.5 — RAN2 的 ISAC 研究旨在制定通用的 procedure 和 protocol design，以适配所有受支持的 sensing modes 并满足受支持用例的需求。讨论指出，并非所有模式都会影响 UE，但其他场景也可能采用相同设计。
- **proposal** 9.5 — RAN2 的 sensing protocols and procedures 应支持广泛的 6G sensing use cases，以 TR 22.870 为起点，并考虑 outdoor 和 indoor deployments。讨论提议优先研究 UE-TRP、TRP-UE bistatic modes，再研究 UE to UE bistatic 和 UE monostatic sensing modes。
- **proposal** 9.5 — RAN2 将识别第一阶段中会带来不同 RAN2 影响的 sensing modes 和 interaction assumptions，并将其作为工作的起点优先处理。
- **proposal** 9.5 — 初始 6G ISAC 研究优先考虑以 mono-static aNB sensing 为基线，并扩展到 bi-static aNB sensing。涉及 UEs 的 sensing modes 不被排除。
- **proposal** 9.5 — UE-involved sensing work 的研究顺序定为：UE 测量 DL sensing reference signals；UE 发送 UL sensing reference signals；UE 为 UE to UE 场景收发 sensing signals。讨论认为第三项的重点可包括 resource allocation，且应在理解前两项后开展。
- **proposal** 9.5 — UE-centric sensing 定义为 UE 发起 sensing session、作为唯一 Rx sensing entity、唯一处理 sensing data 并生成 sensing results 的实体，以及结果的唯一最终消费者。UE 和/或其他 sensing entities 可以发送 sensing signals。
- **proposal** 9.5 — 提议研究适用于 UE monostatic、network-to-UE bistatic/multi-static 和 UE-to-UE bistatic/multi-static modes 的 UE-centric sensing operation mode。讨论聚焦于先研究共通 procedures，包括 UE selection、capabilities、configurations 和 measurements，并指出部分事项依赖其他工作组；意见对其范围及研究顺序存在分歧。
- **proposal** 9.5 — RAN2 可假设核心网中有负责 sensing management 和 sensing data processing 的 SF，以便后续讨论。SF 是否也可部署在 RAN node 等其他节点，可留给其他工作组讨论。
- **proposal** 9.5 — 建议先由 SA2 和 RAN3 讨论 sensing architecture。
- **proposal** 9.5 — 建议 RAN2 研究独立于底层传输层的端到端（SF–UE）Sensing Protocol。讨论中提出，SF 可视为逻辑上位于 CN，且基站负责向 UE sensing entity 分配无线资源；SF 的部署位置及数据特征也被提出讨论。
- **proposal** 9.5 — Sensing procedure 至少包括 UE capability reporting、sensing assistance information transfer、sensing measurement and reporting configuration，以及 sensing measurement reporting（即 sensing data transfer）。讨论指出，最终不一定需要所有这些 procedure；UE assistance 可能包括发射端和接收端的 reference signal configuration resources 请求。
- **proposal** 9.5 — RAN2 初始 ISAC/Sensing 研究范围应包括 UE sensing capability signalling、sensing configuration and activation procedures，以及 UE-to-network sensing data reporting。
- **proposal** 9.5 — RAN2 讨论现有 RRC signaling procedures 是否足以支持 sensing framework，涉及 connection control、configuration management、resource management、UE capability signaling 和 UE authorization。
- **proposal** 9.5 — 建议由 aNB 提供 sensing configuration，包括 sensing resources、sensing signals，以及 measurement data report 的 content、format 和 triggering conditions。
- **proposal** 9.5 — RAN2 应内部讨论并与 SA2、RAN3 协调，以定义通用的 sensing entity selection framework。
- **proposal** 9.5 — RAN2 确认了两种 sensing service request 假设并将进一步研究 RAN2 影响：针对 UE 的请求（选择特定 UE 作为 sensing entity），以及针对 Area 的请求（根据 sensing area 选择 sensing entity）。
- **proposal** 9.5 — RAN2 将研究现有 configuration 和 measurement reporting mechanisms 是否足以支持 ISAC，具体细节待进一步研究。
- **proposal** 9.5 — 研究复用 communication measurement framework，以支持 ISAC-related measurements。
- **proposal** 9.5 — RAN2 可基于 RAN1 simulation results and assumptions 研究 sensing data 的 traffic characteristics，并评估其对 scheduling mechanisms 的影响。该研究还需与 RAN1 正在进行的 6G ISAC study 对齐。
- **proposal** 9.5 — 讨论认为 Service Continuity 应考虑 sensing entity 和/或 sensing target 的移动，并涉及 sensing entity selection 以及 Uu interface 和 aNB interface。对于是否需要考虑移动、能否假设 stationary 或 single cell mobility，以及使用 “service continuity” 一词，各方意见不一；结论为 Noted。
- **proposal** 9.5 — 讨论 ISAC operation 适用的 RRC states；6G 至少应支持 RRC_CONNECTED 下的 UE，并研究在低功耗状态（RRC IDLE、INACTIVE）启用 ISAC 的可行性，以优化 UE energy efficiency。结论为 Noted。

## 6GR AI/ML 协议支持（8 条）

- **proposal** 9.3.3.2 — 提出 6G model transfer 应满足 awareness 和 controllability 要求：MNO 可知晓 model 的存在，并可控制 model transfer/delivery procedure，包括 initiate、suspend、resume 和 stop。
- **proposal** 9.3.3.2 — 提出 UE-sided model transfer 对 NW 透明，因此不需要 NW controllability。
- **proposal** 9.3.3.2 — 对于由 OTT server 训练并存储在 3GPP network 外的 UE-sided model，提出 model transfer/delivery 无需 controllability 或 visibility；model 可由 OTT-server 直接传至 UE，且对 3GPP 透明。该提议标记为 Not treated。
- **proposal** 9.3.3.2 — 提出 network 应能控制 UE 是否应用可能影响 network QoS requirements、user experience 或 overall system performance 的 AIML based functionality。
- **proposal** 9.3.3.2 — 提出 6G AI/ML LCM framework 应支持对 UE-sided model 采用 UE-based 和 NW-based 两种管理方式。
- **proposal** 9.3.3.2 — 提出 network 应能控制 UE 在 AI/ML 与 non-AI/ML functionality 间的切换：可指示或配置 UE 切换，也可控制 UE 是否能自主切换，并要求将当前状态通知 NW。
- **proposal** 9.3.3.2 — RAN2 支持 functionality-based LCM 作为 baseline；是否支持 model-based LCM 仍待进一步研究（FFS）。
- **proposal** 9.3.3.2 — 提出在 6G 中研究 model-based LCM。该提议标记为 Not treated。

## 6GR 控制面其他议题（17 条）

- **agreement** 9.3.2.5 — RAN2 将研究起点聚焦于 FR1-FR2 synchronous non-collocated deployments，latency 上限为 10ms。研究应考虑 single 或 dual scheduler、调度器可协调或不可协调的情况，以及 PUCCH 假设、回传时延对 UP protocol 的影响、性能和可行性。
- **observation** 9.3.2.5 — 原文将 cell 描述为一种 logical concept，用于让 network 管理 physical end points、其资源，并按所需 service quality 配置硬件。需要澄清 6G 中 cell 的定义，以明确 primary 和 secondary serving cells 概念，同时纳入 RAN1/RAN2 和 RAN4 中的 UE requirements。
- **proposal** 9.3.2.5 — 在 RRC_CONNECTED 多载波操作中，6GR UE 可配置不同载波上的多个“serving cells”，RAN2 聚焦其 L2/L3 功能。采用“per cell per carrier”还是“single cell multiple carrier”建模，待 RAN1/4 进一步讨论。
- **proposal** 9.3.2.5 — 6G 支持 carrier aggregation，primary cell 至少用于 system information reception、RLM 等。RAN2 将研究需关联到特定 serving cell 的功能及 primary/secondary serving cells 功能不同的原因，并识别 5G carrier aggregation framework 的待改进之处；6G 术语待 RRC 结构确定后再定。
- **proposal** 9.3.2.5 — 提出支持单一 MAC entity 的 spectrum aggregation，并包含 multiple TAGs、无需 RRC 参与的 component carrier 动态激活/去激活、基于 CA 的 duplication 与 LCH 和 carrier 的灵活映射，以及 early measurement reporting。
- **proposal** 9.3.2.5 — 多载波连接模式下，可考虑增强 fast cell change 和 RLF handling 相关流程。另有提案建议 6G 在 RLF detection 和 RRC re-establishment 之外提供韧性工具，包括额外触发条件及新的 UE 动作。
- **proposal** 9.3.2.5 — 6G 支持 UE 从 IDLE/INACTIVE 转换时，更快重定向到合适的 carrier(s)/cell(s)，并在 RRC_CONNECTED 中建立 aggregation。
- **proposal** 9.3.2.5 — RAN2 研究支持 flexible aggregation 所需的 RRM measurement architecture。
- **proposal** 9.3.2.5 — Cell 被定义为管理 physical carrier resources 的逻辑术语。cell 与 physical carrier(s) 的映射取决于 RAN1 讨论，例如 Gothia cells。
- **proposal** 9.3.2.5 — 提议 RAN2 将 cell 定义为可由 RRC signalling 关联的 downlink 和/或 uplink resources 组合。cell signalling 还应明确区分 schedulable PRBs 和 RF bandwidth。
- **proposal** 9.3.2.5 — 预计 RAN2 在 system information、IDLE mobility、connected mobility 及 RRM 中使用“cell”术语。cell 是否仍用于 connected mode 下 UE 的 radio resource configuration 尚待确定。
- **proposal** 9.3.2.5 — Cell 可包含 downlink、uplink 或两者资源，对应由单一 aNB 控制的一个或多个 TRPs，并关联一个 CD-SSB 和一个 PCI。每个 cell 可为 TDD 或 FDD；“Gothia cell”讨论留待 RAN1。
- **proposal** 9.3.2.5 — RAN2 将考虑 6G FR1-FR2 非共址频谱聚合的要求，包括支持单向 10 ms 或更高的站间时延、吞吐量和覆盖优于 5G FR1-FR2 部署，以及便于从 5G NR-DC 部署迁移。还要求支持非共址节点间跨厂商频谱聚合的标准化接口，并兼容已部署的 RAN 架构。
- **proposal** 9.3.2.5 — 为简化规范和实现，考虑异步操作及 FR1-FR1 非共址部署前，应先证明其实用部署或用例。RAN2 将聚焦 FR1-FR2 和 FR1-FR3 同步部署；针对约 10 ms 回传时延的 FR1-FR2 非共址场景，RAN2 研究应聚焦 UL/DL 解耦。
- **proposal** 9.3.2.5 — 针对回传时延最高 10 ms 的非共址 inter-aNB CA，需讨论网络侧采用集中式还是分布式 MAC scheduler、调度与 HARQ 的影响、PDCP/RLC 的影响，以及是否需要规定节点间接口交换的信息。讨论还提出研究单一和分布式 scheduler 的利弊，并考虑 UL/DL decoupling。
- **proposal** 9.3.2.5 — RAN2 受请评估：非理想回传（最高 10 ms）造成的额外 UP 时延，对于带非理想回传的频谱聚合是否可接受。
- **proposal** 9.3.2.5 — RAN2 需就使用 NR-DC framework 支持回传时延最高 10 ms 的 6G FR1-FR2 非共址频谱聚合进行评估，涵盖 intra-aNB/inter-aNB 及 intra-vendor/inter-vendor 部署的可行性。原文提出现有 NR-DC 复杂，需结合 6GR 设计讨论规范影响及对 5G DC 设计的简化，例如 CP 和 UP 的 PDCP anchor 均仅位于 FR1 站点、无 SRB3、单一 RLM。

## 6GR 数据与模型传输（17 条）

- **agreement** 9.3.3.1 — 感知用例的讨论延期；待感知议题在数据特征、终止点等基础方面取得进一步进展后，可重新讨论其对 data transfer framework 的影响。
- **agreement** 9.3.3.1 — 目前不将 performance monitoring and inference 视为 data transfer。Immediate MDT 暂不属于 data transfer，当前假设其属于 measurement reporting framework。
- **agreement** 9.3.3.1 — 至少考虑以下终止点：RAN 侧的 SON、NW-side data collection 和 logged MDT；OAM 侧终止点留空。标准化 UE-side data collection 将在 MNO 设置一个用于可见性的终止点，但具体位置仍待确定；各公司下次会议应说明终止点设在 RAN 的理由。
- **proposal** 9.3.3.1 — Measurement Data transfer framework 应支持总数据量较小或较大、且时延要求较宽松（数十毫秒至数秒）的用例，包括 immediate MDT、continuous learning 的 NW-side data collection 和 sensing。讨论中对 continuous learning、immediate MDT、QoE 及 performance monitoring 是否属于该框架范围存在不同意见。
- **proposal** 9.3.3.1 — 对于 NW-side data collection 和 SON/MDT 用例，当 RAN 是 data consumer 时，RAN node 作为 termination point 并解码数据。
- **proposal** 9.3.3.1 — 当 OAM 是数据消费者时，应逐跳标识终止点：UE-RAN 数据传输由 RAN 终止，RAN-OAM 数据传输由 OAM 终止。RAN 可以解码数据。
- **proposal** 9.3.3.1 — UE-side data collection 由 UE server 消费时，端到端方案需要与 SA WGs 协调；UE-CN_NF 数据传输的终止点至少包括 CN NF，具体 NF 尚未确定，且 CN NF 可解码数据以核验或匹配请求数据与上报数据。经 OAM 转发的 UE-RAN 数据传输可由 RAN 终止；RAN 是否作为可解码节点应根据传输数据特征确定。
- **proposal** 9.3.3.1 — 对于网络用途的 UE data collection，仅当报告对 Uu 操作和 RAN 优化至关重要时，才将 RAN 视为终止实体，例如 immediate MDT、RVQoE 和 SON reports。此做法也有助于降低 UE AS 的数据收集内存需求，同时提供有意义的报告。
- **proposal** 9.3.3.1 — 条目按 SON、Logged MDT、Immediate MDT、QoE、RVQoE 和 NW-side data collection 分别列出了 consumer、termination entity 和 decodability；其中 Logged MDT 与 QoE 的终止实体为 OAM domain 中的 DCF，RVQoE 的终止实体为 RAN。讨论记录了关于数据是否应在 RAN 或 OAM 终止、解码负担、可见性与可解码性的关系及安全性的不同意见。
- **proposal** 9.3.3.1 — 在 RAN 作为消费者的用例中，数据应对 RAN node 可见且可解码，包括模型训练位于 RAN 的 NW-side data collection、SON、Immediate MDT 和 RAN visible QoE。
- **proposal** 9.3.3.1 — 在 OAM 作为消费者的用例中，数据也可以对 RAN 可见且可解码，包括模型训练位于 OAM 的 NW-side data collection、SON、Logged MDT 和 Immediate MDT。
- **proposal** 9.3.3.1 — 对于 OTT server 作为消费者的 UE-side data collection，由于同一数据也用于 RAN 中的 NW-side model training，数据可以对 RAN node 可见且可解码，并可经 CN/OAM 从 RAN node 共享给 UE-side OTT server。另有提议指出，终止点不是消费者时通常不可解码，但 OAM 消费 SON/MDT 且复用 RRC 是例外。
- **proposal** 9.3.3.1 — 各服务支持的传输方式应考虑服务特定数据特征，例如 latency 和 total data size；RAN2 讨论服务特定协议下方的子层选项，包括 CP-based、UP-based 和必要时的 new plane-based。另有提议主张为不同 6G 用例采用统一的数据收集框架。
- **proposal** 9.3.3.1 — AI/ML、sensing 和 SON/MDT 使用 service-specific protocols；服务的数据处理和控制信令分别在对应的 service-specific protocol 中定义。
- **proposal** 9.3.3.1 — 6G data collection over Uu interface 应考虑避免重复的数据收集和上报，并涵盖数据被多个消费者使用或用于不同用例的情况。
- **proposal** 9.3.3.1 — 将 data collection and transfer 的 controllability 定义为 MNO 能够启动、停止或调节 data transfer traffic 流量，并启用或禁用 data collection measurement resources（例如 reference signals）的能力。
- **proposal** 9.3.3.1 — 提议将 UE 与 network 间 data transfer 在 mobility 期间的 continuity 和 lossless transfer 作为额外方面：continuity 指 handover 期间无需重新发起 data transfer procedure 即可持续传输，lossless 指传输过程中不丢失数据。该提议标记为 Not treated。

## 6GR 提前报告（22 条）

- **agreement** 9.3.3.4 — 原文支持6GR为L2中尚不可用的上行数据提供early scheduling information。上行early scheduling information至少可包含timing information和data volume estimates；是否总是同时报告、报告方式与条件、时序含义及粒度等仍待讨论。

- **proposal** 9.3.3.4 — 建议依靠网络实现监测 prediction performance，并由网络控制是否允许 early reporting；无需引入 confidence 或 performance monitoring enhancement。

- **observation** 9.3.1.3.2 — 6G 中的 MAC CEs 可以采用更结构化的设计，以实现高效处理并满足预期更严格的 6G timing requirements。

- **proposal** 9.3.1.3.2 — 记录的内容为：6G baseline 应支持 4-step RACH 和 2-step RACH。

## 6GR 移动性（50 条）

- **agreement** 9.4 — 6G 可支持 candidate RRC configuration 的预配置，具体细节及如何解决资源效率问题仍待研究。若已向 UE 预配置 candidate RRC configuration，6G mobility procedure 应支持 fast RRC processing；该功能为可选，并非所有 UE 都需要支持。
- **agreement** 9.4 — 研究基于位置和定时器的测量报告/触发及 UE 触发移动性条件，并考虑连接态与空闲/非激活态移动性。研究至少考虑 6G TN–5G NTN 的 inter-RAT 移动性，并研究 NTN 小区中的 TN 测量跳过/放宽、多轨道移动性和 GNSS-free/GNSS-less 操作对 NTN 设计的 RAN2 影响。
- **observation** 9.4 — 即使大幅缩短空口切换中断时间，整体数据转发时延仍会影响 L2 数据传输。
- **observation** 9.4 — Path switch 仍是端到端 UP DL 新数据传输时延中不可忽略的组成部分。当前流程设计基于基本的 L3 handover 机制。
- **observation** 9.4 — UE 应用目标小区配置的时间是空口时延的关键方面。5G LTM 支持快速 UE 处理，但仅适用于预配置 HO CMD 的场景，且 UE 收到 HO execution indication 后才应用完整配置，因此无法将该时间缩短至 0 ms。
- **observation** 9.4 — 通过 advanced delta configuration 缩减 HO command 大小的工作已在“RRC Structure and (re)configuration”议题中进行。RAN2 应避免在 mobility 议题下重复讨论，并等待该议题的结果。
- **observation** 9.4 — 若 gNB 未有选择性或智能地进行 early CSI configuration，UE 可能需要测量多个“不必要”的候选小区/波束的 CSI-RS。这样会增加 UE 处理能力和测量模块的负担。
- **observation** 9.4 — TN-NTN 网络集成的商业部署模式可能不同，联合部署可为 inter-PLMN 或 intra PLMN，也可能由同一或不同运营商提供。这会直接影响 handover latency 等移动性性能指标，进而影响最终用户体验。
- **observation** 9.4 — 5G NTN 与 5G TN 商业部署进度可能分化，使 5G NTN 部署在首个 6G TN 商用网络可用时达到峰值。在这种情况下，稳定的 6G TN–5G NTN 移动性支持标准规范比 6G TN–6G NTN 移动性支持更重要。
- **observation** 9.4 — TN-to-NTN 移动性挑战包括：使用准确的卫星辅助信息和适当的预补偿测量 NTN 小区，以及及时提供切换配置。
- **observation** 9.4 — NTN-to-TN 移动性挑战包括避免在特定区域进行不必要的测量，以及避免 pingpong。
- **observation** 9.4 — 在 multi-orbit 场景中，UE 驻留于 GSO cells，并切换到不同 orbits 以满足不同 QoS requirements。该方式可帮助 UE 和 network 节能，UE 可避免频繁 cell reselection，network 可在无服务需求时关闭 NGSO beams。

## 6GR QoS/QoE 与服务感知（67 条）

- **agreement** 9.3.1.2 — 提出研究面向 Mobile AI、XR 等流量的 dynamic QoS，涵盖应用在 QoS flows 间切换、QoS flow 属性变化及同一 QoS flow 内 PDUs（PDU sets）具有不同 QoS 属性等场景；同时继续研究 UL/DL burst information 的检测与提供方式，并研究增强 uplink scheduling mechanism。作为讨论基线，UE/aNB 至少按 QoS flow 粒度接收上层/CN 数据，并支持到 RB 的 1:1 和 N:1 灵活映射。
- **observation** 9.3.1.2 — 6G 预期支持多样且动态、QoS requirements 随时间变化的流量，因此需要低时延和高效的 QoS adaptation mechanisms 来应对流量变化。
- **observation** 9.3.1.2 — 6G immersive communication 具有相互依赖的多模态 flows（如 video、audio 和 haptic）、多样的流量模式，以及单个或多个 UE 间严格的同步要求。为满足 human perceptual thresholds，需要协调的 L2 handling 和联合 QoS adaptation。
- **observation** 9.3.1.2 — 基于 GBR resource types 和严格 PDB/PER enforcement 的 legacy 5G QoS framework 面向确定性服务优化，在处理 6G immersive services 的非确定性、突发流量模式时会导致显著的频谱效率低下和资源过度配置。
- **observation** 9.3.1.2 — 静态 5QI definitions 和半静态 RRC/NAS configurations 缺乏跟踪 6G 流量快速、多维变化的灵活性；Control Plane 驱动的重配置固有时延也不适用于实时 QoS adaptation 所需的毫秒级响应。
- **observation** 9.3.1.2 — 5GS QoS Flow 为 6G 提供稳定基线，但 flow-level granularity 太粗，无法跟踪 Mobile AI 和 multi-modal services 中快速变化的流量及差异化 packet importance。
- **observation** 9.3.1.2 — 许多典型移动应用会建立大量短连接，导致 destination IP addresses 和 IP 5-tuples 快速变化。IP 5-tuples 动态变化会直接引发对应 QoS rules 和 mappings 频繁且不可预测地变化。
- **observation** 9.3.1.2 — 新兴 6G 服务对 latency、packet loss rate 等 QoS metrics 有严格要求，且 QoS requirements 可能随实时状态动态变化。现有 static QoS mechanism 无法适应这种动态性。
- **observation** 9.3.1.2 — 流量特征包括同一 data flow 内的 packets 具有不同 QoS requirements 的情形，例如 data burst。
- **observation** 9.3.1.2 — NR QoS framework 在 RAN 内将 data flow 中所有 packets 半静态地映射到单一 QoS treatment。因此，同一 DRB 承载的所有 packets 在 RAN protocol stack 中接受统一的 QoS treatment。
- **observation** 9.3.1.2 — 按 per-packet 或 per-packet-group granularity 进行 QoS handling，可比 per-DRB granularity 实现更轻量、高效的差异化处理。Qualcomm 询问了一个打破 intra-flow 的 per-packet group 示例。
- **observation** 9.3.1.2 — Per-packet 或 per-packet-group QoS granularity 可在 data flow 内实现更细粒度、动态的 traffic 到 QoS treatment 的映射。
- **observation** 9.3.1.2 — 更细的 QoS granularity 可使 resource allocation 更好匹配瞬时 traffic characteristics，从而减少 resource over-provisioning。
- **observation** 9.3.1.2 — GBR 需要非常严格的 resource reservation 来保证 bit rate，但这种方式的 resource efficiency 不高。
- **observation** 9.3.1.2 — 支持 dynamic QoS requirements 和 pre-authorization 的解决方案正在 SA2 讨论中。
- **observation** 9.3.1.2 — 5G 仅对 XR service 的部分 packet（即 PDU set）进行区分：UL 取决于 UE 实现，DL 则通过 GTP-U header 中的 CN indication 对 RAN 可见。6G 应支持 diverse applications，并满足同一 service flow（或 QoS flow）内不同 packet 的多样 transmission requirements。
- **observation** 9.3.1.2 — 同一 service 的不同 QoS flows 若因 QoS requirements 不同而映射到不同 DRBs，AS 交付给 upper layer 的 packets 将出现 out-of-order。由此会降低 throughput，并增加 signalling overheads 和 redundant packet transmission。
- **observation** 9.3.1.2 — 6G AI traffic 的独特特征可归纳为 Multi-modality、E2E latency，以及在采用 two-sided model 时的 Error tolerance。
- **observation** 9.3.1.2 — 在当前 5GS QoS framework 中，RAN/UE 不具备对 PDU Set 内 AL-FEC structure 的 awareness，这会导致显著的 resource inefficiency。
- **observation** 9.3.1.2 — SA2 已开始研究 AL-FEC 的 QoS aspects。
- **observation** 9.3.1.2 — 在 RAN 中支持 AL-FEC 有助于缓解 congestion 并降低 latency，而 5G 中 AL-FEC 对 RAN 是 transparent 的。可通过在 RAN 中配置 AL-FEC support，以满足 application layer requirements，并处理 RAN discarding 对 application layer 的影响顾虑。
- **observation** 9.3.1.2 — R19 支持基于 AL-FEC 的 discard 的主要问题是：对于 UM DRB，无法获知 PDCP SDU 是否已成功传输。
- **observation** 9.3.1.2 — 可利用 UL HARQ status indication 来判断 PDCP SDU 是否已成功传输。
- **observation** 9.3.1.2 — 基于 FEC-ratio 的 discard 有助于缓解 congestion，同时维持 immersive communication service 的 continuity。
- **observation** 9.3.1.2 — 在 AI glass、car、high-speed train、UAM、FWA 等场景中，service 可能并非由 UE 发起或终止，而是由通过 non-3GPP link（如 WiFi 和 BT）连接到 UE、并与 DN 通信的 tethered device 发起或终止。
- **observation** 9.3.1.2 — 系留设备经历的 QoS 取决于该设备与 Data Network 之间的端到端路径。
- **observation** 9.3.1.2 — 5G PIN 的 non-3GPP delay 方案无法充分利用数据包在 non-3GPP link 上经历的动态变化时延，也无法及时适配。
- **observation** 9.3.1.2 — E2E reliability 由 non-3GPP link PER 和 3GPP link PER 共同决定。RAN/CN 需要获知 non-3GPP link PER，以便适当设置 3GPP link PER；5G PIN 不支持这一点。
- **observation** 9.3.1.2 — 在 tethering 用例中，air interface delay budget 可以动态变化，以确保满足 end-to-end latency requirement。
- **observation** 9.3.1.2 — 当 tethered UE 经由 tethering UE 使用 non-3GPP link 接入网络时，端到端用户体验取决于 3GPP segment 和 non-3GPP segment。
- **observation** 9.3.1.2 — 根据 5G NR PDU session Modification procedure（TS 23.501），PEGC 向 SMF 提供 non-3GPP delay，SMF 可以通过调整 CN PDB 补偿该时延。
- **observation** 9.3.1.2 — 当前通过 PDU Session Modification 调整 CN PDB 来补偿 non-3GPP delay 的机制，可能不足以覆盖时延动态变化的各种场景。
- **proposal** 9.3.1.2 — RAN2 将研究 6G QoS mechanism 向动态、service-aware model 的演进，重点支持更细粒度 QoS 和快速适配 6G 服务的多维变化及时变需求（例如 Mobile AI 和 immersive communication），同时确保资源高效利用。
- **proposal** 9.3.1.2 — RAN2 将考虑以 5GS QoS Flow 作为 6G 基线，并研究支持更细粒度、使 Access Stratum 内 QoS 能够快速自主调整的增强方案。
- **proposal** 9.3.1.2 — 针对 6G 新服务，需要动态 QoS mechanism，由 RAN 直接调整服务的 QoS requirements，以保障数据传输和处理的及时性与可靠性；调整项可包括 Delay Budget、Error Rate 和 importance，粒度可为 QoS flows、PDU sets 或 packets。采用新 QoS requirements 的 QoS flows/PDU sets 将伴随 L2-related parameters 调整，例如 remaining time thresholds、discard timers、重传机制的启停及 scheduling priority。
- **proposal** 9.3.1.2 — 动态 QoS 研究应考虑关键网络指标监测、业务类型与需求识别、新处理流程设计，以及 RAN 与核心网交互。会上说明，UL 可依赖 UE，DL 可依赖 RNA 进行识别。
- **proposal** 9.3.1.2 — 6G QoS 框架中，QoS flow 仍是最细粒度，并保留与 RB 的灵活映射（1:1 和 N:1），同时支持在 RAN 中更明确地处理 QoS flow。假设 UE 从上层/CN 接收 QoS flow 粒度的数据包，RAN 可继续讨论更细粒度。
- **proposal** 9.3.1.2 — 6GR 支持基于可配置参数的 RAN packet classification，以便在 flow 内进行逐包分类并提供差异化 QoS 处理。讨论提及，burst 或数据包类型的信息可来自 CN 或 UE。
- **proposal** 9.3.1.2 — 6GR 支持根据 PDU 分类结果，将 PDU 动态映射到适用的 QoS 配置之一。讨论确认这是 6G 新增内容，并提出可向 SA2 询问是否支持对数据包或数据包组进行差异化处理。
- **proposal** 9.3.1.2 — 为应对基于 Application/Service awareness 的动态 QoS 需求，RAN2 应优先研究 UE 如何动态调整 UL traffic flow 的 radio treatment。讨论指出，相关 DL 问题需要 SA2 输入，RAN2 仍有进一步研究工作。
- **proposal** 9.3.1.2 — RAN2 可研究三种方式，为同一 traffic flow 中的数据包动态提供差异化 radio treatment：一个 QoS flow 关联多个 DRB 并选择 DRB；一个 DRB 关联多个 RLC/LCH 并选择 C/LCH；或一个 DRB 配置多组参数并按包切换参数集。ZTE 提出可考虑 1:N，并假设不存在 in-order delivery。
- **proposal** 9.3.1.2 — RAN2 研究 aNB/UE 如何及何时在 CN 预配置的 QoS requirements 范围内切换参数，包括 aNB 可依据哪些标准改变 QoS requirements。
- **proposal** 9.3.1.2 — RAN2 应研究支持基于动态 traffic awareness 等因素的 dynamic QoS adaptation，包括 QoS flow 具有一组 QoS 参数取值范围、具有多个 QoS profiles，以及将 application traffic 动态映射到多个 QoS flows。
- **proposal** 9.3.1.2 — RAN2 应研究 dynamic QoS adaptation 引起的 layer 2 影响，例如 DRB 的 LCP adaptation 或 packet retransmission。
- **proposal** 9.3.1.2 — RAN2 应至少研究三类 dynamic QoS 场景：应用在一组 QoS flows 间动态切换 traffic；QoS flow 动态改变某个 QoS attribute；以及同一 QoS flow 内的 PDUs（PDU sets）具有不同 QoS attributes。
- **proposal** 9.3.1.2 — 研究支持目标用例动态 QoS 的 RAN2 方案，包括通过新的 AS signaling 在 RAN 和 UE 间切换 QoS profiles、预配置并联合适配 Layer2 参数与 QoS 属性，以及在同一 QoS flow 内进行差异化 QoS 处理。讨论指出还需明确会变化的 QoS 参数、动态属性及其变化程度，并聚焦需求动态变化且 QoS re-configuration 不足以应对的应用。
- **proposal** 9.3.1.2 — service-awareness framework 应适用于多种应用，包括 immersive communication 和 mobile AI traffics，并支持应用到 UE 的 UL 指示及 CN 到 RAN 的 DL 指示。其要求是同一 service 内不同 packets 可具有 dynamic/adaptive QoS requirement。
- **proposal** 9.3.1.2 — RAN2 假定 UL 和 DL 的 service-awareness 均包含 QoS flow level 的差异化 QoS requirement。还包含同一 QoS flow 内 packet/burst level 的差异化 QoS requirement。
- **proposal** 9.3.1.2 — 拟向 SA2 发送 LS，说明 RAN2 对 generic framework for service-awareness 的理解，并解释同一应用以多个 QoS flows 区分不同 packets 的 QoS requirement 时，AS 到 upper layer 的 out-of-order delivery 问题。还将询问 SA2/SA4 是否会提供标准方案，使 AS layer 能获知 service 的差异化 packet transmission requirements，以支持 UE 的 UL 和/或 RAN 的 DL service-awareness。
- **proposal** 9.3.1.2 — RAN2 将研究 generalized service-awareness framework，其中包括从 UE 向 RAN 暴露 assistance information。XR 中相应的 awareness framework 可作为起点。
- **proposal** 9.3.1.2 — 为获取 TCP ACKs awareness，RAN2 将研究 transmitter side approach，同时支持发送端的 TCP ACK transmission prioritization 和接收端的 selective OOD。
- **proposal** 9.3.1.2 — RAN2 将向 SA2（抄送 RAN3）发送 LS，询问 UPF 是否能对 TCP stream 的 QoS flow 中每个 DL packet 进行分类和标记，以指明其是否携带 TCP ACK，或是否要求 in-order delivery。
- **proposal** 9.3.1.2 — RAN2 将考虑在 6GR 中采用 hybrid SDU delivery mechanism。该机制可对携带 TCP ACK 的 SDUs 选择性采用 out-of-order delivery，而同一 DRB 的其他 SDUs 采用 in-order delivery。
- **proposal** 9.3.1.2 — 为获取 TCP ACKs awareness，RAN2 将研究 transmitter side approach，同时支持发送端的 transmission prioritization 和接收端的 selective OOD。该提案标记为 Noted。
- **proposal** 9.3.1.2 — RAN2 将研究 UE 应向 aNB 提供哪些信息以及如何提供，例如 traffic types、patterns 和相应的 QoS requirements。传递方式可包括 UAI message 或其他机制。
- **proposal** 9.3.1.2 — RAN2 将研究 QoS requirement 变化对 LCP behavior 的影响。还将研究为高效 uplink scheduling 提供精确 data burst information（如 data volume 和 duration）的机制。
- **proposal** 9.3.1.2 — RAN2 将研究引入 AL-FEC aware L2 protocol stack，并研究相应增强，使 source 和 repair packets 能根据 application-layer reconstruction requirements 得到差异化处理。
- **proposal** 9.3.1.2 — 若 RAN2 同意研究 AL-FEC awareness mechanisms，研究应聚焦于达到 reconstruction targets 后主动丢弃冗余 PDUs，以及跨 PDU multiplexing 策略。后者通过将同一 AL-FEC frame 的 packets 映射到不相关的 radio resources 来增强 transmission diversity。
- **proposal** 9.3.1.2 — RAN2 将研究从 CN 和 UE 向 RAN 提供 AL-FEC related information，并研究 UL 和 scheduler 为支持 DL 与 UL 中的 AL-FEC 所需的内容。如有需要，可通过 LS 征询 SA4 意见。
- **proposal** 9.3.1.2 — 研究面向 6G immersive communication 的 FEC-based discard mechanism：拥塞期间，可根据 FEC ratio 并基于 HARQ status indication，丢弃 PDU Set 内冗余的 PDCP SDUs。
- **proposal** 9.3.1.2 — RAN2 同意研究对 service characteristics 进行差异化支持，以改善 E2E user experience。
- **proposal** 9.3.1.2 — 对 E2E user experience 的 service characteristics differentiation 支持应考虑 tethering case。
- **proposal** 9.3.1.2 — 对于 tethering case，E2E user experience 应考虑 tethered device 与 Data Network 之间的端到端路径。
- **proposal** 9.3.1.2 — 为保障 tethered device 与 DN 之间的 E2E user experience，至少需要考虑 latency 和 reliability。
- **proposal** 9.3.1.2 — 为保障 tethering case 的 E2E latency，RAN2 同意研究在 AN PDB 中补偿 non-3GPP delay（tethered device 与 UE 之间的 delay）的 service awareness solutions。已就此决定向 SA2 发送 LS。
- **proposal** 9.3.1.2 — 除 AI applications 外，RAN2 可以同意 varying QoS requirement 的特征也存在于其他用例，包括 Immersive XR 和 Tethering-based 场景。
- **proposal** 9.3.1.2 — 研究 RAN 层面的潜在增强，以支持通过 non-3GPP links 连接的 tethered UEs 的 dynamic QoS handling。

## 6GR 初始接入与系统信息（19 条）

- **agreement** 9.3.2.3 — 研究 periodic SI window，包括可配置的 window 宽度和起始位置，并研究如何处理当前未广播 SI 的窗口预留问题。灵活 SI scheduling 可研究将不同 periodicities 的 SIBs 合并传输、在一个 SI-window 内发送多个 SI messages，或通过不同 frequency resources 发送；评估需考虑网络节省、UE 功耗与复杂度及 SI modification 影响。
- **observation** 9.3.2.3 — NR SIB1 的主要开销来自 DL 和 UL BWP configurations，约占 70%；启用 SUL 或 RedCap 的 initial DL/UL 配置时，BWP 相关配置大小至少翻倍。若网络配置多个 SI、PLMN ID list、UAC list 并支持 RedCap 等额外特性，SIB1 很可能超过 2976 bits 限制。
- **observation** 9.3.2.3 — 当 SIB1 被拆分且部分内容移至 OSI 时，最坏情况下获取完整 SIB1 的时延预计等于最短 SI message periodicity，通常为 80 ms。
- **observation** 9.3.2.3 — 当前 NR SIB1 的很大一部分由 UL 和 DL cell configurations 构成，例如 servingCellConfigCommon、RACH configurations 和 initial BWP。多数此类信息仅在 UE 主动发起接入时需要，而 UE 仅驻留时不需要。
- **observation** 9.3.2.3 — 将 access information 移到另一条 SI message 以解决 SIB1 大小问题，会因 two-step acquisition 及需在 SI window 内获取而引入相较 NR 的接入时延；原文认为 6G 应避免这种做法。
- **observation** 9.3.2.3 — 5G 中，SIB1 大量包含支持特定 features 或 verticals 所需的系统信息。特定 features/verticals 的驻留和接入信息增大了 SIB1，并常导致不必要的网络/UE 功耗。
- **observation** 9.3.2.3 — 增强网络节能的最有效方式是尽可能少发送 SIB1。
- **proposal** 9.3.2.3 — RAN2 需确认 SIB1 split 引入的时延可以接受，且不构成该研究的 showstopper。是否以及如何改善时延仍待研究（FFS）。
- **proposal** 9.3.2.3 — RAN2 将讨论三种 SIB1 splitting 方法并确定偏好：将 UE access 相关字段、area-specific 字段，或不同 device types（如 eMBB UEs）对应字段移至 subSIB1。
- **proposal** 9.3.2.3 — RAN2 可假设从 NR Rel-15 SIB1 拆出的信息量（包括 UE access 相关信息和 paging information）约为 200 至 12000 bits。实际部署中的信息量可能小得多，例如低一个数量级。
- **proposal** 9.3.2.3 — RAN2 讨论是否将 UE access 相关信息和 paging information 移出 SIB1。主要权衡是减少 SIB1 大小与增加 UE 获取相关信息前接入网络的时延。
- **proposal** 9.3.2.3 — RAN2 假设 SIB1 包含 6GR 中适用于所有 features/device types 的通用信息。
- **proposal** 9.3.2.3 — 提出将 SIB1 结构拆为分别发送的 primary SIB1 和 SIB1x：primary SIB1 至少包含 PLMN information、(re)selection parameters 和 cell barring；SIB1x 包含 UL/DL access BW configurations、RACH resources 和 access control parameters。
- **proposal** 9.3.2.3 — Primary SIB1 和 SIB1x 遵循类似 legacy SIB1 的调度原则；SIB1x 不依赖 SI window concept。
- **proposal** 9.3.2.3 — SIB1x 至少包含与所有 UE 支持的最低 device capabilities 相关的驻留和接入参数。额外的 vertical/feature-specific 接入信息或其他载波相关信息可通过不同版本的 SIB1x 广播。
- **proposal** 9.3.2.3 — 暂缓 SIB1 splitting 讨论，待 6G SIB1 内容或新需求有进一步进展后再继续。恢复讨论时可考虑将 UE access、area-specific 或不同 device types/features 相关字段移至 SIB1x 或其他 SIB，并进一步研究 splitting 的动机以及采用 fixed 还是 flexible split。
- **proposal** 9.3.2.3 — RAN2 将研究 SI window 的可配置起始位置，包括 slot granularity 的起始位置，以及 SI window granularity 的 per-window 起始位置（如 Rel-17 NR 的 si-WindowPosition），以便将 SI transmission 与其他 common broadcast signaling 聚集。还指出，部分 OD-SI 即使未发送也会占用 SI window 时间，并影响网络和 UE 的功耗。
- **proposal** 9.3.2.3 — RAN2 将研究 OD-SI 的 dynamic SI window allocation，例如仅在相关 OD-SI 正在广播时分配 SI windows。讨论还涉及可配置 SI window 起始点、缩短 SI messages 的整体发送时长及 clustering，并提到不排除 dedicated OD SI。
- **proposal** 9.3.2.3 — 6G 的 on-demand SI 可考虑支持 on-demand (other) SI，并将 MSG3 based UE request OD SI 作为 baseline，且规定为 UE mandatory feature。RAN2 也应研究 Msg1- 和 Msg3-based Other SI request schemes：前者降低 UE complexity 和 SI acquisition 的 UE power consumption，后者可一次请求多个 SI 以避免大量请求。

## 6GR UE 能力框架（14 条）

- **agreement** 9.2.1 — FeatureSet ID大小和FSC List保留两种候选方案：缩小FeatureSetDownlink/UplinkID，或采用short/long可变长度；细节留待WI stage-3决定，RAN2 SI阶段不再讨论。RAN2还将基于真实NR capability container比较Category 1/3/8方案的收益与限制，并研究Category 6 compression的收益；RACS ID是否继续使用尚无共识，RAN based ID可进一步研究。
- **agreement** 9.2.1 — TR将记录Solution 4（Coarse granularity）和Solution 5（Band combination signalling optimization）。Solution 4针对重复信令的能力，涉及per BC、per band pair per BC、per FSPC及per FS粒度；Solution 5包括移除BW classes的冗余BC，并假设仍需信令BW class。
- **agreement** 9.2.1 — 确认现有 NR UAI 机制在所有用例中的问题，包括网络可能不支持或未启用该功能、UE 无法获知网络是否及如何处理请求，以及网络不了解 UE 未指定的自主行为。研究允许部分用例在无网络预配置时触发 capability update、更新内容、响应消息与响应时限；power saving、foldable phones 和 IDC 列为补充用例。
- **proposal** 9.2.1 — RAN2 将根据 Category 1-3/8 capability signalling design 的结果，研究 Category 6 compression solution 的收益。讨论认为压缩收益取决于最终结构，相关分析可待结构确定后进行，并记录了最高约 50% 收益的观点。
- **proposal** 9.2.1 — 将 Solution 4/5 及其受影响的 capabilities 纳入 TR，并在 WI 阶段根据 6G 的 RAN1/4 feature list 重新评估是否考虑 coarse granularity。
- **proposal** 9.2.1 — 目标是统一 UE capability change signalling procedure，以支持报告 UE envelope capabilities 变化及特定 RF-或 hardware-related capabilities 变化。该目标不意味着所有用例影响相同的 capability fields。
- **proposal** 9.2.1 — 确认现有 NR UAI 机制的两个问题：网络可能不支持或未为 UE 启用 UAI，且没有网络直接响应，UE 无法确定网络是否会处理其变更请求。讨论中还提出，UE 自主 fallback 可能让 UE 行为不可预测。
- **proposal** 9.2.1 — 提出所有用例中的 UE 均可在无网络预配置时触发 capability update，但网络如何处理该更新未作规定。讨论意见涉及网络性能与控制、网络不支持时的开销、适用用例范围，以及避免 UE 在发送指示前进行自主行为。
- **proposal** 9.2.1 — 讨论将更新后的完整 capability container 作为请求 capability update 的指示方式。部分公司支持该方式，另有意见指出完整上报会占用容量并带来开销，并提出 UE 也可提供 preferred configuration。
- **proposal** 9.2.1 — 提出为所有用例定义 capability update 的 response message，具体使用何种消息仍待讨论。意见包括网络可指示是否会处理请求，以及避免使用 reject。
- **proposal** 9.2.1 — 将 power saving 列为 capability update 的补充用例。
- **proposal** 9.2.1 — 将 IDC 列为 capability update 的补充用例；讨论提到可为 IDC 使用标准化方案。
- **proposal** 9.2.1 — 尚在讨论折叠手机是否需要 capability update，以便正确处理。Samsung 认为应按其他用例处理；Oppo 认为这是瞬时变化，可作为 MIMO change 处理；Xiaomi 认为网络应知道这是 UE capability change 所致。
- **proposal** 9.2.1 — 未来可在其他用例的需求明确后讨论这些用例。capability change framework 应力求对这些用例保持 forward compatibility。

## 6GR 用户面架构（94 条）

- **observation** 9.3.1.1 — 观察到 separate layer design 可能存在 robustness 问题：fake PDCP PDUs 可故意更新 RLC variables，阻止 authentic packets 后续处理。
- **observation** 9.3.1.1 — 通过合并 PDCP 和 RLC，re-ordering、window maintenance、status report 和 SDU discard 等重复功能可设计得更高效。
- **observation** 9.3.1.1 — 在 merged layer 中，security function 可识别 fake PDUs，并阻止其故意更新 ARQ state 和 SN status variables。这样 authentic packets 后续到达时仍可处理。
- **observation** 9.3.1.1 — RAN2 应研究以下场景中的 single sequence numbers：无 CU-DU split 且无 Dual Connectivity；有 CU-DU split 且无 Dual Connectivity；有 CU-DU split 且可能有 Dual Connectivity，例如 RANP 讨论的 FR1/FR2 non-collocated deployments。
- **observation** 9.3.1.1 — 在 RLC header 中重复 common SN 是冗余的，并会增加开销和 header processing complexity。
- **observation** 9.3.1.1 — 现场数据表明，携带 NACK 的 RLC Status PDU 中，RLC Status PDU 截断问题较为常见。
- **observation** 9.3.1.1 — 截至 Rel-18，DRB 的 RLC 运行于两种模式：RLC UM 在 RLC 层将时延最小化但不提供可靠性保证；RLC AM 提供 100% 可靠性，但 RLC 时延无界（PDCP discard timer 除外）。
- **observation** 9.3.1.1 — RLC segmentation 会在发送端和接收端造成处理瓶颈：发送端无法进行 pre-processing，接收端则会在 reassembly 时受阻。
- **observation** 9.3.1.1 — 在高数据速率下，RLC segmentation 不增加收益，因为 TB 已可一次承载数百个 IP packets。
- **observation** 9.3.1.1 — RLC segmentation 仅适用于低数据速率链路。
- **observation** 9.3.1.1 — 将多个 QoS flows/traffic flows 映射到单个 DRB，可能因 PDCP reordering 导致 HOL blocking。
- **observation** 9.3.1.1 — 静态 PDCP reordering 机制不适用于具有动态 QoS 的服务特性。
- **observation** 9.3.1.1 — 5G PDCP reordering 机制在 DL 峰值吞吐量下会导致较高的 Rx 内存需求，且无法适应 QoE。
- **observation** 9.3.1.1 — 5G 静态 PDCP discard timer 机制存在两项问题：逐包定时器可能丢弃 application bursts，且不考虑 QoE 是否改善；单一静态 timer 无法适应路径时延变化，控制 application delay 的能力较粗略。
- **observation** 9.3.1.1 — 应论证支持 AQM discarding mechanism 的 AS layer enhancements 相较于现有 SDU discard mechanism 的必要性。关于潜在 ECN enhancements 的讨论取决于 RAN3 对 CU-DU split 的讨论。
- **observation** 9.3.1.1 — NR 中 ROHC、UDC 和 EHC 是分别引入的多种压缩机制，但它们具有共性。
- **observation** 9.3.1.1 — 原文指出 UDC 是成熟且具成本效益的功能，符合包括 IMS service support、TN/NTN convergence、UE power saving 和 uplink coverage enhancement 在内的 6G 核心需求。原文认为 UDC 是 6G Day‑1 deployment 的必要功能。
- **proposal** 9.3.1.1 — RAN2 将基于合并 PDCP 和 RLC 层进一步研究 single sequence numbering functionality；否则保留具有独立 SN 的两个子层。该项被 noted。
- **proposal** 9.3.1.1 — 对于依赖 SN 的功能，(Re)segmentation/reassembly 和 ARQ 应由 RLC 执行，以满足实时低时延要求。
- **proposal** 9.3.1.1 — RAN2 将以 Table 1 为起点，按部署场景研究 unified Sequence number 的三种方案：PDCP 与 RLC 使用独立 SN、两层间统一 SN 但保留独立层，或合并为单层。原文列出合并层对 dual connectivity、CU-DU split、handover 和 data duplication 的影响或疑虑。
- **proposal** 9.3.1.1 — 原文提出暂缓 single SN 的合并 PDCP/RLC 层研究，待 migration options 和 CU-DU split 取得进展，目前假设 PDCP 与 RLC 分层。后续继续研究 single SN 在不同架构场景下的影响、复杂度、利弊及相关功能位置。
- **proposal** 9.3.1.1 — 原文提出由 RAN2 处理 single SN 下的 PDCP control PDU 问题，列出三种方案：分配 PDCP SN 并触发 SN gap report、为控制 PDU 分配独立 PDCP SN，或通过 SRB 传输。
- **proposal** 9.3.1.1 — 原文请 RAN2 讨论最高层 Control PDU 的 SN 分配方案：按 NR 分配 SN、不分配 SN，或仅为部分 Control PDU 分配 SN。该项标注为 Not treated。
- **proposal** 9.3.1.1 — PDCP entity 分配 SN，且 PDCP header 包含 SN。
- **proposal** 9.3.1.1 — RLC 使用 PDCP header 中包含的 PDCP SN 执行 (re-)segmentation 和 ARQ。
- **proposal** 9.3.1.1 — 无论采用何种层建模，利用 SN 的功能应共用 header structure 和 SN allocation mechanism。

- **observation** 9.3.1.4 — HARQ process 成功时在 DCI 中提供 ACK，可使 L2 buffer 需求减少 60–80%。
- **observation** 9.3.1.4 — 基于 ACK signalling 的内存需求减少可 effectively had for free。
- **observation** 9.3.1.4 — 通过 DCI 显式提供 HARQ ACK，可使 UE 避免冗余重传，并确保 MAC CEs 可靠交付。
- **observation** 9.3.1.4 — 若 UE 指示的 ACK 设计为可抵御误解读，aNB 可据此清除其 L2 buffers，使 aNB 的 L2 buffer 需求减少 60–80%。
- **observation** 9.3.1.4 — DL 中，网络可随时终止现有 HARQ process，并立即转为类似 ARQ 的重传；UL 中不可行。
- **observation** 9.3.1.4 — HARQ-assisted DL ARQ 有望显著降低 latency，同时不增加 RLC retransmission rate。
- **observation** 9.3.1.4 — NACK-To-ACK/DTX-to-ACK error detection mechanism 的动机是 DL RLC latency，属于 RAN2 范围；具体机制可由 RAN1 研究。
- **observation** 9.3.1.4 — DL 中 N2A/DTX2A error detection and reporting 的挑战之一，是尽量减少由非 PUCCH errors 引起的 HARQ terminations 所导致的冗余报告。
- **observation** 9.3.1.4 — DL 中，PUCCH errors 和 missed DCIs 会导致 residual HARQ errors，进而需要 NW 进行 RLC retransmission。
- **observation** 9.3.1.4 — 高层 HOL blocking 主要有四类：Type 1 为 PDCP Rx window 内 Inter SDF intra DRB；Type 2 为 RLC Tx side 的 Intra/Inter-SDF intra-DRB。Type 3 为 RLC Tx side 的 PDCP data PDU 阻塞 PDCP control PDU；Type 4 为 Tx side control PDU 与 data PDU 之间的 Inter DRB 阻塞。
- **observation** 9.3.1.4 — 仿真结果显示，Type 1/2 HOL blocking 可能使网页下载延迟增加 80%。
- **observation** 9.3.1.4 — 5G radio bearer setup/release procedure 无法以可扩展、动态、高效且灵活的方式适应应用产生的动态、大量短 TCP/QUIC 连接。
- **observation** 9.3.1.4 — PDCP transmitter 的 HOL blocking 可由 UE/NW 实现充分处理。部分 QoS-related HOL blocking 可能发生在 RLC 的 Tx 与 ReTx buffers 之间。
- **observation** 9.3.1.4 — PDCP Rx 中，若某个 SDU 丢失，即使其他 SDU 属于不同 QoS flow，或无需等到该丢失 SDU 后再交付，也可能被滞留在 Rx buffer 中，从而发生 Head-of-line blocking。
- **observation** 9.3.1.4 — 对于 Rx HOL blocking，从协议或硬件角度看，单个 DRB 使用多个 Sequence Number spaces（用于 reordering）相比多个 DRB 各使用单个 Sequence Number space 没有优势。
- **observation** 9.3.1.4 — 考虑到 6G 中 TB size 可能较大，交付已成功解码的 TB 部分可带来性能收益。
- **observation** 9.3.1.4 — 在 5G NR mechanism 中，单个 CB 或 CBG 不被视为可靠；未成功验证 TB CRC 时，不能将其独立交付给 MAC layer。
- **observation** 9.3.1.4 — 启用将通过 CB-level CRC verification 的 CB/CBG 交付给 MAC，可部分解决 PHY layer HOL blocking：错误 CB/CBG 之前的 CB/CBG 将不再被阻塞。
- **observation** 9.3.1.4 — 从 RAN2 角度看，要完全解决 PHY layer HOL blocking，MAC 需要识别每个已交付 CB/CBG 中 MAC subPDUs 的边界。
- **observation** 9.3.1.4 — 是否可以移除 TB-level CRC verification，以及 6G 是否保留 CBG，需要与 RAN1 确认。
- **observation** 9.3.1.4 — 当前 5G NR 的 MAC subPDU 准备与转发方式不支持提前转发 control 或 data subPDU。HARQ 重传中，相关 CB 已正确解码时仍会造成显著时延。
- **observation** 9.3.1.4 — Early forwarding of MAC CEs 和/或其他 control messages 与 PDCP HOL blocking issue 无关。
- **proposal** 9.3.1.4 — RAN2 倾向于在 DCI 中为指定 HARQ process success 提供显式指示，以清除 UL L2 buffers。该指示如何传送由 RAN1 决定。
- **proposal** 9.3.1.4 — UE 收到 HARQ process success indication 后，可清除 uplink L2 buffer 中对应的数据，且不预期继续 HARQ retransmissions。Mediatek 和 ZTE 说明，原意是在 NDI toggled 时发送 ACK，而非每次 transmission 都发送。
- **proposal** 9.3.1.4 — RAN2 决定不继续推进 positive HARQ feedback assisted RLC enhancement，理由是其在 legacy RLC 之上的预期增益不显著或有限。讨论中提及 NACK 与 ACK 可利用同一 bit，以及 HARQ buffer 清理、RLC 恢复和可靠性等考虑。
- **proposal** 9.3.1.4 — Explicit HARQ ACK 被认为有用，可用于快速更新 transmitting window。UL HARQ process status of ACK 无需针对每个 TB 发送，可在 transmission 成功且网络希望在同一 HARQ process 上以 toggled NDI 调度下一个 TB 时 piggyback。
- **proposal** 9.3.1.4 — UL HARQ process status of ACK 也可得到支持。
- **proposal** 9.3.1.4 — 针对 downlink data 的 uplink HARQ feedback，其设计目标是与 uplink data transmission 一样能够抵御 misinterpretation。
- **proposal** 9.3.1.4 — RAN2 将向 RAN1 发送 LS，提供启用 uplink 和 downlink FARQ 的设计要求。
- **proposal** 9.3.1.4 — 对于 DL fast ARQ，RAN2 将讨论如何实现对 NACK-to-ACK error 的快速检测。
- **proposal** 9.3.1.4 — 对于 DL，FARQ 已可行，其实现由 gNB 决定；HARQ feedback 中 NACK to ACK errors 的改进可留给 RAN1 研究。
- **proposal** 9.3.1.4 — RAN2 将基于 N2A/DTX2A error detection 讨论相关问题，具体取决于 RAN1 的确认和进一步指导。讨论内容包括 UE 检测到错误后的行为（如提前终止 t-reassembly、发送 New MAC CE report）以及如何减少冗余 UE reporting。
- **proposal** 9.3.1.4 — RAN2 将就基于 UE assistance information 支持 DL fast ARQ retransmissions 达成一致，例如指示中止后续 HARQ Retx(s) 并触发 RLC re(tx)。
- **proposal** 9.3.1.4 — RAN2 将研究提高 PDSCH transmissions 的 HARQ feedback reliability、减少 HARQ residual errors 的机制，并研究 UE 能否检测特定 HARQ feedback error cases 且向 NW 指示潜在错误。讨论中对 UE feedback 可能带来的额外开销及其帮助 aNB 了解 HARQ internal status 的作用有不同看法。
- **proposal** 9.3.1.4 — 当收到 UL HARQ process status 为 NACK 时，MAC entity 会重新触发对应 MAC PDU 中的 MAC CE，RLC entity 会重新触发其中的 RLC control PDU。
- **proposal** 9.3.1.4 — 对于未成功终止的 uplink HARQ process 对应的 MAC PDU，RAN2 将进一步讨论其重传处理，包括其中的 MAC CE(s) 和 control PDU(s)（如 status report）。
- **proposal** 9.3.1.4 — 当某个 HARQ process 收到 NACK 时，发送端应仅对对应 TB 中复用的 AM radio bearer(s) 的 SDUs 触发 L2 retransmission。
- **proposal** 9.3.1.4 — RAN2 优先研究 higher layer 的 type 1 和 type 2 HOL blocking 问题。
- **proposal** 9.3.1.4 — 研究 type 1/2 HOL blocking 时应考虑应用流量特征：大量并发、动态且短生命周期的 TCP/QUIC connections（例如超过 100），以及指向多样服务器（包括第三方服务器）的多样 IP addresses。
- **proposal** 9.3.1.4 — 解决 type 1/2 HOL blocking 的方案应考虑 scalability、latency、signalling overhead 和 flexibility。
- **proposal** 9.3.1.4 — 为缓解 higher layer HOL blocking，支持在 PDCP 层感知 QoS flow。研究选项包括在 PDCP Data PDU header 中通过 in-band signaling 携带 QFI，或由一个 PDCP entity 拆分到多个 RLC bearers 承载不同 QoS flows 或 QoS flow groups。
- **proposal** 9.3.1.4 — RAN2 将研究接收端避免 HOL blocking 的两种方案：接收 PDCP entity 为不同 QoS flows 或 QoS flow groups 维护不同队列，或为 DRB 中的 QoS flows 配置不同的 in-order delivery requirements。
- **proposal** 9.3.1.4 — HOL blocking 解决方案不应在 DRB 内引入多个 PDCP sequence number spaces。
- **proposal** 9.3.1.4 — 研究接收端对部分 PDCP SDUs 进行选择性处理并乱序转发至上层；如何识别这些 SDUs 及转发标准仍待讨论。研究将不考虑 DRB 内多个 PDCP sequence number spaces，并将接收端选择性处理与 QoS 和 differentiated treatment 一并讨论，同时研究 Type 3 和 Type 4 HOL blocking。
- **proposal** 9.3.1.4 — 向 RAN1 发送 LS，询问无论 TB CRC verification 结果如何，是否有必要且可行将成功解码的 CBs 或 CBGs 交付给 MAC layer。
- **proposal** 9.3.1.4 — 向 RAN1 发送 LS，澄清 lower layer HOL blocking，并询问能否将通过 CB-level CRC verification 的已成功解码 CB/CBG 交付给 MAC layer。原文指出，按 CB multiplexing data 可能造成大量 segmentation 和 header overhead；CB 解码下若不提高 HARQ feedback granularity，fast ARQ 可能导致已解码数据被不必要地重传。
- **proposal** 9.3.1.4 — 从 RAN2 角度，如果能立即使发送端获知接收情况，则将完全/成功接收的 PDUs 从未完全接收的 TB 中交付给上层可能有益。
- **proposal** 9.3.1.4 — 为避免不必要的重传，需要向发送端指示：从未完全接收的 TB 中，某组 CBs 已成功解码。
- **proposal** 9.3.1.4 — 对于 HOL blocking 的 lower layer 解决方案，RAN2 应等待 RAN1 完成 CB/CBG level design 后再继续讨论。
- **proposal** 9.3.1.4 — 研究对不同 payload types 进行 early forwarding 的收益，包括 MAC CEs、Other control messages 和 User Data。
- **proposal** 9.3.1.4 — 研究基于 MAC PDU preparation 的 early forwarding 方案，且不影响 TBtoCB splitting 或其他 RAN1 定义的 PHY 机制。
